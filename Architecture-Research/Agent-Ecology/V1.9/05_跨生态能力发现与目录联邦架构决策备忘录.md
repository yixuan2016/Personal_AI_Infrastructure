## 1. 决策摘要

V1.8 已确立“多中心自治、联邦协调、本地主权执行”的基本边界。V1.9 聚焦一个具体问题：

**如何让一个生态发现另一个生态的能力，并判断该能力是否值得协商，而不把目录发现误当成信任、授权或实时可用性证明？**

本轮形成八项候选决策：

1. **能力权威归属本地。** 每项能力的定义、版本、发布、暂停、撤销和证据由能力 Owner 所在生态负责。
2. **联邦目录只保存最小化摘要。** FCP 可以维护跨生态能力索引，但不取得能力所有权，不保存成员域生产凭证，也不直接执行成员域副作用动作。
3. **目录发现允许最终一致。** 目录只负责返回候选能力；目录新鲜度不足、成员状态不明或撤销状态不可达时，候选必须标记 HOLD，不得用于高风险执行。
4. **授权必须在执行域重新判定。** 发起域、执行域、数据 Owner、资源 Owner 的必要授权均按本地策略检查；目标资源本地 PEP 在副作用发生前执行。
5. **硬约束先于软排序。** 身份、成员状态、授权范围、Purpose、数据分类、地域、版本、撤销和协议兼容属于硬门槛；语义相似度、信誉和成本只能用于合格候选的排序。
6. **观察由 Runtime 保证。** 不依赖模型自发重新读取共享环境；Runtime 应提供事件订阅、状态变更唤醒、游标续读和周期性对账。
7. **协议职责分离。** A2A 负责 Agent 间发现与任务协商；MCP 负责 Agent 与工具/资源交互；CloudEvents 负责事件封套；Ontology 负责共同语义；工作负载身份与策略执行仍由本地信任体系负责。
8. **不建立全局超级信任根。** 每个生态保留本地根身份、根策略和最终授权权；联邦信任通过可验证的成员声明、信任材料和双边/多边关系建立。

## 3. 架构模型

### 3.1 四个逻辑责任域

| 责任域 | 权威职责 | 不拥有的权力 |
|---|---|---|
| Local Ecology Domain | 本地 ADS、Environment Runtime、Ontology、能力 Owner、PDP/PEP、数据与资源 Owner | 不控制其他生态的根策略和本地业务事实 |
| Federation Edge | 成员身份验证、能力导出过滤、签名校验、数据最小化、速率限制、反重放 | 不签发成员域生产授权 |
| Federation Coordination Plane | 联邦目录、摘要同步、候选查询、协商路由、证据索引、事件中继 | 不持有成员域生产凭证，不替代本地 PDP/PEP |
| Human Governance | 根策略、关键审批、独立评估、否决、接管、事故问责 | 不由模型评分或联邦多数投票替代 |

### 3.2 能力目录的双层结构

**本地权威目录（Local Authoritative Directory）**

- 由能力 Owner 所在生态维护；
- 保存完整能力描述、契约版本、依赖、限制、测试证据、发布状态和撤销信息；
- 能够回答该能力当前是否有效、谁负责、何时变更、使用何种策略；
- 本地目录是能力事实的权威来源。

**联邦摘要目录（Federated Summary Directory）**

- 由 FCP 或多个可互联目录节点维护；
- 只同步经过导出策略允许的能力摘要、语义标签、版本、证据引用、有效期和来源水位；
- 可以使用最终一致的增量同步；
- 只用于发现候选和路由，不得签发授权、证明实时可用或替代本地事实；
- 目录被污染或失陷时，影响范围应限制在候选发现，不得直接产生生产副作用。

### 3.3 目录一致性与执行授权分层

| 对象 | 一致性/权威要求 | 允许用途 |
|---|---|---|
| 本地能力定义、Owner、版本 | 本地 Owner 权威；变更有版本和审计 | 能力事实 |
| 联邦能力摘要 | 最终一致；附来源、版本、观察时间和水位 | 候选发现 |
| 运行可用性提示 | 短时有效；必须附观察时间和过期时间 | 候选排序 |
| 成员身份与信任状态 | 来源域签发；执行前核验有效性和撤销状态 | 建立信任上下文 |
| PolicyDecision | 由目标资源/数据 Owner 的 PDP 决定；范围和有效期明确 | 当前授权判断 |
| PEPReceipt | 由目标资源本地 PEP 签发 | 证明执行点的强制执行结果 |
| Environment 投影 | 可最终一致；标记来源水位和新鲜度 | 协作观察与进度展示 |

**关键规则：最终一致只适用于发现视图，不适用于高风险动作的最终授权。**

如果撤销状态不可达、目录水位落后、成员状态过期或证据无法核验，高风险动作必须 HOLD。不得用历史信誉、缓存排序或来源生态的批准代替当前本地授权。

## 4. CapabilityAdvertisement 候选契约

### 4.1 对象定位

CapabilityAdvertisement 是能力 Owner 对外发布的、可验证且有期限的能力声明。它回答“该生态声明自己拥有什么能力”，不回答“请求者是否获准调用”。

### 4.2 最小字段组

| 字段组 | 关键字段 | 目的 |
|---|---|---|
| 标识 | advertisementId、domainId、capabilityId、version | 唯一定位来源与能力版本 |
| 权威 | ownerRef、signerPrincipal、workloadIdentityRef | 明确能力 Owner 与运行主体 |
| 语义 | ontologyRefs、ontologyVersion、conceptId | 跨生态语义映射 |
| 契约 | inputSchemaRef、outputSchemaRef、contractVersion | 输入输出兼容 |
| 接口 | supportedProtocols、endpointRef | 声明 A2A、MCP 或其他交互方式 |
| 范围 | allowedActions、sideEffectClass、dataClasses、purposeRefs | 声明能力边界，不构成授权 |
| 风险 | riskClass、resourceConstraints、residencyConstraints | 约束候选筛选 |
| 证据 | evidenceRefs、evaluationContext、lastVerifiedAt | 支持独立验证 |
| 生命周期 | lifecycleState、issuedAt、expiresAt、revocationRef | 管理发布、暂停、撤销和过期 |
| 完整性 | sourceWatermark、revocationEpoch、digest、signature | 防止伪造、重放和旧状态复活 |
| 导出 | exportPolicy、visibleToDomains | 执行最小化披露 |

### 4.3 能力状态候选

候选状态：PUBLISHED、VERIFIED、ACTIVE、DEGRADED、SUSPENDED、REVOKED、EXPIRED。

- PUBLISHED：Owner 已发布声明，不代表通过独立验证。
- VERIFIED：在明确的验证上下文中有证据支持，不代表所有任务都适用。
- ACTIVE：Owner 声明当前可参与发现；仍需执行前核验。
- DEGRADED：能力受限或服务质量下降。
- SUSPENDED：暂停新协作。
- REVOKED：Owner 撤销该声明或其信任材料。
- EXPIRED：声明超过有效期。

状态变化必须保留来源、版本、时间和签名；不得通过旧事件覆盖新撤销状态。

### 4.4 信誉与能力证明分离

不使用单一信誉分决定能力是否可信。建议保留多维向量：

Identity Assurance、Authorization Validity、Capability Evidence、Provenance Integrity、Safety Record、Freshness、Independent Review、Revocation Status。

硬风险维度不能由其他维度高分抵消。能力验证必须绑定任务类型、输入范围、环境、模型/工具版本、验证时间和限制条件。

## 5. 跨生态能力发现流程

### 5.1 候选流程

1. **任务意图规范化：** 发起方将任务目标映射到共同 Ontology 和本地领域扩展。
2. **本地优先查询：** 优先检索本生态的权威能力目录。
3. **联邦摘要查询：** 本地能力不足时，向获准的联邦目录请求最小化摘要。
4. **硬约束过滤：** 检查成员状态、签名、有效期、撤销水位、Purpose、数据分类、地域、动作级别、协议和 Schema 兼容。
5. **语义匹配：** 使用 Ontology 关系、输入输出类型、能力依赖和任务约束进行匹配。
6. **候选排序：** 仅对通过硬约束的候选，按语义匹配、证据质量、资源、时延和上下文信誉排序。
7. **来源域实时核验：** 拉取最新能力声明、撤销状态和短时可用性证明。
8. **A2A 任务协商：** 协商任务输入、输出、成本、责任、失败处理和证据要求。
9. **本地授权：** 发起域与执行域分别完成必要授权；涉及数据或资源时分别检查 DataUseGrant/Resource Grant。
10. **本地 PEP 执行：** 目标资源本地 PEP 在副作用发生前重新检查策略和撤销状态。
11. **痕迹回写：** Environment 写入状态变化、任务工件、证据引用和回执；联邦视图仅同步获准的投影。
12. **独立验收：** 结果、业务验收和独立评价分别记录，执行成功不等于业务验收成功。

### 5.2 硬约束与软排序

**硬约束：**

- 成员不处于 ACTIVE 或允许的受限试点状态；
- 身份、签名、有效期或撤销状态无法核验；
- Purpose、Audience、数据分类、驻留或动作范围不匹配；
- 本地策略 DENY，或关键策略 ABSTAIN；
- Schema/协议不兼容，且无经批准的转换契约；
- 高风险动作缺少目标 Owner 的实时授权或本地 PEP。

处理结果：DENY、HOLD 或 EXCLUDE，不得进入普通排序。

**软排序：**

- 语义匹配程度；
- 适用上下文中的验证证据；
- 资源成本与时延；
- 能力依赖和可组合性；
- 网络条件和服务质量；
- 历史安全表现与证据时效。

软排序不能改变硬约束结果，也不能把未验证能力升级为 VERIFIED。

## 6. Stigmergy：共享环境观察与触发机制

### 6.1 新增架构判断

共享环境不是一个被动的共享数据库，而是协作状态、任务工件、事件痕迹和因果关系构成的协作介质。

2026-11-09 的两套独立实现复现实验显示：Agent 即使不知道其他 Agent 存在，也可能读取共享存储中其他 Agent 留下的中间结果；但是否写入、是否再次观察共享空间，会受到模型与工作流程指令影响。

因此，不能将“Agent 自己会回来看”当作 Runtime 的可靠保证。

### 6.2 Observation Runtime 必备能力

1. **事件订阅：** Agent 按任务、能力、领域、Purpose 和权限订阅状态变化。
2. **状态唤醒：** 相关事件到达后，Runtime 将观察任务加入调度队列。
3. **游标续读：** 每个订阅记录消费游标、来源水位和已处理事件。
4. **周期对账：** 事件丢失、网络分区或订阅失效时，按本地策略重新读取权威状态。
5. **幂等观察：** 重复通知不产生重复业务副作用。
6. **命名空间隔离：** 按 Ecology Domain、Task、Purpose、Data Classification 隔离共享状态。
7. **痕迹审计：** 记录谁发布、谁读取、谁订阅、谁触发后续动作及其授权依据。
8. **敏感内容最小化：** 共享环境默认存放引用、摘要和状态，不放 Bearer Token、私钥、生产凭证或不必要的原始正文。

### 6.3 观察与通信的混合模式

- 常规协作：优先通过环境状态、工件和事件痕迹进行间接协调。
- 任务协商：使用 A2A 直接交互。
- 工具调用：使用 MCP 或经批准的资源接口。
- 紧急控制：使用明确的控制事件和本地治理流程。
- 状态不确定：读取权威 Owner 状态并对账，不以聊天内容推断事实。

### 6.4 共享环境的安全边界

共享状态本身可能形成非预期通信通道。必须防范：

- 跨租户/跨生态读取；
- 隐蔽写入和数据外带；
- 任意键名覆盖与碰撞；
- 过期工件被重新解释为当前授权；
- 订阅越权和事件投毒；
- 共享缓存中的身份或任务信息泄露。

不得设置无边界的全局共享 Scratchpad。

## 7. 协议映射与接口边界

| 协议/技术 | 负责什么 | 明确不负责什么 |
|---|---|---|
| A2A | Agent Card、Agent 发现、任务协商、任务状态交互 | 生态根治理、完整授权/撤销语义、业务事实权威 |
| MCP | Agent 与工具/资源服务交互、请求响应、扩展任务 | 跨生态成员治理、能力 Owner 权威、业务验收 |
| CloudEvents | 事件来源、ID、类型、主题、Schema 与事件封套 | 事件真实性的业务判断、授权、状态机正确性 |
| Ontology | 概念、关系、约束、语义映射 | 身份认证和执行授权 |
| SPIFFE/SVID | 可选工作负载身份、短期凭证和信任材料分发 | 业务 Purpose 授权、数据 Owner 审批 |
| 本地 PDP/PEP | 策略决策、强制执行、执行回执 | 其他生态的根策略与本地 Owner 决策 |

### 7.1 候选接口

V1.8 已提出联邦能力广告接口。本轮补充一个候选能力解析入口：

- POST /federation/v1/capabilities:resolve：提交语义化能力查询，返回带来源、新鲜度、证据和撤销状态的候选清单。

该路径仅是 FCP 候选接口，不是已批准 API。正式字段、认证、安全方案、分页、缓存、错误码、幂等和 Owner 均需评审。

不得把它与 ADS/SCO 的 API-SIGN-027 SearchCapabilities、API-SIGN-075 GetApiCapabilities 混为同一接口。HybridArchitectureResearch V2.9 已指出这两项属于不同系统；其服务 basePath 仍待 Owner 签认。V1.9 不修改该 75 项 API 基线。

候选 CloudEvents type 命名空间（尚未注册）：

- org.agentecology.capability.advertised.v1
- org.agentecology.capability.updated.v1

## 8. 失效模式与安全控制

| 威胁/故障 | 风险 | 候选控制 |
|---|---|---|
| 伪造能力广告 | 恶意 Agent 被发现 | Owner 签名、身份绑定、来源验证 |
| 目录投毒 | 错误候选被优先选择 | 本地权威校验、独立证据、异常隔离 |
| 目录陈旧 | 已停用能力仍被发现 | 新鲜度字段、TTL、Owner 实时核验 |
| 撤销传播延迟 | 已撤销能力继续被使用 | 撤销水位、单调撤销状态、不可达时 HOLD |
| Sybil/串谋 | 伪造成员和信誉 | 组织/域身份尽调、关联分析、独立评估 |
| 身份混淆 | Agent 冒用其他主体 | Workload Identity、受众绑定、短期凭证 |
| 混淆代理 | Agent 借合法能力越权 | Purpose/Resource/Action 逐项授权 |
| Ontology 错配 | 错误能力被认为兼容 | 版本锁定、映射证据、未知关键概念 HOLD |
| 事件重放/乱序 | 状态回退或重复副作用 | source+id 去重、序列水位、幂等与对账 |
| 共享环境侧信道 | 私有信息越权流动 | 命名空间、字段级策略、最小化、审计 |
| FCP 失陷 | 联邦目录被篡改 | FCP 无成员生产凭证；本地 Owner 重新核验 |
| Agent 自主扩权 | 超越授权执行 | 本地 PDP/PEP、不可委托权限、人类外环 |

## 9. F1 验收设计

所有测试仅允许合成身份、虚构域、模拟能力、模拟密钥和合成数据。F0 未通过前不启动真实双生态测试。

### 9.1 必测场景

- 有效能力广告可发现，但发现结果不产生授权；
- 过期能力广告不能作为高风险执行依据；
- 旧事件不能覆盖新版本或撤销状态；
- 签名错误或来源不明的能力进入隔离；
- 撤销服务不可达时，高风险动作 HOLD；
- 跨域查询不泄露未授权能力细节；
- 语义版本不兼容时明确返回 HOLD；
- 软排序不能覆盖硬约束 DENY；
- A2A AUTH_REQUIRED 不能被解释为已授权；
- MCP 凭证不能跨发行者或跨受众复用；
- 事件重复、乱序、丢失后可以对账；
- FCP 失陷不能直接在成员生态执行生产动作；
- 共享环境中不能读取其他域无权访问的状态；
- Agent 不主动重读时，Runtime 仍能按订阅/唤醒策略触发观察；
- RSI 不得修改根策略、根身份、权限上限或审计历史。

### 9.2 关键安全不变量

- 未授权跨域副作用：0；
- 撤销后高风险使用：0；
- 旧状态覆盖新撤销：0；
- 未授权跨域数据暴露：0；
- 旧 Fencing Token 被接受：0；
- UNKNOWN 后盲目重放：0；
- 无 Owner 的领域事实：0；
- FCP 直接执行成员域生产动作：0。

性能指标（发现延迟、同步延迟、目录命中率、陈旧候选比例、重复观察成本、协作开销）先建立可复现实验基线，不在缺乏实验数据时预设虚构 SLA。

## 11. 本轮结论与待决策事项

### 已形成的候选结论

1. 本地权威目录 + 联邦摘要目录的双层目录架构。
2. 发现最终一致、执行前本地授权的分层一致性模型。
3. 能力广告、能力证明、可用性提示、授权和执行回执的对象分离。
4. 硬约束过滤先于软排序。
5. 共享环境观察由 Runtime 保障，不依赖模型自发行为。
6. A2A、MCP、CloudEvents、Ontology、SPIFFE 的职责边界。
7. FCP 不拥有成员域生产凭证，不作为全局信任根。
