# WP-020｜跨生态信任协议与能力授权链设计备忘录

**版本：** Agent Ecology V1.9 / WP-020  
**日期：** 2026-11-14  
**状态：** Candidate / Research Design  
**范围：** 身份信任、能力 Owner 签名、委托链、运行时令牌、撤销与密钥生命周期  
**不包含：** 生产密钥生成、真实成员入盟、生产令牌签发、Runner 启用或真实跨域执行

---

## 0. 决策摘要

WP-020 的目标是把 V1.8 F0 已定义的“生态身份、运行实例身份、操作授权、能力证据”四类对象，细化成可审查、可验证、可撤销的跨生态信任协议。

**核心结论：Agent Ecology 不建立一个全局超级信任根。** 每个生态保留独立 Root Governance、Domain Identity、密钥管理和本地 Authorization Server。生态之间通过明确的双边信任关系或受约束的联邦信任链互认；FCP 只负责发现、路由和同步最小化的信任元数据，不签发成员域身份，不替成员域批准操作，也不持有成员域生产凭证。

必须严格分离五种判断：

1. **主体身份：** 谁在发起请求（生态、组织、Owner、工作负载、人类审批人）。
2. **声明来源：** 谁签署了能力声明，是否有权代表能力 Owner。
3. **委托合法性：** 当前 Agent 是否在委托链内，是否超出上游权限。
4. **本次操作授权：** 目标生态是否允许该主体在此 Purpose、Audience、Resource、Action、期限和风险等级下执行。
5. **能力可靠性：** 能力声明是否有与当前任务上下文相匹配的独立证据。

任何一项不能由另一项替代。有效身份不是授权；Owner 签名不是调用许可；有效委托不是目标域最终许可；能力证据也不是本次执行安全保证。

## 1. 与 V1.8 F0 的继承关系

WP-020 不修改 V1.8 F0 的治理权力边界，继承以下约束：

- 各生态独立持有根身份、根策略、数据权威、业务 Owner 与本地执行门禁。
- 根治理权限、根私钥、权限上限、生产凭证规则、审计规则和关键审批不可委托给 Agent、RSI 或 FCP。
- 跨域授权采用安全交集：任一必要授权 DENY 即 DENY；关键授权 ABSTAIN、过期、撤销状态不可达或证据缺失时 HOLD。
- 执行域必须在副作用发生前重新验证本地凭证、Purpose、范围、策略版本、撤销状态与预算。
- FCP 可以停止目录发现、路由和新协商，但不能替代成员域本地 Kill Switch 或 PEP。

V1.8 F0 仍为 Candidate / NOT PASSED。WP-020 文档完成不等于 F0 Gate 通过。

## 2. 信任对象与身份层次

| 层次 | 主体/对象 | 主要回答 | 权威来源 |
|---|---|---|---|
| T0 | 生态根身份 / Trust Domain | 哪个自治生态、哪个根治理域 | 各生态自己的 Root Governance |
| T1 | 组织/运营主体 | 谁承担组织和法律责任 | 组织尽调与本地登记 |
| T2 | 能力 Owner / Data Owner / Resource Owner | 谁拥有能力、数据或资源决策权 | 本地域 Ontology / Owner Registry |
| T3 | 工作负载身份 | 哪个 Agent、服务或运行实例正在行动 | 本地域 Workload Identity Provider |
| T4 | 人类审批主体 | 谁对关键操作作出批准或否决 | 本地身份系统与审批收据 |
| T5 | 委托凭证 | 该主体被授予哪些任务级权力 | 委托者与目标域授权服务 |
| T6 | 能力证明 | 能力声明由谁签署、基于何种证据 | 能力 Owner 与独立验证者 |

**SPIFFE/SVID 仅是 T3 工作负载身份的一种可选实现。** 它可证明某个工作负载身份属于哪个 SPIFFE Trust Domain；不能独自证明该工作负载代表哪个业务 Owner，也不能替代 Purpose、DataUseGrant、预算或人类审批。

身份标识建议采用稳定的、带域限定的主体 ID，例如 `domain_id + principal_id`。不得仅凭显示名称、Agent 名称、电子邮件或可变 URL 判断主体同一性。测试、预发布和生产必须使用不同 Trust Domain 与密钥边界。

## 3. 双边信任关系：默认模式

### 3.1 本地信任锚

每个生态维护自己的 Trust Anchor Set。每个本地验证器只接受本地配置明确允许的锚；不能把所有生态的公钥混成一个无域区分的全局 Key Store。

每条 Peer Trust Binding 至少绑定：

- 本地 Domain ID 与对端 Domain ID；
- 双方各自的 Trust Anchor / Key Set 引用；
- 允许的身份 Profile 与签名 Profile；
- 可互认的用途、能力类别、数据分类和最大风险等级；
- 是否允许跨域能力广告、只读目录查询或委托任务；
- 是否允许传递信任（默认 false）；
- 有效期、状态、双方接受收据、撤销端点和单调配置版本；
- 本地策略版本、事故联系人与紧急停止方式。

双方各自保存本地接受记录；任何一方均可独立暂停或撤销关系。单方撤销足以阻止该方继续接受对端身份或新请求，但对端必须收到撤销事件并按本地策略处理在途任务。

### 3.2 不默认传递信任

A 信任 B、B 信任 C，不自动推出 A 信任 C。跨越中间组织或联邦协调器的信任必须显式列出路径、用途和限制，并由 A 的本地策略批准。默认禁止 transitive trust。

OpenID Federation 1.0 可作为需要层级式 Entity Statement、Trust Chain 和 Trust Mark 的可选适配器；它不是 Agent Ecology 必须使用的全局根体系。即使使用第三方 Resolver，本地验证方仍应按本地信任锚与策略独立评估信任链，不能把 Resolver 的返回值当作最终授权。

### 3.3 SPIFFE Federation 的适用边界

若双方均采用 SPIFFE，可通过 Bundle Endpoint Federation 交换外部 Trust Domain 的 Bundle。必须始终保留 `<trust_domain, bundle>` 绑定，不能将不同 Trust Domain 的公钥合并成一个无来源的信任池。Bundle Sequence 用于更新顺序与传播测量；新 Bundle 移除旧密钥后，相关旧 SVID 必须按规范失效。

SPIFFE Federation 解决工作负载身份跨域认证，不解决业务委托和资源授权。信任链应尽量短；每个参与域都成为安全依赖。

## 4. 能力 Owner 签名与声明验证

### 4.1 Owner 对能力声明负责

能力广告由 Capability Owner 或其明确授权的 Publisher 签名。Agent 可以起草、分析、测试和提交待签名变更，但不能因为能访问目录就获得 Owner 签发权。

签发时至少验证：

1. 签发主体属于声明中的 Owner Domain；
2. 签发主体是能力 Owner，或具有未过期且未撤销的 Publisher Delegation；
3. 委托范围覆盖该 capability_id、版本、声明字段和导出受众；
4. 签名密钥属于该主体、用途正确、算法在本地允许列表内；
5. 能力内容摘要、版本、签发时间、过期时间、Purpose、受众与撤销 Epoch 被签名覆盖；
6. 该签名不是从其他环境、其他能力或其他用途复制而来。

### 4.2 规范化与签名配置

候选配置采用 RFC 8785 JSON Canonicalization Scheme（JCS）为 JSON 声明计算确定性摘要；采用 JWS/JWT 作为签名封装候选。JCS 仅解决 JSON 规范化，不负责身份、授权、密钥托管或抗重放。

签名验证必须：

- 按本地 allowlist 校验 `alg`；拒绝 `none`，不得由输入内容自行选择算法；
- 每把密钥只绑定一种算法和明确用途，Owner 签名密钥与工作负载身份密钥分离；
- 校验 `kid`、签发者、受众、`typ`、`iat`、`nbf`、`exp`、`jti`；
- 验证签名覆盖的 payload digest 与实际 JCS 摘要一致；
- 验证 Owner / Publisher Delegation、key epoch 和撤销状态；
- 对不支持的算法、未知密钥、密钥状态未知、签名覆盖范围不明或格式歧义，一律 HOLD / QUARANTINE，不进入可用候选。

初始候选算法集合可考虑 ES256、EdDSA、PS256；实际启用集合由每个生态的安全策略、运行环境和合规要求收窄，不建立全局强制单一算法。任何算法升级必须有双版本验证窗口、迁移截止时间和旧算法退役条件。

## 5. Owner 委托链与权限衰减

### 5.1 委托链规则

委托链采用显式、可验证、可追溯的 Grant 对象：

`Root Governance → Domain Owner → Capability Owner → Authorized Publisher / Agent → Task Actor`

上述链条是职责示意，不表示每个任务都需要所有层级签发。每个实际委托必须能回溯到授予者的合法权限来源。

### 5.2 权限只能衰减

子委托必须满足：

- 子委托的 Action 集合是父委托允许集合的子集；
- Resource 范围、Purpose、Audience、Data Class 不得扩大；
- 子委托有效期不得超过父委托；
- 子委托预算、调用次数、数据量和风险等级不得超过父委托；
- 子委托深度不得超过父委托剩余深度；
- 父委托未明确允许 `mayDelegate=true` 时，禁止继续委托；
- 根治理、根身份、生产根密钥、权限上限和审批豁免永远不得通过 Agent 委托。

语义验证器必须逐层比较父子 Grant 的集合和约束。JSON Schema 只能校验字段形状，不能证明子权限确实是父权限的子集。

### 5.3 禁止代理混淆

委托凭证必须区分：
- `subject`：权利所属主体或被代表主体；
- `actor`：实际执行动作的工作负载；
- `issuer`：签发该 Grant 的授权主体；
- `audience`：唯一或明确列出的目标资源服务；
- `purpose`：当前允许用途。

不得把 Agent 的工作负载身份直接当作用户/Owner 身份；不得将 Agent 之间的任务交接解释为权限自动继承。

## 6. 运行时授权与令牌交换

### 6.1 目标域本地授权

跨生态调用按以下顺序进行：

1. 发起方发现能力，并取得最小化的签名 CapabilityAdvertisement。
2. 发起方验证 Owner 声明、来源 Trust Domain、密钥状态、签名和广告有效期。
3. 发起方建立明确的 Task Contract：Purpose、目标资源、动作、数据类别、预算、期限、风险等级和验收标准。
4. 发起方证明自己的 Workload Identity，并提交必要的 Subject / Actor / Delegation Chain 证据。
5. 目标域本地 Authorization Server 验证成员关系、身份、委托链、目标 Audience、Purpose、撤销状态和本地策略。
6. 目标域按风险等级取得 Data Owner / Resource Owner / 人类审批收据。
7. 只有本地 PDP 返回 ALLOW，PEP 才能在副作用前签发/接受短期、窄范围、受众绑定的执行凭证。
8. 执行完成后回写 PEP Receipt、Task Result、Evidence Ref 和状态事件；失败或超时进入明确状态，不推断成功。

### 6.2 OAuth Token Exchange 可选适配

RFC 8693 Token Exchange 可用于在授权服务器之间表达 Subject 与 Actor 的委托上下文。候选映射：

- `subject_token`：代表被委托主体/任务权利来源；
- `actor_token`：代表当前执行 Agent 或受托工作负载；
- `audience` / `resource`：绑定目标执行服务；
- 输出令牌：由目标域或其认可的授权服务签发，范围不超过已验证 Grant 与本地策略交集；
- `act` 等委托上下文：保留代理链用于审计。

Token Exchange 本身不决定目标域是否应该授权，也不自动证明上游主体有权委托。授权服务器必须独立验证输入 Token 和 Actor Token，并执行本地策略。

### 6.3 防止令牌被盗用

优先采用短期访问令牌、严格 Audience 和最小 Scope。可根据部署选用 DPoP（RFC 9449）或 OAuth mTLS（RFC 8705）进行发送方约束。DPoP 的 `jti`、`htm`、`htu`、`iat` 和可选服务端 nonce 可用于请求绑定与重放检测；多副本服务必须明确共享去重状态或采用其他可验证的防重放方案。

不得把长期密钥、刷新令牌或生产凭证写入 Prompt、Stigmergy 痕迹、共享 Artifact、普通日志或 FCP。令牌只在受控安全通道传递，日志记录其不可逆摘要或安全事件 ID，不记录完整秘密。

## 7. 密钥生命周期与撤销协议

### 7.1 密钥状态机

`GENERATED → ACTIVE → ROTATION_PENDING → OVERLAP → RETIRED`

异常路径：

`ACTIVE / ROTATION_PENDING → SUSPECTED_COMPROMISE → REVOKED`

- Root Key：由各生态人类根治理控制，隔离托管；Agent 不可读取、导出或轮换。
- Domain Signing Key：用于域级成员/委托/声明签名；受 SEC 与 Root Governance 控制。
- Owner Signing Key：只用于 Owner 指定的能力声明和委托签发。
- Workload Key：短期、自动轮换，绑定工作负载身份。
- Token Proof Key：只用于 DPoP 或相应发送方证明，不复用为 Owner 签名密钥。

### 7.2 撤销与水位

每个 Domain 维护自己的单调 `keyEpoch`、`revocationEpoch` 和事件序号。不同 Domain 的序号不可直接比较。

撤销事件至少包含 issuer domain、subject/key/capability/grant ID、旧/新 Epoch、effectiveAt、reasonCode、事件 ID、签名和因果引用。接收方维护每个来源域的独立水位；旧水位、旧事件或过期缓存不能覆盖更高 Epoch 的撤销状态。

高风险执行前必须回源核验或使用满足本地 freshness budget 的可信撤销状态。撤销状态 UNKNOWN / STALE / UNREACHABLE 时：
- 高风险操作：HOLD / DENY，不得继续副作用；
- 低风险只读：仅在本地策略明确允许且使用短时缓存时继续；
- FCP 不可用：不影响本地 Kill Switch 与本地 DENY；不得把目录可用性当作信任状态。

### 7.3 紧急撤销与在途任务

紧急撤销优先停止新任务和新令牌签发，再隔离被怀疑密钥、撤销 Grant、使能力广告失效并传播事件。目标域必须本地拒绝已撤销主体或能力的新副作用请求。对在途任务按风险和补偿策略处理，不允许旧令牌自动续期。恢复必须由原本有权的 Owner / SEC / Root Governance 按本地流程批准。

## 8. 端到端信任与授权状态机

`UNBOUND → PEER_PROPOSED → BILATERAL_ACCEPTED → IDENTITY_VERIFIED → CAPABILITY_ATTESTED → TASK_AUTH_PENDING → LOCAL_POLICY_ALLOWED → TOKEN_ISSUED → EXECUTING → RECEIPTED`

异常状态：

`HOLD / QUARANTINED / SUSPENDED / REVOKED / EXPIRED / DENIED / COMPENSATING`

关键约束：
- `BILATERAL_ACCEPTED` 只表示双方建立了信任关系，不代表任意能力都被允许。
- `IDENTITY_VERIFIED` 只表示主体身份在当前 Trust Domain/Profile 下通过验证。
- `CAPABILITY_ATTESTED` 只表示 Owner 对能力声明的签名与权限链有效。
- `TASK_AUTH_PENDING` 不等于 ALLOW。
- 只有目标域本地 `LOCAL_POLICY_ALLOWED` 并完成必要人工审批，才可进入 `TOKEN_ISSUED`。
- 任意时刻撤销/过期/风险升级均可将流程转入 HOLD / DENIED / REVOKED。
- 任何状态都不得通过重放旧事件回退到更宽松状态。

## 9. 协议适配矩阵

| 技术/规范 | WP-020 采用职责 | 不承担的职责 |
|---|---|---|
| SPIFFE / SVID | 工作负载身份与 Trust Domain Bundle 联邦 | 业务 Owner 授权、Purpose、DataUseGrant |
| OpenID Federation 1.0 | 可选 Entity Statement / Trust Chain / Trust Mark 适配 | 全局生产授权根 |
| JWS / JWT BCP | 签名声明与受众/时间/算法验证 | 业务授权决策 |
| RFC 8785 JCS | JSON 摘要规范化 | 身份或签名算法本身 |
| OAuth Token Exchange RFC 8693 | Subject/Actor 委托上下文交换 | 上游授权合法性与目标域最终许可 |
| DPoP RFC 9449 / OAuth mTLS RFC 8705 | 令牌发送方约束与重放防护 | 资源范围和业务 Purpose |
| A2A | Agent Card、任务协商、状态交互 | Owner 签名和本地 Permit |
| MCP | Agent 与工具/资源服务交互 | 跨生态成员身份治理 |

## 10. WP-020 验收门槛

进入受控合成实验前，至少需要：
1. Trust Domain Binding Schema 完成完整 Draft 2020-12 Validator。
2. Capability Attestation 与 Delegation Grant Schema 完成完整 Validator。
3. JWS/JCS 测试向量覆盖签名、摘要、kid、typ、alg、audience、时间与重放。
4. 父子委托语义验证器证明权限单调衰减。
5. SPIFFE Bundle 映射测试证明 Trust Domain 与 Bundle 不会错配。
6. 撤销事件乱序、丢失、重复、延迟和网络分区测试。
7. OAuth Token Exchange / DPoP / mTLS 的可选适配边界有明确互操作结果。
8. 目标域本地 DENY/HOLD 无法被 FCP、Agent 或上游域覆盖。
9. 本地 Kill Switch 在 FCP 不可用时仍有效。
10. 安全 Owner、各生态 Root Governance 与能力 Owner 完成桌面评审。

**WP-020 当前全部为设计候选；不得标记为实现通过或生产可用。**
