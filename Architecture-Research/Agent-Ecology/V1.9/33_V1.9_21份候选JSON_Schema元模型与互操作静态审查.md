# Agent Ecology V1.9｜21 份候选 JSON Schema 元模型与互操作静态审查

- 审查日期：2026-11-21
- 审查基线：PR #18 候选分支 integration/agent-ecology-v1.9-mainline-clean-20261121
- 审查对象：V1.9/contracts/ 下 21 份候选 JSON Schema
- 审查性质：JSON 语法、Schema 结构、局部组合逻辑、跨协议语义与安全不变量静态审查
- 结论状态：CANDIDATE / STATIC_REVIEW / P0_BLOCKERS_OPEN
- 不构成：完整 JSON Schema Draft 2020-12 Validator 报告、密码学验证、跨语言互操作报告、Runtime 测试报告、Owner 批准或生产安全认证

## 1. 执行结论

本轮逐一读取并解析 21 份候选 Schema，完成以下静态核验：

1. 21/21 文件均可作为 JSON 文档解析。
2. 21 个 $id 均存在且互不重复。
3. 21 份 Schema 均声明 Draft 2020-12。
4. CapabilityResolution 使用 oneOf 区分 Request/Response；3 个内部 $ref 指向同文件 $defs 中的 requiredCapability、constraints、candidate。
5. CoalitionLifecycleEvent 存在一处条件分支属性名大小写错误：条件分支约束根对象未声明的 previousEventDigest，而实际字段为 CloudEvents 小写扩展名 previouseventdigest。
6. TrustRootUpdateEnvelope 的 updateMode 没有配套条件门禁；正常双阈值升级与紧急带外恢复两条路径都允许缺少各自关键证据。
7. WitnessLifecycleEvent 和 WitnessKeyLifecycleRecord 的签名字段在 properties 中定义，却没有列入 required，因此结构上允许无签名生命周期记录。
8. WitnessQuorumPolicy 只把 2q-n>f 存成字符串常量，没有验证 n/f/q 数值关系、见证集合数量和身份唯一性。
9. CapabilityLifecycleEvent 对所有未知顶层属性使用 additionalProperties=true，未限制 CloudEvents 扩展属性名称和 JSON 值类型。
10. Coalition Charter 的 Digest 字段排除规则和多语言 JCS 测试向量仍未冻结；Owner Acceptance 的 signature 目前只是字符串长度约束。

**裁决：** 21 份文件的 JSON 语法解析通过，不等于 21 份 Schema 已通过 Draft 2020-12 元 Schema 验证。当前至少有 4 个 P0 协议门禁缺口、若干 P1 互操作/治理缺口。所有 Schema 保持 Candidate；不得据此冻结协议、启动真实跨生态写操作或把任何验收项改为 PASS。

## 3. 发现的问题

### 3.1 P0｜必须在 F0/F1 协议准入前关闭

#### AE-SCH-P0-01｜Trust Root 更新模式没有互斥的证据门禁

涉及文件：trust-root-update-envelope.schema.json

现状：
- updateMode 允许 NORMAL_DUAL_THRESHOLD 与 EMERGENCY_OUT_OF_BAND_RECOVERY。
- oldRootSignatures 是必填数组，但没有 minItems，允许空数组。
- recoveryAnchorRefs 是必填数组，但没有 minItems，允许空数组。
- newRootSignatures 虽要求至少一项，但没有根据 newThreshold 校验签名数量。
- Schema 没有按 updateMode 分支的 if/then 条件。
- rootThreshold.oldThreshold、newThreshold、minimumDistinctCustodyDomains 与签名数量、Custody Domain 唯一性之间没有可执行绑定。

可构造的危险结构：
- 正常升级模式：oldRootSignatures=[]、recoveryAnchorRefs=[]，仍满足数组字段结构。
- 紧急恢复模式：recoveryAnchorRefs=[]，仍满足数组字段结构。

修订要求：
1. NORMAL_DUAL_THRESHOLD 必须执行旧根阈值与新根阈值双重验证；签名数量、Key Epoch、签名时间、不同 Custody Domain 数量由确定性 Policy Validator 校验。
2. EMERGENCY_OUT_OF_BAND_RECOVERY 必须要求事前登记且独立保管的 Recovery Anchor 证据；不得把失陷旧根的签名当作恢复信任根。
3. 两种模式都必须绑定 Root Digest、单调 Root Version、有效期、签名覆盖范围和防回滚证据。
4. 增加模式专属正向/负向测试；缺少任一模式所需证据必须 FAIL-CLOSED。

#### AE-SCH-P0-02｜WitnessLifecycleEvent 允许无签名生命周期事件

涉及文件：witness-lifecycle-event.schema.json

现状：
- signature、issuedBy、issuerKeyId、issuerKeyEpoch 在 properties 中定义。
- 根 required 未包含上述字段。
- 因此事件可以有 eventDigest，却没有可验证的签名和签发者/密钥身份绑定。

修订要求：
1. 将签发者、签名密钥 ID、Key Epoch、签名对象列为必填。
2. 将签名从不透明字符串升级为明确 Profile：格式、算法、Key ID、Key Epoch、规范化/摘要 Profile、签名覆盖范围和签名值。
3. 对 eventType 建立合法状态迁移表；ACTIVATED、SUSPENDED、QUARANTINED、REINSTATED、RETIRED 等必须具有各自所需的审批与证据。
4. 运行时验证签名、身份、权限、事件序列和前序摘要；JSON Schema 通过不得被解释为事件可信。

#### AE-SCH-P0-03｜WitnessKeyLifecycleRecord 允许无签名、无最终事件摘要

涉及文件：witness-key-lifecycle-record.schema.json

现状：
- signature、eventDigest 在 properties 中定义，但未列入 required。
- keyStatus 可表达 ACTIVE、SUSPECTED_COMPROMISE、QUARANTINED、REVOKED、RETIRED、DESTROYED 等状态。
- 结构上允许关键密钥状态记录不携带签名和事件摘要。

修订要求：
1. signature 和 eventDigest 必须成为必填字段。
2. 必须绑定 witnessId + keyId + keyEpoch + keyFingerprint + keyPurpose + lifecycleSequence。
3. 对 REVOKED、DESTROYED、SUSPECTED_COMPROMISE 等状态要求相应时间、原因和证据字段。
4. 禁止旧 Key Epoch 重新激活；状态转换由追加式事件验证器检查。

#### AE-SCH-P0-04｜WitnessQuorumPolicy 未验证实际 Quorum 数学关系

涉及文件：witness-quorum-policy.schema.json、witness-fault-scenario.schema.json

现状：
- intersectionRule 固定为字符串 2q-n>f，但没有验证数值字段。
- totalWitnesses、maxByzantineWitnesses、requiredCosignatures、minIntersection 各自只有独立的最小值。
- totalWitnesses 未绑定 witnesses 数组实际长度。
- 未对 Witness ID、Key ID、Public Key Fingerprint 做跨条目唯一性验证。
- 未验证运营域、故障域、Witness Group 的集合关系。
- 因此不满足 2q-n>f 的数值组合也可能通过结构检查。

修订要求：
1. 定义唯一的 Quorum Policy Validator，输入固定成员集合、n、f、q、Witness Group、运营域和故障域。
2. 至少验证 q<=n、f<n、2q-n>f、签名数门槛和独立运营/故障域约束；所有公式须以规范化整数计算。
3. totalWitnesses 必须等于去重后的有效成员集合大小；重复 ID、Key、Fingerprint 或不合格成员不得计入 Quorum。
4. Quorum Policy 的签署接受必须绑定相同 Policy Digest、Peer Binding、Key Epoch 和有效期。
5. 无法完成独立性核验、成员集对账或公式验证时返回 HOLD/QUARANTINE，不得自动降低门槛。

### 3.2 P1｜协议冻结前必须明确

#### AE-SCH-P1-01｜CloudEvents 扩展属性没有一致的命名和类型约束

涉及文件：capability-lifecycle-event.schema.json

现状：
- 根对象使用 additionalProperties: true。
- 未限制未知顶层属性的名称是否符合 CloudEvents 小写 ASCII 字母/数字命名规则。
- 未限制未知顶层属性的值是否属于 CloudEvents 类型系统允许的 JSON 类型。
- 这与 CoalitionLifecycleEvent、FederationRevocationEvent 使用封闭对象的策略不一致。

修订要求：
- 对允许扩展的事件采用明确 Profile：未知扩展属性只允许 CloudEvents 规定的属性名字符集和受支持值类型；复杂对象放在 data 负载中。
- 对不允许扩展的事件继续采用封闭 Schema，但明确其版本兼容策略。
- 对每个事件定义扩展属性注册表，避免同名异义和跨协议映射冲突。

#### AE-SCH-P1-02｜CoalitionLifecycleEvent 存在无效的条件分支属性名

涉及文件：coalition-lifecycle-event.schema.json

现状：
- 根字段为小写 CloudEvents 扩展属性 previouseventdigest。
- allOf[0].then.properties 同时包含 previousEventDigest 与 previouseventdigest。
- 根 additionalProperties=false，因此 previousEventDigest 不属于合法根字段；该条件分支对它的约束不可达/无效。

修订要求：
- 删除错误大小写的 previousEventDigest 分支，只保留 previouseventdigest。
- 保留 sequence=1 时前序摘要为全零摘要的约束。
- 增加 sequence=1、sequence>1、缺失前序摘要、错误摘要长度的正负测试。

#### AE-SCH-P1-03｜Coalition Charter Digest 与 Owner Acceptance 签名 Profile 尚未冻结

涉及文件：coalition-charter.schema.json、WP-026 静态审查

现状：
- Charter 同时包含 charterDigest 与 acceptances[]；每个 Acceptance 又绑定 charterDigest。
- 文档已指出采用 JCS，但 Digest 输入字段排除规则、签名覆盖范围和跨语言测试向量仍 OPEN。
- Acceptance 的 signature 仅为字符串长度约束；Schema 没有定义算法、签名格式、签名摘要和编码。

修订要求：
1. 定义 Charter Digest 的唯一规范化投影：明确是否排除 charterDigest、acceptances、签名值、创建时间等字段，禁止循环摘要。
2. 定义 Acceptance Receipt 的规范化载荷，绑定 Charter Digest/Version/Epoch、接受角色、Scope Digest、Policy Digest、Principal、Key ID/Key Epoch、Audience 和接受时间。
3. 固定签名算法允许列表、签名封装格式和编码；提供跨语言正负向量。
4. 新版本、范围变化、Purpose/成员/预算/风险变化必须触发受影响 Owner 重新接受。

#### AE-SCH-P1-04｜PeerTrustBinding 的传递信任开关缺少额外准入门禁

涉及文件：peer-trust-binding.schema.json

现状：
- transitiveTrust 是必填布尔值。
- ACTIVE 状态要求双方接受，但 Schema 没有对 transitiveTrust=true 要求额外的授权范围、链路深度、目的限制和独立接受证据。

修订要求：
- 初始 Profile 默认且建议固定 transitiveTrust=false。
- 若未来允许开启，必须有独立的双方显式接受、最大链路深度、允许目的、身份映射和撤销传播规则。
- A 信任 B 不自动推出 A 信任 C；不得把传递信任用于扩大 Owner Grant 或目标域 Permit。

#### AE-SCH-P1-05｜Witness Registry 的 ACTIVE 状态不保证独立性证据已通过

涉及文件：witness-registry.schema.json

现状：
- operationalStatus=ACTIVE 与 independenceClaim 未建立条件约束。
- separateOperator、separateAdministrativeControl、separateKeyCustody、separateFailureDomain 可以为 false。
- evidenceRefs 没有 minItems，允许空数组。

修订要求：
- 区分在线可用与可计入 Quorum 的独立 Witness 两个状态。
- 只有独立审查证据通过的 Witness 才可进入 Quorum eligible set。
- 对运营主体、管理权限、密钥托管、云账号/供应链和故障域进行共同控制分析；自我声明不等于独立性证明。

#### AE-SCH-P1-06｜Witness Quorum、Policy Approval 和 Owner Acceptance 的签名封装不一致

涉及文件：witness-quorum-policy.schema.json、coalition-charter.schema.json、witness-recovery-snapshot-manifest.schema.json

现状：
- 不同对象有的采用 JWS 对象，有的只用字符串 signature。
- 部分签名对象包含 Key ID/Key Epoch，部分缺少算法、签名摘要或签名覆盖范围。
- 结构层不能确保不同实现对同一对象签署完全相同的字节序列。

修订要求：
- 建立公共 Signature Profile：format、algorithm、keyId、keyEpoch、canonicalizationProfile、signedPayloadDigest、signatureValue、typ。
- 明确 JWS Protected Header 与外部字段的一致性检查。
- 不同签名用途必须区分域分离，禁止同一密钥跨 Trust Root、Witness、Log、Backup、Transport 等用途复用。

#### AE-SCH-P1-07｜Owner Delegation Grant 的父子权限衰减仍依赖运行时语义

涉及文件：owner-delegation-grant.schema.json

现状：
- Schema 可检查 mayDelegate 与 maxDelegationDepth 的局部组合。
- 不能验证子 Grant 的 Capability、Resource、Action、Purpose、Audience、DataClass、Risk、Budget、期限和撤销 Epoch 是否均不超出父 Grant。

修订要求：
- 定义确定性 Grant Attenuation Validator，逐维验证子集/上限/期限/深度单调性。
- 父 Grant 撤销必须按依赖图阻断所有后代授权。
- 缺少父 Grant、父摘要不匹配、循环委托或状态未知时 HOLD。

#### AE-SCH-P1-08｜Witness 生命周期状态转换和 Key 状态时间关系没有条件约束

涉及文件：witness-lifecycle-event.schema.json、witness-key-lifecycle-record.schema.json

现状：
- 事件类型/密钥状态使用枚举，但没有定义允许的前后状态迁移。
- REVOKED、DESTROYED、SUSPECTED_COMPROMISE 等状态与对应时间字段之间没有 Schema 条件约束。
- 需要防止已撤销密钥被重新激活、事件序列回退和历史状态被覆盖。

修订要求：
- 建立事件状态机与 Key Lifecycle Validator。
- 状态转换必须追加式、单调、可签名、可重放验证。
- 非法转换、Epoch 回退、事件链断裂和时间矛盾一律拒绝或隔离。

#### AE-SCH-P1-09｜FederationSyncCheckpoint 的有效期和快照连续性绑定不完整

涉及文件：federation-sync-checkpoint.schema.json

现状：
- validUntil 存在于 properties，但不在 required。
- snapshot.snapshotSequence 与顶层 contiguousSequence 没有跨字段相等性约束。
- completeRevocationSet=true 与 includesAllTombstones=true 是声明值，不能证明实际快照完整。

修订要求：
- 明确 Checkpoint 的有效期是否必须；若是，设为必填并定义时钟偏差/过期处理。
- 运行时核验快照序列、摘要、Merkle Root、连续性证明、完整墓碑集合和来源签名。
- 快照完整性不能仅由布尔声明或 Merkle Root 自证。

#### AE-SCH-P1-10｜Lifecycle Event 的状态机约束仍需运行时验证

涉及文件：coalition-lifecycle-event.schema.json、capability-lifecycle-event.schema.json

现状：
- 枚举限制了 eventType、fromState、toState 或 lifecycleState 的取值。
- Schema 不能单独证明某种事件允许从某一状态迁移到另一状态，也不能证明事件序列、来源水位和撤销 Epoch 单调。

修订要求：
- 建立统一 Lifecycle Transition Registry。
- 将事件类型、前态、后态、Actor Role、审批证据、Epoch 和有效时间绑定。
- 对重复事件、乱序、Gap、回放和状态复活建立负向测试。

## 5. 下一轮必须形成的验证资产

1. 完整 Draft 2020-12 Validator 报告：固定验证器名称/版本、Draft、命令、执行环境、所有 Schema 的元 Schema 验证结果和输出。
2. Schema Positive/Negative Vector：每份 Schema 至少覆盖正常样例、缺失必填、未知字段、错误类型、错误枚举、越权/撤销/过期、边界值和跨字段不变量。
