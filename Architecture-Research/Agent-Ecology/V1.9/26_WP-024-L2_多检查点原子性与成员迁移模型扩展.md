# WP-024-L2｜多检查点原子性、密钥纪元与成员迁移模型扩展

**版本：候选研究设计 0.1｜日期：2026-11-16**  
**上位基线：Agent Ecology V1.9 / WP-020—WP-024 / WP-024-L0/L1**  
**研究性质：架构研究、形式化模型扩展设计与验收规划；不代表已运行 TLC、确定性模拟或生产测试。**

## 1. 本轮目标

WP-024-L0 已对固定成员 Quorum 集合完成组合穷举；WP-024-L1 已使用 Python BFS 有限状态参考检查器研究单个 Witness 在状态擦除恢复后是否可能对冲突 Checkpoint 双签。本轮不重复这两项工作，而是把验证对象从“一个 Witness 对两个冲突值”扩展到更接近真实透明日志见证服务的生命周期：

1. 多个 Checkpoint 连续推进时，并发请求能否造成状态回退或冲突签名？
2. 崩溃、快照恢复、WAL 截断或身份克隆后，原 Witness 是否可能在丢失防双签状态的情况下重新 ACTIVE？
3. Key Epoch、Membership Epoch、Trust Root Version 和 Policy Digest 变更时，旧新成员能否对同一过渡状态形成一致认可？
4. 网络分区、监视器视图滞后和跨运营域共因故障，是否会造成错误 PASS 或错误宣称独立性？
5. 安全性与活性是否被分开验证，而不是以“多数节点可达”代替完整安全条件？

本轮只定义下一层模型和证据门槛，不新增生产实现，不启用 Runner，不修改 main。

## 2. 既有验证结果及边界

### 2.1 L0：固定成员 Quorum 组合穷举

对 n=4/7/10/13、q=2f+1 的全部不同 Quorum 集合对完成 262,611 对穷举。四组参数的最小交集均符合 2q-n=f+1。

这只证明给定固定成员集合、固定阈值和身份去重假设下的组合交集性质；不自动证明节点行为诚实、密钥安全、状态持久化正确、成员迁移安全或真实部署可用。

### 2.2 L1：单个决策实例的恢复状态模型

Python BFS 参考模型在 n=4、Byzantine={W1}、q=3 的有限模型中：
- 不在签名前持久化、恢复后重新 ACTIVE：发现 14 步冲突证书反例。
- 签名前持久化、但恢复时清空状态并重新 ACTIVE：仍发现 14 步反例。
- 签名前持久化、恢复后隔离：在该有界模型中未发现反例。
- 签名前持久化、恢复后保留单调状态：在该有界模型中未发现反例。

以上是 Python BFS 有限状态结果，不是 TLC 结果；“未发现有界反例”不等于对任意协议或实现的数学证明。

### 2.3 当前 TLA+ 模型覆盖范围

现有 WitnessRecovery.tla 使用固定 Witness 集合、一个抽象日志实例、两个互斥 Checkpoint 值 A/B，以及每个 Witness 的 durable、pending、status、signatures 状态。它适合研究状态擦除与双签的最小反例，但尚未显式表示：

- Checkpoint 的 Tree Size、Root Hash 和连续性证明；
- 同一 Witness 对 N、N+1、N+K 等多个 Checkpoint 的推进；
- 两个并发请求携带相同 oldSize 的比较并推进；
- Membership Epoch、Key Epoch、Trust Root Version；
- Policy Digest、Registry Digest 和双方接受的过渡配置；
- 外部单调锚、独立 Monitor 高水位、WAL 水位和快照代次；
- 运营域、密钥托管域、部署域等共同故障关系。

因此，当前模型不能替代 WP-024 矩阵中并发提交、成员迁移、外部高水位对账和灾难恢复相关项目的验证。

## 3. 本轮外部证据与架构启发

### 3.1 C2SP Transparency Log Witness Protocol v1.1.0

该协议要求 Witness 检查请求中的 old size 是否等于其为该日志最近一次签署的 Checkpoint 大小；通过一致性验证后，必须先持久化新 Checkpoint 再响应。规范明确指出，检查旧大小与持久化新状态必须原子执行，否则并发请求可能先提交 N+K，再被较晚完成的旧请求回写成 N，造成状态回退。

**对本项目的启发：** WP-024-L2 必须显式建模 Compare-and-Advance（比较并推进）原子事务，不能只建模“签名前先写一个值”。Witness Quorum 仍是透明证据见证机制，不应被误写为完整 BFT 状态机共识。

来源：https://c2sp.org/tlog-witness@v1.1.0

### 3.2 The Update Framework（TUF）Specification 1.0.37

TUF 规范版本 1.0.37 于 2026-10-08 更新。其 Root 更新要求逐版本取得 N+1 元数据；新 Root 必须同时满足前一版本 Root 的签名阈值和新 Root 自身的签名阈值，并拒绝跳号或回滚。这为信任根升级提供了可借鉴的连续信任链模式。

**对本项目的启发：** Trust Root Version 不得直接跳跃；常规升级必须绑定旧根阈值、新根阈值、版本连续性和完整 Digest。根阈值失陷的紧急恢复仍应走事先登记的带外恢复锚，不能伪装成普通轮换。

来源：https://theupdateframework.github.io/specification/latest/

### 3.3 NIST SP 800-57 Part 1 Rev.6 状态

截至 2026-11-16，NIST 官方 Key Management Publications 页面仍将 SP 800-57 Rev.6 标记为 Draft；其 Initial Public Draft 于 2025-12-05 发布，评论期于 2026-02-05 结束。Rev.5 仍列为 Final。

**对本项目的启发：** Rev.6 可以作为密钥管理研究输入，但不得标注为最终生效规范；正式合规映射应区分 Rev.5 Final 与 Rev.6 Initial Public Draft。

来源：
- https://csrc.nist.gov/Projects/Key-Management/publications
- https://csrc.nist.gov/pubs/sp/800/57/pt1/r6/ipd

### 3.4 状态擦除恢复与 BFT Quorum 交集研究

arXiv:2610.07759 于 2026-10-06 发布，研究单阶段 BFT 证书模型中，正确副本若丢失投票状态但保留原身份和签名密钥，可能破坏依赖 Quorum 交集的安全性。作者明确区分单阶段证书与多阶段协议；多阶段协议还需要按其 View、Locking 和 Justification 规则单独分析。

**对本项目的启发：** 该预印本支持把状态擦除、身份保留和密钥保留作为独立威胁变量，但不能据此宣称 C2SP Witness 协议或所有 BFT 协议普遍不安全。

来源：https://arxiv.org/abs/2610.07759

## 4. WP-024-L2 模型扩展设计

### 4.1 核心状态变量

建议在现有最小模型之外增加以下抽象状态：

| 状态域 | 变量 | 含义 |
|---|---|---|
| Checkpoint | lastSize、lastRootHash、lastCheckpointDigest | 每个日志实例的最新已接受状态 |
| 并发事务 | requestId、expectedOldSize、targetSize、targetRootHash | 请求的比较基准和目标状态 |
| 持久化 | durableSequence、walWatermark、snapshotGeneration | 已提交状态、WAL 水位和快照代次 |
| 外部锚 | externalCheckpoint、externalSequence | 独立 Monitor/Witness 可核对的外部高水位 |
| 身份与密钥 | witnessId、keyId、keyEpoch、keyStatus | 身份唯一性、密钥纪元和生命周期 |
| 成员配置 | membershipEpoch、memberSet、quorumPolicyDigest | 当前成员集合及 Quorum 策略 |
| 信任根 | trustRootVersion、oldRootDigest、newRootDigest | 信任根连续升级链 |
| 治理策略 | registryDigest、policyDigest、ownerAcceptance | Registry、Policy 与 Owner 双边接受状态 |
| 故障域 | operatorDomain、kmsDomain、deploymentDomain | 运营、密钥托管和部署控制域 |

以上为模型变量候选，不代表已经冻结的数据 Schema。

### 4.2 核心状态转换

1. **Submit：** 接收 Checkpoint 请求，记录 requestId、expectedOldSize 和目标 Digest。
2. **Validate：** 校验签名、身份、Key Epoch、策略版本和 Merkle 一致性证明。
3. **AtomicCompareAndAdvance：** 在同一原子事务中比较 expectedOldSize 与当前 lastSize，验证连续性，持久化新状态和 WAL 水位。
4. **ReleaseSignature：** 仅在原子提交成功后释放 Cosignature；提交成功但响应丢失时，重试必须幂等。
5. **Crash / Recover：** 在提交前、提交后、签名后、响应前等边界注入崩溃；恢复必须核对本地快照、WAL 与外部高水位。
6. **RotateKey：** 进入新 Key Epoch，记录旧密钥停止签名、撤销或退役状态。
7. **BeginMembershipChange：** 建立新 Membership Epoch 和过渡策略；旧、新成员集合对同一个 Checkpoint Digest 和 Policy Digest 形成联合确认。
8. **MonitorReconcile：** 从独立 Monitor 或 Witness 获取最新 Checkpoint，发现分叉、回退或证据缺失时进入 HOLD/QUARANTINED。
9. **Activate：** 只有状态连续性、密钥、成员、策略和独立故障域门禁全部通过，并完成治理审批后，才允许恢复 ACTIVE。

### 4.3 必须检查的不变量

- **I-01 单调性：** 同一日志的 Tree Size 不得回退；相同 Tree Size 不得出现不同 Root Hash。
- **I-02 不双签：** 同一 Witness 身份不得对不一致的 Checkpoint 历史释放签名。
- **I-03 原子提交：** 每一份已释放签名都必须对应已经持久化的状态推进记录。
- **I-04 幂等恢复：** 提交成功但响应丢失后，重试不能重复推进或制造冲突签名。
- **I-05 身份唯一：** 同一 witnessId 即使使用多个 URL、实例或 Key ID，也只能按一个成员计票。
- **I-06 Epoch 绑定：** 签名必须绑定 Membership Epoch、Key Epoch、Registry Digest 和 Policy Digest；不同版本不得混合计票。
- **I-07 恢复隔离：** 无法证明快照、WAL 和外部高水位连续时，旧身份不得恢复 ACTIVE。
- **I-08 根升级连续：** 常规 Root 更新必须逐版本验证旧根阈值和新根阈值，拒绝跳号与回滚。
- **I-09 联合迁移：** 成员迁移期间，旧、新 Quorum 必须针对同一过渡 Checkpoint 与同一策略 Digest 完成确认；不得各自认可不同 Root Hash。
- **I-10 故障域独立：** 同一控制域、KMS 域或部署域的多个实例不能被重复计算为独立 Witness。
- **I-11 证据新鲜度：** Monitor 视图过期、外部锚不可达或撤销水位不明时，不得返回可信 PASS。
- **I-12 阈值不降级：** 分区、节点退出或故障预算超限不得自动降低 Quorum 阈值。

### 4.4 安全性与活性分开

安全性检查回答“是否可能产生冲突签名、回退或错误授权”；活性检查回答“在明确的网络稳定、节点可达、故障预算和公平调度假设下，是否最终能够完成签署或恢复”。

网络分区时，系统可以牺牲可用性进入 HOLD；不能为了恢复可用性自动降低 Quorum。任何活性结论必须写清楚同步性、可达节点数量、故障上限和公平性假设。

## 5. L2 最小验证场景

| 编号 | 场景 | 预期结果 |
|---|---|---|
| L2-01 | 两个请求均以 N 为 oldSize，分别推进 N+1 与 N+K | 只能有一个原子推进成功；另一个冲突重试，不得回写旧状态 |
| L2-02 | 相同 Tree Size、不同 Root Hash | 拒绝签名并记录分叉证据 |
| L2-03 | 状态提交成功、响应返回前崩溃 | 恢复后保持已提交状态，重试幂等 |
| L2-04 | 已签名后恢复旧快照 | 外部水位高于本地时隔离旧身份 |
| L2-05 | 本地快照有效但外部锚不可达 | 保持 OBSERVE_ONLY/HOLD，不恢复签名 |
| L2-06 | Key Epoch 已撤销但旧快照仍 ACTIVE | 拒绝旧 Epoch，要求新密钥与审批 |
| L2-07 | Root Version 从 N 跳到 N+2 | 拒绝跳号，逐版本核验 |
| L2-08 | Root 更新缺少旧根或新根阈值签名 | 拒绝常规升级 |
| L2-09 | 旧、新 Quorum 对同一过渡 Digest 均确认 | 按 Joint Quorum 规则进入下一阶段 |
| L2-10 | 旧、新 Quorum 确认不同 Root Hash | 拒绝迁移，固定 Fork Evidence |
| L2-11 | 同一身份通过多个端点或密钥重复计票 | 只计一个 witnessId |
| L2-12 | 多个 Witness 共用同一 KMS/管理员控制域 | 不满足独立故障域门槛，不得 PASS |
| L2-13 | Monitor 仅观察到过期 Checkpoint | 标记 STALE/INDETERMINATE，高风险操作 HOLD |
| L2-14 | 故障数超过 f，尝试自动降低 q | 拒绝自动降级，进入隔离或人工治理 |

以上为待执行的模型场景；不得把预期结果标注为已经通过的测试。

## 6. 工具与验证路线

### L2：扩展模型
- 保留现有单决策模型作为最小反例基线。
- 增加多 Checkpoint、并发比较并推进、Epoch、外部高水位和成员迁移状态。
- 将每项不变量映射到具体状态变量与反例场景。

### L3：模型检查
- 先运行现有三个 TLC 配置，记录工具版本、命令、配置、状态数和结果。
- 再运行 L2 的小规模固定参数配置，优先检查安全性不变量。
- 对活性性质单独设置公平性和网络假设，不与安全性结果混写。
- 使用 Python BFS 作为独立参考检查器；只有在状态、假设和性质一致时才比较轨迹。
- 可评估 Apalache 的有界模型检查作为补充，不将不同工具的模型语义差异隐藏起来。

TLC 对有限配置的完整状态探索只对该配置、常量和假设成立；不自动证明任意规模或真实实现正确。

### L4：确定性模拟与故障注入
在模型层发现反例并修复后，才设计确定性分布式模拟和 Jepsen 风格故障注入，覆盖延迟、乱序、重复、分区、进程崩溃、磁盘回滚、快照截断、密钥撤销与恢复。所有结果必须保留可重放种子、事件轨迹和独立 Checker 证据。

### L5：独立复核与治理
- 由独立复核者检查模型假设是否遗漏真实攻击路径。
- 真实 HSM/KMS、备份、外部 Checkpoint 和灾难恢复演练另设批准门禁。
- 任何生产密钥、生产凭证和真实跨生态接入均需 Owner、安全与人类治理审批。

## 7. 候选决策与验收门槛

建议后续在 ADR 登记册中评审以下候选决策：

- **ADR 候选：Atomic Checkpoint Compare-and-Advance。** Checkpoint 比较、连续性验证、状态持久化必须构成原子推进边界。
- **ADR 候选：Recovery Continuity Proof。** 快照签名不等于新鲜度证明；无法核对外部高水位时隔离旧身份。
- **ADR 候选：Epoch-Bound Joint Membership Transition。** 成员迁移必须绑定同一 Checkpoint Digest、Policy Digest、Membership Epoch，并由旧、新配置共同确认。

正式验收门槛：
1. TLA+ 模型语法与配置通过工具检查；
2. 危险配置能够重现已知反例；
3. 安全配置在明确边界内未发现反例；
4. 并发提交、恢复、密钥轮换和成员迁移场景均有可复现轨迹；
5. 独立复核确认模型假设、性质和反例解释；
6. 未运行的项目继续保持 NOT_RUN，不以文档完成替代验证通过；
7. 在 Owner 与人类治理审批前，productionAllowed=false，Runner 不启用。

## 8. 本轮结论

WP-024-L0/L1 已证明固定成员 Quorum 交集的组合结果，并揭示状态擦除恢复可能破坏依赖身份交集的安全假设；但尚未验证真实 Witness 的多 Checkpoint 并发原子推进、Epoch 绑定、Joint Quorum 迁移和外部恢复连续性。

**下一项最优先工作是 WP-024-L2：把“单值双签模型”扩展为“多 Checkpoint 原子推进 + 身份/密钥/成员 Epoch + 外部恢复锚”的有限状态模型。**

这项工作完成并经过 TLC 与独立复核之前，不进入真实双生态生产试点，不降低 Quorum，不允许恢复身份自动重新获得签名权。
