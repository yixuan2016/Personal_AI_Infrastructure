# WP-023｜跨生态可信见证网络治理、密钥生命周期与灾难恢复

**版本：** Agent Ecology V1.9 / WP-023  
**日期：** 2026-11-15  
**状态：** Candidate / Research Design  
**范围：** Witness 生命周期、运营主体治理、密钥生命周期、信任根升级、备份恢复、灾难恢复、重新加入与 Quorum 联合迁移  
**不包含：** 真实根密钥、生产 Witness 节点、HSM/KMS 生产配置、真实灾难演练、自动化密钥轮换、生产 Runner 或生产授权

---

## 0. 决策摘要

WP-022 建立了 Witness Cosignature、K-of-N Quorum、Monitor Gossip 和 Fork Evidence。但多方见证网络本身仍可能遭遇密钥泄露、运营主体退出、Witness 管理域被接管、状态存储回滚、备份损坏或信任根失陷。

**WP-023 的核心决策：将 Witness 网络视为具有独立身份、密钥、策略和持久状态的自治治理网络；所有加入、退出、密钥轮换、策略迁移和恢复都必须产生可验证的生命周期事件，并且不能绕过历史连续性验证。**

本工作包建立六类治理能力：

1. **Membership Governance（成员治理）：** Witness 提名、独立性审查、观察期、激活、暂停、退出、替换和重新加入。
2. **Key Lifecycle（密钥生命周期）：** 密钥生成、用途隔离、激活、轮换、停用、泄露标记、撤销、归档和销毁。
3. **Trust Root Update（信任根升级）：** 版本单调、门槛签名、过期检测、回滚防护和紧急恢复锚。
4. **State Continuity（状态连续性）：** Witness 最新 Checkpoint、状态序列、WAL、备份清单和外部见证锚。
5. **Disaster Recovery（灾难恢复）：** 先冻结风险、再验证证据、后恢复信任；不能证明连续性时隔离，不允许静默重置。
6. **Joint Policy Migration（联合策略迁移）：** 成员集合或 Quorum 变更时，旧策略和新策略必须对同一过渡 Checkpoint 建立可验证的联合接受。

## 1. 架构边界

### 1.1 密钥分层与职责隔离

| 密钥类别 | 职责 | 建议保护 | 不得承担 |
|---|---|---|---|
| Trust Root Keys（信任根密钥） | 签署 Witness Registry、Quorum Policy 信任根和紧急恢复授权 | 离线、多方分持、门槛签名 | 日常 Checkpoint 签名 |
| Witness Signing Keys（见证签名密钥） | 对指定 Log Origin 的 Checkpoint 生成 Cosignature | HSM/KMS 或受控签名设备、用途绑定 | 修改根策略、授予业务权限 |
| Log Signing Keys（日志签名密钥） | 签署来源生态 Checkpoint | 与 Witness 密钥分离 | 为 Witness 身份背书 |
| Backup Encryption Keys（备份加密密钥） | 加密状态快照、WAL 和恢复材料 | 独立保管、访问审计、定期恢复验证 | 签署 Checkpoint 或策略 |
| Transport / Workload Identity（传输/工作负载身份） | 认证管理 API、节点间连接和自动化任务 | 短期凭证、可撤销身份 | 替代 Witness Cosignature |

不得跨角色复用同一私钥。任何密钥材料、访问令牌、恢复口令和 HSM 导出内容均不得写入 Git、普通配置文件、日志或公开证据包。

### 1.2 信任根不是单一在线服务

- 根密钥持有人应分属不同运营主体或独立治理角色。
- 根密钥离线保存，按事先批准的门槛共同签署。
- 根密钥负责授权 Witness 身份、角色、策略和恢复锚，不直接签署每个业务 Checkpoint。
- Witness 在线签名密钥按单一 Witness 身份和用途隔离，泄露不得直接导致整个生态根密钥失陷。
- FCP 仅负责目录和消息中继，不持有根密钥，不决定成员身份，不替代信任根。
- 每个 Peer Binding 必须明确接受自己使用的 Trust Root Version、Witness Registry Version 和 Quorum Policy Digest。

### 1.3 外部规范借鉴边界

TUF 面向软件更新系统，而不是多生态 Witness 治理协议。本项目只借鉴其安全原语：根元数据版本递增、旧根与新根门槛签名、逐版本连续验证、元数据过期检测和回滚/冻结攻击防护；不宣称 WP-023 等同于 TUF 实现。

NIST SP 800-57 Rev.6 当前检索到的是 Initial Public Draft（2025-12-05 发布，2026-02-05 截止征求意见），不是最终版。可作为密钥管理、存储、密钥失陷和恢复规划参考，正式采用前需重新核验最终出版状态。

## 2. Witness 成员生命周期

### 2.1 状态机

`PROPOSED → IDENTITY_VERIFIED → OBSERVE_ONLY → ACTIVE`

异常与退出路径：

- `ACTIVE → SUSPENDED`：临时停止新签名，保留只读观察和历史证据。
- `ACTIVE → QUARANTINED`：发现密钥/状态/运营异常，隔离，不参与 Quorum。
- `SUSPENDED → ACTIVE`：完成独立审查、状态连续性验证、密钥有效性复核和策略重新接受。
- `ACTIVE → RETIRING → RETIRED`：经策略迁移退出，不再参与新 Quorum。
- `QUARANTINED → RETIRED`：无法恢复信任或运营主体退出。
- 重新加入必须生成新的 Membership Epoch；不得将旧 Witness 的历史状态、密钥或签名记录删除后重新注册为“干净节点”。

### 2.2 加入门槛

Witness 进入 ACTIVE 前至少完成：

1. 运营主体身份与控制权核验。
2. 管理员、密钥托管、云账号、备份和发布流水线的控制关系披露。
3. 公钥指纹、算法、Key Epoch 和用途登记。
4. 签名端点与独立监视端点验证。
5. Checkpoint 验签、Consistency Proof、单调状态和原子持久化互操作测试。
6. 观察期内只读取/验证、不计入 Quorum。
7. 独立审查者签署加入证据。
8. 更新 Witness Registry 与 Quorum Policy，并由 Peer Binding 双方接受同一版本和 Digest。

观察期长度由风险和验收策略确定，不在架构层面虚构统一天数。观察期结束不自动激活。

### 2.3 退出与替换

- 退出事件必须带有生效时间、最后参与的 Policy Version、最后签名 Checkpoint 和后继/替代关系。
- 退出不抹除该节点过去签署的 Checkpoint、Cosignature 或审计记录。
- 替换节点先进入 OBSERVE_ONLY，完成独立性审查与历史状态同步后再进入新策略。
- 不能在旧节点退出后自动降低 Quorum 门槛或把新节点临时算作旧节点。
- 旧、新策略过渡期间，必须对同一个过渡 Checkpoint 同时满足旧 Quorum 与新 Quorum（Joint Quorum），或使用双方事先接受且明确约束安全性的专门恢复路径。
- Joint Quorum 的目的是确保成员集合切换时不会出现两个独立配置分别认可不同历史的窗口；不意味着所有场景都必须长期双重签名。

## 3. 密钥生命周期

### 3.1 Key State

`GENERATED → REGISTERED → ACTIVE → DEPRECATED → RETIRED → DESTROYED`

异常路径：

- `ACTIVE → SUSPECTED_COMPROMISE → QUARANTINED → REVOKED`
- `DEPRECATED → REVOKED`
- `ACTIVE → REVOKED`

每次状态变化必须生成不可覆盖的 Key Lifecycle Event，并绑定：

- witnessId、keyId、公钥指纹、算法、Key Epoch；
- 密钥用途、授权范围、运营主体和密钥托管域；
- 生成、登记、激活、停用、泄露发现、撤销和销毁时间；
- 事件签发者、签名密钥 Epoch、事件序列、前一事件 Digest；
- 相关 Checkpoint、Policy Version 和事件证据引用。

私钥只保存在经过批准的签名设备或密钥托管系统。Schema 只保存公开密钥标识和受控引用，不接收或输出私钥。

### 3.2 正常轮换

1. 新密钥在独立安全环境生成。
2. 核验算法、密钥长度/参数、用途和保护等级。
3. 将新公钥登记为 PREPARED，不立即接受其签名。
4. 由旧密钥和按策略要求的信任根/独立审批者签署 Key Transition Statement。
5. 更新 Witness Registry 和 Quorum Policy 的 Key Epoch。
6. Peer Binding 双方接受新 Policy Digest。
7. 进入新旧密钥重叠验证窗口：新密钥先通过观察和互操作检查；过渡 Checkpoint 按明确策略处理。
8. 新密钥激活后，旧密钥停止签署，进入 DEPRECATED/RETIRED。
9. 保留旧公钥、证书/身份材料和历史事件以供离线历史验证；不得删除历史验证所需信息。

轮换失败不得回滚 Key Epoch 或重新激活已撤销密钥；应暂停签名并启动恢复流程。

### 3.3 密钥疑似泄露与历史签名判断

必须区分：
- `detectedAt`：发现时间；
- `suspectedCompromiseSince`：最早可能泄露时间；
- `confirmedCompromiseAt`：确认时间；
- `revokedAt`：正式撤销时间。

如果泄露开始时间无法确定，采用最早可信怀疑时间作为保守风险边界；不能用“发现时间”假定之前签名都安全。

历史签名分级：

| 情形 | 历史验证状态 | 新签名权限 |
|---|---|---|
| 有可信时间戳/Checkpoint 证明，且早于最早疑似泄露时间 | 可按历史策略继续验证 | 立即停止旧密钥 |
| 签名时间落在疑似泄露区间 | INDETERMINATE / HOLD | 停止 |
| 签名晚于泄露边界 | REJECT / COMPROMISED | 停止 |
| 缺少可信时间证据，无法定位签名先后 | INDETERMINATE | 停止 |
| 仅正常退役，无泄露迹象 | 按签名时有效策略验证 | 不再用于新签名 |

不能因今天撤销密钥，就无差别否定所有历史签名；也不能因历史签名曾被 Quorum 接受，就默认泄露后签名继续有效。历史验证必须同时检查签名时的密钥状态、策略版本、可信时间证据和 Checkpoint 见证状态。

## 4. Trust Root Update（信任根升级）

### 4.1 正常升级

候选规则：

1. Trust Root Version 严格递增，一次只接受当前版本的下一个版本。
2. 新根元数据由旧根阈值和新根阈值分别签名；每个唯一 Key ID 最多计一次。
3. 更新必须逐版本验证，不允许从旧版本直接跳到未验证的新版本。
4. 根元数据必须有有效期；过期、更新长期不可达或版本回退时进入 STALE/HOLD。
5. 根元数据、签名、策略、Witness Registry 和历史版本归档必须可离线复核。
6. Trust Root、Witness Registry 和 Quorum Policy 版本之间必须显式绑定，避免混合读取不同版本造成策略拼接。
7. Root Rotation 完成后，所有 Peer Binding 必须按自己的信任关系获取并接受新版本；不能由 FCP 自动替所有生态接受。

### 4.2 紧急根密钥失陷

如果旧根密钥达到失陷门槛，不能继续依赖旧根签名证明新根可信。必须使用预先登记的独立 Emergency Recovery Anchors（紧急恢复锚）：

- 恢复锚由不同运营/治理主体离线分持；
- 门槛、身份和适用范围在事故发生前登记；
- 紧急恢复必须产生独立事件、审查报告和新的根版本；
- 新根必须重新核验 Witness Registry、Quorum Policy、密钥 Epoch 和 Peer Binding；
- 各 Peer Binding 通过已登记的带外渠道核验新根指纹；
- 不能通过网络自动发现一个新公钥并将其当成可信根；
- 无法证明恢复锚有效时，相关跨生态信任保持 SUSPENDED/HOLD。

### 4.3 版本回滚与冻结

- Root Version、Policy Version、Membership Epoch 和 Key Epoch 均不得倒退。
- 任何旧版本响应必须与本地已接受版本比较，低于本地版本即拒绝并留痕。
- 元数据过期或长时间无法获取更新时，标记 STALE；高风险动作 HOLD。
- 不允许通过延长本地时钟、重置数据库或清除版本记录绕过冻结检测。
- 时间源不可信时，依赖单调计数器、可信时间戳和外部 Witness 观察；无法判定时 HOLD。

## 5. Witness 状态备份与恢复

### 5.1 必须备份的状态

- 每个 Log Origin 的最新已验证 Checkpoint；
- Checkpoint Tree Size、Root Hash、Log Origin 和一致性证明引用；
- 已接受的 Trust Root、Witness Registry、Quorum Policy 版本及 Digest；
- Witness Membership Epoch、Key Epoch 和 Key Lifecycle Events；
- 状态提交序列、WAL/事务日志位置、备份代次和前序快照 Digest；
- 关键审计事件、签名响应索引、隔离和恢复事件；
- 恢复所需的公开密钥、算法参数、验证器版本和策略解释材料。

不备份明文私钥，不把 KMS/HSM Secret 导出到快照；备份加密密钥和恢复授权材料单独管理。

### 5.2 备份结构

每个恢复快照包含：
- snapshotId、witnessId、logOrigin；
- stateSequence、snapshotGeneration、previousSnapshotDigest；
- latestCheckpointDigest、treeSize、rootHash；
- trustRootVersion、registryVersion、policyVersion；
- keyEpoch、lastAcceptedEventSequence、WAL watermark；
- capturedAt、storageFailureDomain、encryptionKeyRef；
- snapshotDigest、完整性签名、保留策略和独立见证收据。

至少保存跨不同管理/故障域的加密副本，并进行定期恢复验证。多份备份如果共享同一管理账号、密钥托管或发布流水线，不能被认定为真正独立。

### 5.3 防回滚恢复原则

- Witness 在签名任何新 Checkpoint 前，必须把本地恢复状态与独立 Witness 最新观察、已知 Quorum Bundle 和来源 Log 的一致性证明进行比对。
- 快照签名只证明快照来源和完整性，不证明快照是最新状态。
- 快照的 generation、stateSequence、policyVersion、keyEpoch 必须与外部可信锚比较。
- 若快照低于已知状态、WAL 缺失、前序 Digest 断裂或无法获得一致性证明，进入 QUARANTINED。
- 不得通过重置 stateSequence、删除历史文件或重新初始化数据库绕过回滚检查。
- 只有完成独立核验、连续性证明和恢复审批后，才允许恢复 ACTIVE。

### 5.4 恢复点目标

- **Anti-equivocation State RPO：** 已经对外返回有效 Cosignature 的状态必须在返回前持久化；不得存在“已签名但未持久化”的窗口。
- **Backup RPO：** 由业务风险、WAL 连续性、外部 Checkpoint 见证和可恢复能力共同确定；不在缺乏实测时宣称固定 RPO=0。
- **RTO：** 按风险域分别设定并通过演练测量；恢复时间未测量前不得给出承诺值。
- 如果不能证明最新状态，宁可延迟恢复和保持 HOLD，也不能以旧状态继续签名。

## 6. 灾难恢复 Runbook

| 阶段 | 主要动作 | 放行条件 |
|---|---|---|
| 0. 事件分级 | 判断密钥失陷、状态损坏、运营退出、根失陷或区域故障 | 确定影响范围和事件负责人 |
| 1. 风险冻结 | 停止受影响 Witness 新签名；相关 Peer Binding 高风险 HOLD | 冻结范围和时间已记录 |
| 2. 证据保全 | 固定内存/存储/日志证据、Checkpoint、Cosignature、备份和访问审计 | 独立审查者可读取原始证据 |
| 3. 密钥处置 | 标记疑似失陷时间、撤销密钥、暂停相关身份和令牌 | 新旧密钥与受影响 Epoch 明确 |
| 4. 根信任恢复 | 正常双阈值 Root Rotation，或启用预登记 Emergency Recovery Anchors | 根版本和带外指纹核验通过 |
| 5. 状态恢复 | 选择快照、重放 WAL、核对独立 Witness 最新 Checkpoint | 连续性、单调性、策略版本均通过 |
| 6. 成员/策略重建 | 替换失陷节点、重新评估运营域、签署新 Policy | Peer Binding 双方接受同一 Digest |
| 7. 观察期 | 先 OBSERVE_ONLY，不计入生产 Quorum | 独立观察和故障注入达标 |
| 8. 恢复服务 | 按策略逐步恢复签名；保留事故告警与监控 | 人类外环批准，目标域本地策略放行 |

### 6.1 恢复失败时

- 进入 QUARANTINED，不允许自动初始化一个“空白但 ACTIVE”的 Witness。
- 若原 Witness 身份不能恢复，创建新 Membership Epoch 和新密钥。
- 若 Trust Root 不能恢复，停止依赖该根的所有跨生态信任，等待带外重新绑定。
- 旧签名、Checkpoint 和 Fork Evidence 归档保留，不能以重建为由清除。
- 重新加入不自动继承旧节点的 Quorum 票权。

## 7. 多运营主体与共同故障域治理

独立性审查不仅看公钥和组织名称，还必须检查：

- 最终控制人和管理员权限；
- 云账号、KMS/HSM、备份账号和网络控制平面；
- 软件构建、部署流水线和供应链；
- 事故响应、审计和恢复审批是否由同一主体控制；
- 运行地域、网络供应商和时间服务；
- Witness 与 Log Operator 是否存在利益冲突；
- 多 Witness 是否共享相同的第三方托管服务。

建立 `operatorDomainId`、`administrativeDomainId`、`keyCustodyDomainId`、`backupFailureDomainId` 和 `deploymentDomainId`。Quorum 计算必须使用实际独立域证据，而非仅使用名义组织名称。

独立性证据需要定期复核；发生控制权、云账号、托管商或管理员变化时，应触发重新评估。无法证明独立性的 Witness 可以保留为观察节点，但不得被计入独立运营域门槛。

## 8. Joint Quorum（联合策略迁移）

成员集合变化会改变 WP-022 的 n、f、q 和交集关系。不得把“新旧节点都能签名”简单理解为安全迁移。

候选迁移步骤：

1. 生成新 Policy Version 和完整成员变更 Diff。
2. 验证旧策略与新策略各自的 2q-n>f 假设、独立域约束和 Key Epoch。
3. 双方 Peer Binding 接受相同的新 Policy Digest 和过渡区间。
4. 对同一过渡 Checkpoint，同时要求旧 Quorum 与新 Quorum 通过。
5. 所有 Monitor 获取并比较同一过渡 Checkpoint 和策略版本。
6. 过渡完成后，旧节点停止新签名并进入 RETIRING。
7. 新策略成为唯一 ACTIVE 策略，旧策略只保留历史验证用途。
8. 若旧 Quorum 无法满足，进入受控恢复流程，不自动把新 Quorum 当作旧 Quorum。

若无法建立安全的联合过渡，则必须暂停相关跨域高风险操作，并由双方治理主体重新设计成员切换窗口。

## 9. 关键指标与验收

- ACTIVE / OBSERVE_ONLY / SUSPENDED / QUARANTINED / RETIRED 成员数量与变更历史；
- Witness 独立运营域、管理域、密钥托管域和故障域覆盖率；
- 各 Key Epoch 的有效、过期、撤销、疑似失陷和历史验证状态；
- Root / Registry / Policy Version 单调性和更新传播延迟；
- 双阈值 Root Rotation 成功率、回滚/冻结攻击检测率；
- 已返回 Cosignature 与持久状态提交的严格先后关系；
- 备份快照 Digest、WAL 水位、跨故障域副本和恢复验证结果；
- 恢复后 Checkpoint 与外部 Witness 的一致性；
- Joint Quorum 迁移成功率和过渡期拒绝/隔离事件；
- RPO/RTO 实测分布、恢复失败率、误 HOLD 率和恢复后回滚次数。
