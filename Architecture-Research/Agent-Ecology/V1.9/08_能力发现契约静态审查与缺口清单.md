# V1.9｜能力发现候选契约静态审查与缺口清单

**日期：2026-11-14｜审查范围：CapabilityAdvertisement / CapabilityResolution 两份 JSON Schema 与跨生态能力发现备忘录**  
**审查类型：静态结构审查；不构成完整 JSON Schema 合规验证、密码学验证、互操作测试或生产安全评估。**

## 1. 审查结果摘要

已从 GitHub 远端回读两份候选 Schema，并通过 JSON 解析检查：

- capability-advertisement.schema.json：JSON 语法有效。
- capability-resolution.schema.json：JSON 语法有效。
- 两份 Schema 均声明 JSON Schema Draft 2020-12。
- CapabilityResolution 使用 oneOf 区分 Request 与 Response。
- Response 将 authorizationGranted 固定为 false，这是正确的安全方向。
- 本轮未执行完整 Draft 2020-12 Validator，也未执行签名验证、跨字段语义验证、协议互操作或负向测试。

**结论：可以进入候选契约评审，但不能标记为 Schema 已通过或接口已冻结。**

## 2. P0 安全缺口

### CR-01｜CapabilityAdvertisement 缺少机器可读的“非授权”标记

现状：
- Schema description 表明广告只用于发现，不授予调用权。
- CapabilityResolutionResponse 有 authorizationGranted=false。
- CapabilityAdvertisement 本身没有必填的 notAuthorization=true 或 authorizationGranted=false。

风险：
- 消费方可能把 ACTIVE/VERIFIED 能力广告误解为可以直接调用。
- 仅依赖自然语言 description，无法形成可靠的机器校验不变量。

建议：
- 增加必填 notAuthorization=true，或固定 authorizationGranted=false。
- 在广告、解析结果、A2A Task、PolicyDecision 和 PEPReceipt 之间保持不同对象类型。

### CR-02｜候选资格与撤销/新鲜度状态缺少跨字段约束

现状：
- Candidate.eligibility 可为 ELIGIBLE_CANDIDATE。
- attestationStatus 可为 UNKNOWN/EXPIRED。
- revocationStatus 可为 UNKNOWN/STALE。
- ResolutionResponse.freshnessStatus 可为 STALE/PARTIAL/UNKNOWN。
- 现有 JSON Schema 没有完整约束这些字段之间的组合。

风险：
- 可能出现撤销未知或目录陈旧，但候选仍被标记为可用。
- 消费方实现不一致，可能将软排序结果误用于高风险动作。

建议的语义不变量：
- attestation INVALID/EXPIRED → INELIGIBLE。
- revocation REVOKED → INELIGIBLE。
- revocation UNKNOWN/STALE → HOLD。
- freshness STALE/UNKNOWN，或关键目录水位缺失 → HOLD。
- 只有签名有效、撤销状态可核验、策略硬约束通过且语义/Schema 兼容时，才允许 ELIGIBLE_CANDIDATE。
- 任一硬约束 DENY 不得被语义分数、信誉或成本排序覆盖。

### CR-03｜签名有效性与来源身份绑定不能由 JSON Schema 单独证明

现状：
- Schema 包含 signerDomain、signerPrincipal、keyId、algorithm、payloadDigest 和 signatureRef。
- Schema 不能验证密码学签名，也不能证明 signerPrincipal 有权代表 capabilityOwner。

风险：
- 结构合法的广告可能仍是伪造、重放或由无权主体签发。
- payloadDigest 若没有规范化序列化和签名覆盖范围，可能产生多种解释。

建议：
- 单独定义签名覆盖范围、规范化序列化、密钥状态和算法允许列表。
- 验证 signer 与 Owner 的授权委托关系。
- 校验签名、摘要、有效期、撤销水位和防重放 nonce/epoch。
- 验证失败或密钥状态未知时进入 HOLD/QUARANTINE，不进入普通候选排序。

## 3. P1 契约完整性缺口

### CR-04｜VERIFIED 状态缺少明确的验证上下文

现状：
- lifecycleState 包含 VERIFIED。
- Schema 有 evidenceRefs，但没有必填 verifierRef、verificationContextRef、verifiedAt、验证方法和模型/工具版本。

建议：
- VERIFIED 必须绑定独立验证者、任务类型、输入范围、环境、模型/工具版本、验证时间、证据等级和限制条件。
- Owner 自述、发布成功或可用性探测不能单独把状态提升为 VERIFIED。
- 需要区分 Owner 声明、来源签名、独立评估和业务验收。

### CR-05｜分页响应缺少对应的请求游标字段

现状：
- Response 有 nextPageToken。
- Request 没有 pageToken/cursor，也没有 maxCandidates/pageSize。

建议：
- Request 增加 pageToken 和 pageSize/maxCandidates。
- 定义分页游标绑定 requester、purpose、过滤条件、目录水位和过期时间。
- 不允许客户端修改游标内容扩大可见范围。

### CR-06｜成本约束和证据等级缺少规范化单位/枚举

现状：
- maxCost 可出现，但 costUnit 不要求同时出现。
- requiredEvidenceLevels 目前是任意字符串。

建议：
- maxCost 存在时必须提供 costUnit、计费维度和有效期。
- requiredEvidenceLevels 使用受控枚举（如 E0-E4），并明确本项目证据等级定义。
- 证据等级不可由目录排序器自行升级。

### CR-07｜导出策略与可见域列表缺少组合约束

现状：
- exportPolicy 包含 PUBLIC、FEDERATION_MEMBERS、NAMED_DOMAINS、PRIVATE_REFERENCE_ONLY。
- visibleToDomains 是可选字段。

建议：
- NAMED_DOMAINS 必须提供非空 visibleToDomains。
- PRIVATE_REFERENCE_ONLY 只能返回受控引用和最小必要元数据。
- PUBLIC 仍须执行字段级敏感信息过滤，不等于公开 endpoint、内部依赖或凭证。
- 目录缓存必须尊重导出策略变化和撤销。

### CR-08｜时间关系和新鲜度水位缺少语义校验

现状：
- 有 issuedAt、observedAt、expiresAt、sourceWatermark、revocationEpoch。
- 有 availabilityHint 的 observedAt/expiresAt。
- JSON Schema 未表达所有时间先后和跨对象约束。

建议：
- expiresAt 必须晚于 issuedAt。
- observedAt 不得晚于当前验证时间；超出 freshness budget 必须标记 STALE。
- availabilityHint 过期不能覆盖广告过期或撤销。
- sourceWatermark 和 revocationEpoch 必须单调，旧值不能复活旧状态。
- 不同 Owner 的聚合序号不可直接比较。

### CR-09｜候选记录应暴露必要的来源水位

建议：
- Candidate 至少引用 advertisementRef，并可回溯 sourceWatermark、revocationEpoch、observedAt 和证据水位。
- Response 的 directoryWatermark 不能代替每个来源域的水位。
- 任何缺失的来源水位均应按风险等级决定 HOLD 或重新向 Owner 对账。

### CR-10｜能力生命周期事件缺少独立事件 Schema

现状：
- 备忘录列出 advertised/updated/suspended/revoked/expired 等候选 CloudEvents type。
- 本轮尚未提供这些事件的 JSON Schema 与状态迁移规则。

建议：
- 后续定义统一事件封套和事件 data Schema。
- 绑定 source、id、type、dataschema、Owner 聚合序号、因果引用、签名和发生时间。
- 对撤销事件设置单调性、幂等、乱序保护和重放测试。

## 4. 与现有架构边界的关系

1. 能力广告只描述能力，不构成调用授权。
2. 联邦摘要目录允许最终一致；本地 Owner 目录是能力事实权威。
3. 高风险动作必须在执行域重新核验身份、Purpose、撤销和本地策略。
4. A2A AUTH_REQUIRED 只表示任务等待授权，不代表已授权。
5. MCP 凭证必须按发行者、受众、范围和有效期约束。
6. CloudEvents 负责事件封套，不负责业务事实真实性或授权。
7. SPIFFE/SVID 可提供工作负载身份，但不替代业务 Purpose、DataUseGrant 和人类审批。
8. FCP 不持有成员域生产凭证，不直接执行成员域副作用动作。
9. ADS/领域 Owner 保留本地权威；FCP 的发现与路由结果不能覆盖本地 DENY/HOLD。
10. 所有 Schema 和接口保持 Candidate，不能回写为正式 ADS/SCO API 基线。
