# WP-021｜跨生态目录一致性与撤销传播研究证据登记

**日期：** 2026-11-15  
**状态：** Research Evidence / Design Candidate  
**原则：** 规范或论文中的机制可作为设计依据，但不代表 Agent Ecology 已部署、复现或通过验收。

| 来源 | 类型/状态 | 已有机制与证据 | WP-021 可借鉴点 | 适用边界 |
|---|---|---|---|---|
| CloudEvents Core Specification v1.0.2（事件 specversion 仍为 1.0） | CNCF 项目规范 | 定义 source、id 等事件上下文；source + id 对每个不同事件唯一，重复重发可沿用相同 id；扩展属性名限定为 ASCII 小写字母/数字，建议不超过 20 字符，属性值限于规范类型 | 以 (source,id) 建立持久去重键；Feed 序列与签名摘要作为小写标量扩展属性；复杂签名/主体对象放入 data 负载 | CloudEvents 不承诺传输 exactly-once，也不提供来源签名、连续序列或授权决策 |
| Kubernetes API Concepts：Watch / resourceVersion / BOOKMARK / 410 Gone | Kubernetes 官方 API 文档 | List-then-watch；BOOKMARK 表示已发送到某 resourceVersion；历史版本不可用时返回 410 Gone，客户端需重新 List 并续 Watch | 建立游标、进度水位、断线续读、历史压缩后的重新同步流程 | Kubernetes resourceVersion 语义不能直接等同跨生态 Feed Sequence；只借鉴控制流模式 |
| etcd v3.6/v3.7 Watch API | etcd 官方 API 文档 | start_revision、progress_notify、compact_revision；压缩后旧历史不可再读取 | 事件流续读、进度通知、Gap 检测和压缩恢复 | progress notify 只是服务端进度提示；分区节点的本地 revision 不一定代表集群最新状态 |
| Dynamo（SOSP 2007） | 已发表系统研究 | 高可用 KV 系统；以 Merkle Tree 比较副本差异，支持 anti-entropy 同步并减少数据传输 | 用 Merkle 树定位不一致分区，避免每轮全量拉取 | Dynamo 选择了特定可用性/一致性权衡；不直接满足跨生态身份、授权或撤销安全要求 |
| RFC 9162 Certificate Transparency v2 | IETF Experimental RFC（2021-12） | Merkle inclusion proof、consistency proof 验证追加历史；文档指出单一 Log 可能向不同客户端展示不一致视图，Gossip 检测属于其范围外 | 借鉴签名 Tree Head、追加历史证明、跨接收方 Checkpoint 对账 | 该 RFC 是 Experimental，目标是 TLS 证书透明日志；不应宣称为通用联邦目录规范 |
| Shapiro 等：A Comprehensive Study of Convergent and Commutative Replicated Data Types | INRIA Research Report RR-7506（2011-01-13） | 形式化状态型/操作型 CRDT；G-Set 仅支持 add/lookup，使用集合并集形成单调半格；2P-Set 使用 tombstone 集合并规定删除后不再重新添加 | 只对不可变对象撤销墓碑采用 add-only 集合并集，保证合并不删除已知撤销 | 不将整个能力目录做成 G-Set；目录元数据、版本和授权仍需 Owner 权威、事件序列与本地策略 |

## 研究判断

- **已验证的技术原语：** CloudEvents 事件标识语义、Kubernetes/etcd 的游标续读与历史压缩处理、Dynamo 的 Merkle 反熵实践、RFC 9162 的追加历史一致性证明、G-Set 的单调并集合并。
- **尚未验证的项目组合：** 把上述机制组合成多自治生态的签名撤销 Feed、Peer Binding 专属连续序列、完整快照恢复、撤销墓碑与本地 PEP 联动。
- **关键限制：** 消息被确认接收不等于撤销已生效；Merkle Root 不等于快照包含完整数据；签名的单一 Checkpoint 不足以排除来源域向不同接收者展示不同视图；最终一致目录不构成授权。
- **建议：** 先做确定性状态机与小规模故障注入，再评估消息总线、事件存储和 Merkle 实现选型；本轮不指定厂商或编写生产代码。
