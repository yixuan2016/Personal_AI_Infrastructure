# WP-021｜跨生态能力目录一致性与撤销传播协议

**版本：** Agent Ecology V1.9 / WP-021  
**日期：** 2026-11-15  
**状态：** Candidate / Research Design  
**范围：** 联邦能力目录增量同步、撤销事件、源域序列、水位、快照恢复、反熵同步、网络分区与本地执行门禁  
**不包含：** 生产消息总线部署、真实跨域事件推送、真实密钥/撤销凭证、Runner 启用或生产任务执行

---

## 0. 决策摘要

WP-021 解决一个分布式安全问题：多个自治生态的能力目录可以因网络延迟、消息重复、事件乱序、历史压缩、节点失联或恶意中继而暂时不一致；但目录同步故障不能使已撤销的能力、密钥、成员关系或委托重新变为可执行。

**核心决策：目录视图可以最终一致；安全撤销必须单调、可验证，并在目标域本地执行边界生效。**

本轮提出六项候选机制：

1. 每个来源生态为每条受信任 Peer Binding 提供明确的安全控制事件流；流内序列号连续递增，不跨生态比较。
2. 采用 CloudEvents 风格事件封装，使用 (source, id) 做持久幂等去重；传输按至少一次交付设计，不假设 exactly-once。
3. 对已验证的撤销事件立即添加本地撤销墓碑；即使前序事件缺口未补齐，也不能延迟已知撤销的生效。
4. 事件缺口、来源水位过期、签名未知或状态不可达时，保持连续水位不前进；高风险跨域动作进入 HOLD。
5. 历史被压缩后，只允许通过来源域签名的完整撤销快照和可验证的摘要/一致性证据恢复；不得把游标直接跳到最新值。
6. FCP 只做缓存、中继、目录发现和反熵协调；来源域是其自身事件的权威，目标域本地 PDP/PEP 是最终执行权威。

## 1. 安全不变量

### 1.1 来源权威不转移

- 能力 Owner / 成员域授权主体仍是对象状态的权威签发方。
- 来源域签名的事件由来源域负责；FCP 不得自行制造、改写、补序或签发撤销事件。
- 接收生态可暂停接受某来源域，但不能替来源域改写其历史。
- 目标域本地 DENY / HOLD 不得被来源域 ALLOW、目录 ACTIVE 或 FCP 缓存覆盖。

### 1.2 撤销单调

撤销对象必须使用不可变的对象引用（例如能力版本、Grant ID、Key ID + Key Epoch、Peer Binding Version）。撤销后，该对象版本永不重新 ACTIVE。

- 撤销状态以只增不减的墓碑集合保存，合并采用集合并集。
- 目录更新、旧广告、旧快照或旧事件均不得删除已知墓碑。
- 如需恢复服务，必须由有权 Owner 重新签发新对象版本、新签名和新授权；不得对原撤销对象执行“取消撤销”。
- 父 Grant 撤销后，引用其授权链的子 Grant 必须在语义验证器中判为失效；不能只撤销父对象而继续使用孤立子凭证。

### 1.3 序列只在自己的流内有序

- 序列作用域为 (sourceDomainId, streamId)；不同 Domain、不同 Stream 的序列号不可比较。
- 每个 Peer Binding 的安全控制 Feed 应对接收方提供连续的 feedSequence，事件必须绑定 peerBindingId。若采用字段过滤，不得静默跳过序列；应使用独立 Feed，或发送可验证的最小化占位记录。
- 来源域的 revocationEpoch 是域级单调版本，可跳号；它不是跨域全局时钟。
- 事件时间 time/effectiveAt 仅用于业务时效与审计，不用于替代来源序列判定先后。

## 2. 目录与控制面分层

| 平面 | 数据 | 一致性目标 | 权威 |
|---|---|---|---|
| 本地权威目录 | Owner 签名的能力对象、版本、状态 | Owner 域内按对象版本/事务约束提交 | Capability Owner |
| 联邦发现目录 | 最小化能力摘要、版本、来源、状态提示 | 允许最终一致，允许暂时缺失 | FCP 是缓存/索引，不是权威 |
| 安全控制事件流 | 撤销、密钥/Grant/成员/Peer Binding 状态变化 | 连续水位、可验证顺序、幂等处理 | 来源 Domain |
| 接收方撤销索引 | 已知撤销墓碑、来源水位、快照根 | 墓碑单调；水位不可回退 | 接收方本地安全服务 |
| 执行授权平面 | Purpose、Action、Resource、Audience、风险、Freshness | 执行前本地重新判定 | 目标域 PDP / PEP |

能力目录状态 ACTIVE 只表示发现层候选可见，不表示执行授权。目录可短暂显示过期候选，但执行端必须依据本地撤销索引、来源水位、签名和本地策略拒绝不安全请求。

## 3. 事件流与序列设计

### 3.1 Feed 标识与序列

每个 Peer Binding 至少绑定一个来源域安全控制 Feed：

**feedKey = (sourceDomainId, streamId, peerBindingId)**

每条 Feed 事件包含：

- CloudEvents 核心字段：specversion、id、source、type、subject、time；
- 域扩展字段：domainid、streamid、peerbindingid、sourcesequence、revocationepoch；
- 完整性字段：previouseventdigest、eventdigest、signature；
- 撤销负载：目标对象类型、不可变对象 ID/版本、有效时间、原因码、级联范围和最小证据引用。

source + id 在一个事件来源内唯一；同一逻辑撤销进入不同 Peer Binding Feed 时分别形成该 Feed 的唯一事件 ID；同一 Feed 的重复投递沿用原 ID 并按同一事件处理。接收端必须将去重记录持久化，不能只依赖内存缓存。

### 3.2 接收算法

1. 验证 Peer Binding、来源 Domain、事件签名、密钥用途、Key Epoch、事件类型和 Schema。
2. 计算规范化事件摘要，校验 eventdigest、前序摘要和签名。
3. 若 (source,id) 已存在且摘要相同，幂等忽略；若同一 ID 对应不同摘要，隔离来源并触发等价性/分叉告警。
4. 若事件是有效撤销，立即将目标不可变对象引用写入本地墓碑集合；不要等待缺失的前序事件。
5. 若 sourcesequence = contiguousSequence + 1 且前序摘要匹配，则提交事件并推进连续水位；随后按顺序处理已缓冲事件。
6. 若序列大于期望值，缓冲事件、记录 Gap，向来源域请求缺失区间；连续水位不得越过缺口。
7. 若序列小于或等于已确认水位但事件 ID/摘要不匹配，视为重放、冲突或来源分叉，进入 QUARANTINED。
8. 高风险动作要求来源 Feed 无缺口且水位满足本地 Freshness Budget；否则 HOLD。

**关键细节：** 有效的后序撤销可以先行使撤销墓碑生效，但不能据此宣称前序历史完整。对存在 Gap 的来源域，高风险授权仍然 HOLD，直至缺口被补齐或由完整签名快照恢复。

### 3.3 不以时间戳排序

网络时延、时钟偏差、重试和跨域时区会造成事件时间乱序。事件顺序由来源 Feed 的单调序列和摘要链确定；time 与 effectiveAt 仅用于审计和业务生效时间，必须校验合理时钟偏差，但不能取代序列。

## 4. 撤销墓碑与版本冲突

### 4.1 只增不减的撤销集合

接收端维护：

**RevokedSet := RevokedSet ∪ {immutableObjectRef}**

两个副本合并时采用集合并集。该模式借鉴 Grow-Only Set 的单调合并性质，但仅用于不可变对象版本的撤销墓碑，不把整个能力目录设计成 G-Set，也不意味着所有目录字段都可无冲突合并。

### 4.2 撤销优先规则

对于同一个不可变对象版本，撤销状态优先于挂起、过期和 ACTIVE 广告。这是安全状态优先级，不是对所有业务状态的通用排序。

若收到同一 Owner、同一对象版本、相同版本号但不同摘要的两个有效签名声明，不采用 Last-Write-Wins；应 QUARANTINE 并由 Owner 处理冲突。

### 4.3 恢复规则

- 能力恢复：创建新的 capabilityVersion / advertisementId，重新签名并重新验证。
- Grant 恢复：签发新 Grant ID，重新验证父授权链。
- 密钥恢复：新 Key ID / Key Epoch，旧密钥墓碑永久保留。
- Peer Binding 恢复：建立新的 Binding Version 和双方接受收据。
- 成员恢复：重新入盟，不复用旧 Membership Grant。

## 5. 快照、压缩与断点恢复

### 5.1 Checkpoint 必须证明什么

来源域签名 Checkpoint 至少绑定：

- sourceDomainId、streamId、peerBindingId；
- contiguousSequence 和该位置的 lastEventDigest；
- revocationEpoch；
- snapshotSequence、snapshotRoot、snapshotDigest、条目数量；
- completeRevocationSet=true；
- issuedAt、签名主体、Key ID、Key Epoch 和签名。

Checkpoint 只证明来源域对所声明 Feed/快照的承诺，不自动证明该来源域没有向其他接收方展示不同视图。

### 5.2 快照必须包含完整可查询状态

Merkle Root 只提供完整性承诺，不包含可查询的撤销状态。快照必须包含该 Peer Binding 范围内完整的撤销墓碑集合（或受认证、可查询且有完整性证明的等价索引），并用 Root/Digest 验证内容。不能只下载一个 Root 就把本地状态视为已恢复。

### 5.3 压缩恢复流程

1. 若来源历史已压缩，接收端不得无限重试旧游标，也不得直接跳到最新序列。
2. 获取来源域签名的完整快照及 Checkpoint。
3. 验证 Trust Binding、签名、Key Epoch、快照摘要、Merkle Root、对象范围和完整性声明。
4. 将快照墓碑与本地墓碑做并集；任何本地已知墓碑不得被快照删除。
5. 验证快照与上次可信 Checkpoint 的一致性证明；若来源域不提供可验证连续性，必须进入人工/安全审查路径。
6. 从 snapshotSequence + 1 续读事件，直到 Feed 连续水位追平。
7. 完成差异对账并重新满足本地 Freshness Budget 后，才解除对应来源域的同步 HOLD。

### 5.4 Merkle 的两种用途必须区分

- **反熵差异定位：** 可借鉴 Dynamo 的 Merkle Tree 比较分区摘要，定位需要同步的键/对象范围，减少全量下载。
- **追加历史一致性：** 可借鉴 RFC 9162 的 Merkle consistency proof，验证新树是否包含旧树前缀。
- RFC 9162 是针对 Certificate Transparency 的 Experimental RFC，不是 Agent Ecology 的通用联邦目录标准；本项目只借鉴可验证追加历史的技术原语。
- 单一 Merkle Log 仍可能向不同客户端展示不同视图；需要跨接收方交换签名 Checkpoint（Gossip）或独立见证来检测分叉。Gossip 的部署方式和见证门槛仍是待验证事项。

## 6. 网络分区与风险分级

Freshness Budget 必须由目标域 Policy Owner 按风险、数据分类和业务影响配置；本协议不写死一个适用于所有生态的秒数。

| 场景 | 目录发现 | 低风险只读 | R2/R3 跨域副作用 | R4 |
|---|---|---|---|---|
| Feed 连续且新鲜 | 可用 | 按本地策略 | 重新核验后可申请本地授权 | 不允许 Agent 自动执行 |
| Feed 有 Gap | 可标注不完整 | 仅本地策略明确允许时使用 | HOLD | 不允许 |
| Checkpoint 过期 | 可显示旧缓存并标注 | 默认 HOLD；仅明确允许的低风险场景例外 | HOLD | 不允许 |
| FCP 不可用 | 可使用标记过期的本地缓存 | 按本地 Freshness Budget | HOLD，除非有独立、明确的本地授权路径且无撤销未知 | 不允许 |
| 来源签名/摘要冲突 | 隔离该来源 | HOLD | HOLD | 不允许 |
| 本地 Kill Switch 触发 | 停止该 Peer/能力路由 | DENY | DENY | 人类根治理流程 |

本地业务在不依赖跨生态数据的情况下可继续运行；跨域能力调用必须重新核验来源域状态。FCP 离线不能关闭本地 PEP、撤销墓碑或 Kill Switch。

## 7. FCP 与本地 Runtime 职责

- FCP：目录索引、事件中继、Feed 游标转发、反熵协调、健康度/延迟观测；无权改写来源签名事件、清除墓碑或批准执行。
- Source Domain Revocation Authority：签发本域撤销事件、Checkpoint 和完整快照；负责序列和密钥生命周期。
- Receiving Domain Sync Agent：验签、去重、缓冲、补洞、快照恢复、Merkle 对账；不得签发来源域事件。
- Receiving Domain Revocation Store：保存本地撤销墓碑、每个来源 Feed 的连续水位、最近 Checkpoint 和 Freshness 状态。
- PDP：根据来源状态、Purpose、Action、Resource、Audience、风险、Freshness Budget 和本地政策作出授权判断。
- PEP：副作用前执行 DENY/HOLD/ALLOW；撤销或 Kill Switch 必须可本地即时生效。

## 8. 状态机

SYNCED → EVENT_RECEIVED → VERIFIED → APPLIED → CHECKPOINTED

异常状态：

DUPLICATE / GAP / STALE / COMPACTED / QUARANTINED / FORK_SUSPECTED / HOLD / RECOVERING

恢复路径：

GAP → BACKFILL → CONTIGUOUS

COMPACTED → SIGNED_SNAPSHOT → PROOF_VERIFIED → REPLAY → RECONCILED

FORK_SUSPECTED → QUARANTINED → INDEPENDENT_REVIEW → REBIND_OR_REJECT

不能仅因网络恢复、事件队列清空或 FCP 返回成功，就自动把来源状态标记为 SYNCED。

## 9. 观测指标与实验变量

至少记录：

- 每个 (sourceDomainId, streamId) 的连续水位、最新观察序列、Gap 长度和最长 Gap 持续时间；
- 来源 Checkpoint 年龄、签名失败数、摘要冲突数、重复事件率、乱序率；
- 撤销事件从来源签发到本地墓碑生效的延迟分布；
- 从撤销生效到所有受影响 PEP 拒绝新请求的延迟分布；
- 快照恢复时间、反熵字节量、Merkle 差异定位成本；
- FCP 分区期间的本地 DENY 生效时间和误放行数（安全目标为 0）；
- 误 HOLD 率、恢复误差率、人工介入次数和对业务可用性的影响。

实验需区分“事件已送达”“墓碑已写入”“水位已追平”“PEP 已拒绝”四个不同时间点，不能用消息队列 ACK 代替撤销生效。

## 10. WP-021 验收门槛

进入受控合成实验前：

1. Revocation Event 与 Sync Checkpoint 完成 JSON Schema Draft 2020-12 Validator。
2. CloudEvents (source,id) 去重和持久幂等行为有测试向量。
3. 事件序列、前序摘要、来源签名和撤销 Epoch 的语义验证器可运行。
4. 撤销墓碑并集、旧广告覆盖、对象版本重发和父 Grant 级联撤销有证明/测试。
5. Snapshot 完整性、Merkle Root、历史连续性和压缩恢复路径有测试。
6. Gap、乱序、重复、丢失、分区、恢复和来源分叉有故障注入方案。
7. R0—R3 Freshness Budget 由目标域 Policy Owner 定义；R4 不进入 Agent 自动执行。
8. FCP 离线时本地 PEP / Kill Switch 仍能独立 DENY。
9. 安全 Owner、来源域 Owner、接收域 Owner 和独立评估者完成桌面审查。
