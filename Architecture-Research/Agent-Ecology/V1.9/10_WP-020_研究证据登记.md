# WP-020｜跨生态信任协议研究证据登记

**日期：** 2026-11-14  
**用途：** 为 WP-020 设计提供正式规范和稳定工程规范依据。  
**证据边界：** 规范存在不等于 Agent Ecology 已实现或通过互操作。

| 来源 | 类型/状态 | 可借鉴的具体机制 | 对 Agent Ecology 的适用边界 |
|---|---|---|---|
| SPIFFE Trust Domain and Bundle | SPIFFE 稳定规范 | Trust Domain 与身份命名空间绑定；Bundle 保存域级权威公钥；Bundle Sequence 可用于更新排序；不同域密钥不应无差别混池 | 仅作为工作负载身份与信任包实现候选；不等于业务授权 |
| SPIFFE Federation | SPIFFE 稳定规范 | Bundle Endpoint、端点认证、外部 Trust Domain Bundle 交换、保留 Trust Domain 与 Bundle 绑定、密钥轮换 | 双方可选择 SPIFFE；信任链需短且明确；不授予数据/业务权限 |
| OpenID Federation 1.0 Final | OpenID Foundation 最终规范 | Entity Configuration、Subordinate Statement、Trust Chain、Trust Mark、有效期与本地 Trust Anchor 校验 | 作为可选层级联邦适配器；不把某个 Anchor 变成所有 Agent Ecology 的全局根 |
| RFC 9700 / BCP 240 | IETF Best Current Practice | OAuth 2.0 安全最佳实践；Sender-Constrained Token；优先避免不安全授权模式 | 用于授权服务与令牌交换安全配置，不替代本地业务策略 |
| RFC 8693 | IETF 标准轨道 RFC | Subject Token、Actor Token、Audience、Delegation Context 与 `act` 委托链 | 可用于表达主体/代理关系；目标 Authorization Server 仍须独立决策 |
| RFC 9449 | IETF 标准轨道 RFC | DPoP Proof、`jti`、`htm`、`htu`、`iat`、服务端 nonce、重放检测 | 发送方约束，不替代资源/动作/Purpose 授权 |
| RFC 8705 | IETF 标准轨道 RFC | OAuth mTLS Client Authentication 与 Certificate-Bound Access Token | 可作为 DPoP 的另一种发送方约束方案，依部署选择 |
| RFC 8725 / BCP 225 | IETF Best Current Practice | JWT 算法验证、受信算法列表、密钥用途与算法绑定、避免 `none` | 用于 Owner Attestation / JWT 验证配置；JSON Schema 无法代替密码学验证 |
| RFC 8785 | IETF RFC Editor 发布的 Informational RFC | JSON Canonicalization Scheme，用于可重复的 JSON 摘要与签名输入 | 仅解决 JSON 表示一致性；必须统一处理 I-JSON、重复属性和 Unicode |

## 证据等级与成熟度

- SPIFFE Trust Domain/Bundle 与 Federation：稳定的工程身份规范；实际实现仍需检查产品、SDK 和控制平面兼容性。
- OpenID Federation 1.0：最终规范；可用作信任链/Trust Mark 的可选互操作配置，不代表本项目采用。
- RFC 9700、RFC 8725：IETF Best Current Practice。
- RFC 8693、RFC 9449、RFC 8705：已发布 RFC；具体部署需确认授权服务器、资源服务器、代理链和 SDK 支持。
- RFC 8785：Informational RFC；实现方仍需共享测试向量，不能仅因引用 RFC 就宣称签名互操作。

## 研究结论

1. 以 SPIFFE Trust Domain 作为可选工作负载身份底座，保留域与 Bundle 的一一绑定。
2. 以双边显式 Trust Binding 为 Agent Ecology 默认信任建立方式；OpenID Federation Trust Chain 仅作可选适配，不默认传递信任。
3. Owner 能力声明使用独立签名配置；Owner Signing Key 与 Workload Key、DPoP Proof Key 分离。
4. 委托必须可衰减，目标域本地 Authorization Server 决定是否签发本地 Audience 的短期令牌。
5. Token Exchange 可表达 Subject/Actor 关系，但不是授权决定；DPoP/mTLS 可约束令牌持有者。
6. 撤销状态按来源域维护独立单调水位；高风险状态未知或过期时 Fail Closed。
