# Agent Ecology V1.9｜P0 协议门禁与确定性 Policy Validator 设计

- 日期：2026-11-21
- 依据：33_V1.9_21份候选JSON_Schema元模型与互操作静态审查.md
- 状态：DESIGN_CANDIDATE / NOT_IMPLEMENTED / NOT_EXECUTED
- 范围：Trust Root 更新、Witness Lifecycle、Witness Key Lifecycle、Witness Quorum
- 约束：仅定义协议门禁、确定性验证规则和验收向量；不编写工程实现代码，不启用 Runner，不接入真实密钥或生产数据。

## 1. 目标与设计原则

本文件把四项 P0 静态缺口转化为可实现、可测试、可审计的规范候选。目标不是把 JSON Schema 变成万能授权引擎，而是建立分层验证：

1. JSON Schema：字段结构、类型、枚举、必填和局部条件。
2. Deterministic Policy Validator：跨字段数值关系、集合关系、状态机、版本/时间单调性。
3. Cryptographic Verifier：签名、摘要、规范化、密钥状态、Key Epoch 和防重放。
4. Owner / Independent Review：根治理授权、Witness 独立性、恢复锚保管和例外审批。
5. PEP / Execution Gate：最终执行前本地 DENY/HOLD/ALLOW；本文件不授予任何执行许可。

任何一层证据缺失、过期、冲突或无法验证，都不得由下一层自动补齐。未知状态不得降级为成功。

## 2. 统一验证结果模型

所有 P0 Validator 使用统一结果：

| 结果 | 含义 | 后续动作 |
|---|---|---|
| PASS | 结构、策略、签名和所需证据均通过 | 可进入下一道独立门禁，不自动代表业务授权 |
| FAIL | 明确违反结构、策略、数学关系或状态机 | 拒绝当前对象，记录可复现错误 |
| HOLD | 证据缺失、状态未知、过期、网络不可达或无法判断 | 暂停，不签发、不推进状态 |
| QUARANTINE | 疑似密钥失陷、状态回滚、签名冲突、分叉或身份克隆 | 隔离相关身份/对象，启动独立审查与恢复流程 |

统一输出字段建议：
- validatorId / validatorVersion / profileVersion
- objectType / objectId / objectVersion / objectDigest
- evaluatedAt / evaluationContextRef
- result / reasonCodes[]
- inputEvidenceRefs[] / missingEvidence[]
- policyDigest / trustRootVersion / keyEpoch
- replayableInputBundleRef / outputDigest

Validator 输出本身也必须可审计；不得只记录一个布尔值。

## 3. P0-A｜Trust Root Update Validator

### 3.1 输入对象与外部权威

输入：
- TrustRootUpdateEnvelope
- 当前可信 Root Version、Root Digest、Root Key Set 和 Root Policy
- 旧根签名、新根签名或 Emergency Recovery Anchor 证据
- Key Registry、Key Epoch、Custody Domain 与撤销状态
- 目标 Peer Binding 对更新的接受记录（若策略要求）

外部权威：
- Root Governance Owner 决定更新模式和阈值。
- Emergency Recovery Anchor 的真实性由事前登记的带外流程核验。
- Validator 只执行已批准规则，不自行降低阈值或替换 Root Owner。

### 3.2 NORMAL_DUAL_THRESHOLD 规则

必须同时满足：
1. updateMode = NORMAL_DUAL_THRESHOLD。
2. previousRootDigest 与当前可信 Root Digest 精确匹配。
3. rootVersion 严格大于当前版本；不得回退、复用或跳号后覆盖历史。
4. oldRootSignatures 的有效唯一签名数达到 oldThreshold。
5. newRootSignatures 的有效唯一签名数达到 newThreshold。
6. 每个签名均绑定相同 rootDigest、rootVersion、updateMode 和签名 Profile。
7. 签名 Key ID 属于对应版本允许的 Root Key Set，Key Epoch 有效且未撤销。
8. 满足 minimumDistinctCustodyDomains；同一管理主体、同一托管控制面或同一故障域不得被重复计作独立签署方。
9. issuedAt / expiresAt 合法，且评估时间处于有效窗口。
10. 新根密钥集合不存在重复 Key ID、重复 Fingerprint 或用途越权。

### 3.3 EMERGENCY_OUT_OF_BAND_RECOVERY 规则

必须同时满足：
1. updateMode = EMERGENCY_OUT_OF_BAND_RECOVERY。
2. recoveryAnchorRefs 至少包含策略要求数量的有效带外锚证据。
3. Recovery Anchor 在事故发生前已登记，且其保管、分发和核验渠道不依赖被判定失陷的旧根。
4. 恢复审批达到事前定义的独立人类/治理门槛；不能由单一受影响域自行批准。
5. newRootSignatures 达到新根阈值；每个签名绑定同一新 Root Digest 和 Recovery Case ID。
6. 对失陷旧根签名不计入恢复授权阈值；可保留为取证材料，但不得作为信任依据。
7. 恢复过程生成独立 Incident Record、证据包、受影响 Peer 清单、撤销传播计划和回滚/隔离策略。
8. 更新后强制重新验证 Peer Binding、Witness Registry、Quorum Policy 和相关 Key Epoch。

### 3.4 必须拒绝/隔离的情形

- NORMAL 模式旧根或新根签名不足。
- EMERGENCY 模式缺少带外恢复锚或独立审批。
- Root Version 不单调、previousRootDigest 不匹配。
- 签名 Key 已撤销、用途错误、Epoch 回退或签名时间无法确定。
- 关键 Custody Domain 不能证明独立性。
- 同一签名被重放到不同 Root Digest、更新模式或事故上下文。
- 无法确定旧根是否失陷、恢复锚是否独立时，结果为 HOLD/QUARANTINE，不允许猜测。

## 4. P0-B｜Witness Lifecycle Event Validator

### 4.1 必需签发与完整性字段

WitnessLifecycleEvent 至少要求：
- witnessId、membershipEpoch、eventSequence、eventType
- previousEventDigest、eventDigest
- operatorDomainId、administrativeDomainId、keyCustodyDomainId、backupFailureDomainId、deploymentDomainId
- effectiveAt、issuedAt、issuedBy
- issuerKeyId、issuerKeyEpoch
- signatureProfile、signatureValue
- policyRef、evidenceRefs

签名必须覆盖规范化事件主体，且签名覆盖范围不得包含签名自身。字段缺失、签名无效、签发者不具备相应权威或密钥状态未知时不得推进事件链。

### 4.2 候选状态迁移表

| 当前状态 | 事件 | 目标状态 | 附加条件 |
|---|---|---|---|
| NONE | PROPOSED | PROPOSED | 新 Witness ID 与初始登记证据 |
| PROPOSED | IDENTITY_VERIFIED | IDENTITY_VERIFIED | 独立身份核验与运营主体证明 |
| IDENTITY_VERIFIED | OBSERVE_ONLY | OBSERVE_ONLY | 密钥、故障域和观察策略登记 |
| OBSERVE_ONLY | ACTIVATED | ACTIVE | 观察期通过、独立性评审、Quorum Policy 接受 |
| ACTIVE | SUSPENDED | SUSPENDED | 暂停理由、影响范围和生效时间 |
| ACTIVE | QUARANTINED | QUARANTINED | 回滚、双签、密钥失陷或分叉等风险证据 |
| SUSPENDED | REINSTATED | OBSERVE_ONLY | 修复证据、独立复核；不得直接恢复 ACTIVE |
| QUARANTINED | REINSTATED | OBSERVE_ONLY | 事故关闭、状态连续性证明和独立批准 |
| ACTIVE / SUSPENDED | RETIRING | RETIRING | 退出计划、在途任务和替代成员 |
| RETIRING | RETIRED | RETIRED | 旧密钥撤销、历史证据归档、成员移除完成 |
| RETIRED | REJOINED | PROPOSED | 必须提升 membershipEpoch，重新身份核验，不复用旧激活状态 |

此表是候选规则，最终状态机必须经 Witness Owner、Security Owner 和独立验证者批准。

### 4.3 单调性规则

- eventSequence 在同一 Witness + membershipEpoch 内严格递增。
- previousEventDigest 必须匹配已接受的前一事件。
- membershipEpoch 只能在重新加入/重新建立成员身份时递增，不得回退。
- RETIRED 不得直接恢复 ACTIVE；重新加入必须重新经过身份核验与 OBSERVE_ONLY。
- 已撤销或失陷密钥不得签署新的生命周期事件。
- 事件乱序、重复、Gap 或历史分叉必须 HOLD/QUARANTINE。

## 5. P0-C｜Witness Key Lifecycle Validator

### 5.1 必需字段

Key Lifecycle Record 至少要求：
- witnessId、keyId、keyFingerprint、algorithm、keyEpoch、keyPurpose、keyStatus
- custodyDomainId、publicKeyRef、validFrom
- lifecycleSequence、previousEventDigest、eventDigest
- signer identity、signer key reference、signatureProfile、signatureValue

签名必须覆盖 Key ID、Fingerprint、Purpose、Epoch、状态转换和关键时间字段。

### 5.2 候选状态迁移表

| 当前状态 | 允许事件/目标状态 | 限制 |
|---|---|---|
| GENERATED | REGISTERED | 公钥指纹、算法、用途和托管域登记 |
| REGISTERED | PREPARED | Root/Policy/Owner 接受已完成 |
| PREPARED | ACTIVE | 生效时间到达且无撤销/冲突 |
| ACTIVE | DEPRECATED | 有替代 Key Epoch 和迁移窗口 |
| ACTIVE | SUSPECTED_COMPROMISE | 必须记录 detectedAt 与 suspectedCompromiseSince |
| SUSPECTED_COMPROMISE | QUARANTINED | 立即停止新签名并隔离身份 |
| QUARANTINED | REVOKED | 由授权 Key Owner/治理流程确认 |
| ACTIVE / DEPRECATED | REVOKED | 立即停止新签名，保留历史验证材料 |
| REVOKED / RETIRED | DESTROYED | 必须有销毁回执和独立核验 |

禁止：
- REVOKED → ACTIVE
- DESTROYED → 任意可用状态
- 旧 Key Epoch 覆盖新 Epoch
- 同一 Key Fingerprint 在不同用途或身份中被静默复用

### 5.3 时间与证据约束

- ACTIVE 必须有 validFrom，若策略要求有限期则 validUntil 必填。
- SUSPECTED_COMPROMISE 必须有 detectedAt 与 suspectedCompromiseSince。
- REVOKED 必须有 revokedAt、reasonCode 和撤销事件引用。
- RETIRED 必须有 retiredAt 与替代 Key 关系。
- DESTROYED 必须有 destroyedAt 和销毁证明；当前 Schema 尚缺专用字段，需补充。
- 任何状态时间不得晚于签名/事件的可信时间而造成因果倒置；异常时 HOLD。

## 6. P0-D｜Witness Quorum Policy Validator

### 6.1 规范化集合

定义：
- W：去重后、身份有效、密钥有效、独立性核验通过的 Witness 集合。
- n：|W|，即有效 Witness 数量。
- f：策略声明的最大拜占庭故障数。
- q：requiredCosignatures。
- I：任意两个合法 Quorum 的最小交集数。

必须满足：
1. totalWitnesses = n。
2. 0 ≤ f < n。
3. 1 ≤ q ≤ n。
4. I = 2q - n。
5. I > f。
6. 即 2q-n>f。
7. 每个 Quorum 的签名者必须来自 W，且签名 Key Epoch/状态有效。
8. 实际独立运营域数与故障域数满足策略最小值。
9. 每个 Witness 的公钥、Key ID、Fingerprint 和身份绑定唯一；同一控制主体不得通过多个 ID 重复计数。

### 6.2 集合与身份验证

- Witness ID、Key ID、Public Key Fingerprint 必须唯一。
- totalWitnesses 必须等于过滤失效/撤销/隔离/不合格 Witness 后的有效集合数。
- operatorDomainId、failureDomainId、keyCustodyDomainId、administrativeDomainId、deploymentDomainId 应分别核验；不能只比较字符串不同就断言真实独立。
- maxWitnessesPerOperator 必须对实际成员集合计算。
- minDistinctOperators 和 minDistinctFailureDomains 必须基于独立证据核验后的集合计算。
- Witness Group 的成员必须是 W 的子集；minimumSignatures 不得大于该组有效成员数。
- policyApprovals 必须绑定同一 agreementDigest，并满足不同授权域与密钥的批准要求。

### 6.3 参考数值向量

| n | f | q | 2q-n | 预期 |
|---:|---:|---:|---:|---|
| 4 | 1 | 3 | 2 | PASS，2>1 |
| 4 | 1 | 2 | 0 | FAIL，0 不大于 1 |
| 7 | 2 | 5 | 3 | PASS，3>2 |
| 7 | 2 | 4 | 1 | FAIL，1 不大于 2 |
| 10 | 3 | 7 | 4 | PASS，4>3 |
| 10 | 3 | 6 | 2 | FAIL，2 不大于 3 |
| 13 | 4 | 9 | 5 | PASS，5>4 |
| 13 | 4 | 8 | 3 | FAIL，3 不大于 4 |

以上只验证固定成员集合下的交集不等式，不证明运营主体真实独立、不证明 Witness 诚实，也不构成完整 BFT 共识证明。

## 8. 验收证据与准入门禁

每条向量必须归档：
- 输入对象及其 SHA-256
- Validator 版本、配置、规则 Profile 和依赖版本
- 执行环境、时间、随机种子（若有）
- 预期结果与实际结果
- 完整结构化日志、reasonCodes 和证据引用
- 独立复核者、复核时间和签署记录
- 回归运行结果及变更影响分析

阶段门禁：
1. Schema 结构与元 Schema 验证通过。
2. P0 Policy Validator 设计经 Owner/Security Review。
3. 正向/负向向量全部按预期执行。
4. 密码学验证与跨语言互操作通过。
5. 独立审查证据完整。
6. 才可申请 F0/F1 Gate Review；仍不自动授权生产实施。
