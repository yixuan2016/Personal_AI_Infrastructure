# Agent Ecology V1.3
## 群体智能、自组织协作与 ADS 生态融合研究

**版本：V1.3 研究设计版｜日期：2026年11月10日｜语言：简体中文**

> 本卷承接 V1.2《协议契约与协作机制冻结设计》，从协议定义进入群体行为、运行时机制、跨域治理与对照实验设计。V1.3 当前形成的是候选参考架构和实验方案，尚未声称已完成多 Runtime 实测或性能验证。

## 摘要

Agent Ecology 的关键不是取消 Agent 间通信，而是改变协作的默认载体：从大量临时点对点消息，转向共享环境中持久、可查询、可订阅、可验证的状态、痕迹和成果。Agent 观察环境变化，依据能力、权限、预算和依赖条件决定是否行动；执行后再将新的成果、证据、风险或状态变化写回环境，形成持续演化的协作循环。

本报告将 Agent Environment 定义为五个逻辑平面：State、Trace、Artifact、Semantic、Governance。它不是一个共享聊天记录，也不是一个不加区分的共享数据库。不同平面具有不同一致性要求和访问边界：任务认领、租约、授权和执行权需要强约束；发现索引和非关键投影可采用最终一致；痕迹与审计记录应保留不可变历史；敏感数据通过本地执行点和最小化投影控制跨域访问。

研究比较集中式编排、消息/事件驱动和环境痕迹驱动三种范式，提出以环境驱动为主、事件通知为辅、A2A 必要交互、ADS 跨域治理的混合 Agent Ecology。该架构允许 Agent 在局部授权范围内自组织，同时保留人类对高风险动作、关键授权、生态级策略变更和最终问责的控制权。

## 执行摘要：本版核心判断

1. **环境是协作主上下文，不是无边界共享数据库。** 状态、痕迹、成果、语义和治理必须分层。
2. **Stigmergy 不是“无通信”。** 它把大部分异步协调转移到环境；即时谈判、澄清、强同步事务仍需要直接交互。
3. **数字信息素只用于发现排序，不是事实真伪或权限依据。** 必须有来源独立性、反证、衰减、隔离和恢复。
4. **任务竞争必须有原子执行权。** CAS、租约、递增 Fencing Token、幂等和审计缺一不可。
5. **A2A 与 Agent Environment 互补。** A2A 提供 Agent 互操作；环境提供持久协作上下文；CloudEvents 提供事件信封；MCP 负责工具接入；ADS 负责生态治理。
6. **ADS 不是超级调度器。** ADS 负责跨域能力、共同语义、授权、预算、审计与生态进化；领域主体保留数据所有权、专业执行和专业验收。
7. **群体学习不能以多数意见代替证据。** 个体、领域、生态三个尺度的进化必须分开评估和发布。
8. **V1.3 结论必须经实验验证。** 本卷给出五组对照条件、八类场景和指标体系，不虚构实验结果。

# 37. 研究命题、证据层级与边界

## 37.1 核心研究命题

**Agent Ecology 的协作主线由共同环境中的可观察状态变化驱动，直接通信作为补充通道。**

Agent 不必预先知道其他 Agent 的具体身份、在线时间或执行位置，只需要观察自己有权访问的环境投影，就能判断是否存在值得执行的任务、是否已有前置成果、是否出现阻塞或风险、是否需要补位。

这并不意味着环境本身能自动产生智能。环境提供的是共享状态与协作刺激；目标理解、能力判断、局部规划、执行和验证仍由 Agent 与治理规则共同完成。

## 37.2 证据层级

| 证据类型 | 可支持的结论 | 不可直接推出的结论 |
|---|---|---|
| 生物群体与群体机器人 Stigmergy | 环境修改可以成为间接协调机制；局部规则可能形成群体模式 | LLM Agent 一定更高效或更智能 |
| 软件 Agent 协调模型 | 黑板式、Linda-like、直接通信等是可比较的协调模型 | 任意共享数据库都能产生自组织 |
| LLM 多 Agent 基准 | 协作与竞争需要构件级指标；拓扑效果依任务而变 | 某一种拓扑在所有任务最优 |
| A2A、CloudEvents 等协议 | 可标准化 Agent 交互和事件信封 | 协议自身提供生态级冲突治理、资源公平或事实验证 |

## 37.3 关键研究资料与局限

- Boldini、Civitella 与 Porfiri（2024）提出从数学建模到控制的 Stigmergy 研究框架，讨论群体成员通过动态环境修改进行间接通信。它为数字痕迹场建模提供理论启发，但不是 LLM Agent 的直接实证。
- Ribeiro 等（2026）系统综述分析 338 项群体机器人研究，讨论鲁棒性、可扩展性、适应性与混合方法趋势；作者同时说明未进行正式偏倚风险评估或元分析。
- Cabri 等（2026）梳理软件 Agent 协调模型与语言，为直接通信、黑板式和其他协调模型提供分类参考，但不是现代 LLM Agent 的运行时性能对照。
- MultiAgentBench（ACL 2025）以里程碑指标评价协作与竞争，并比较 star、chain、tree、graph 等拓扑。其结果依赖具体模型和任务设置。
- CoCoBench（2026 预印本）提供 897 个 oracle-validated 实例，分别评价任务分配、顺序约束、互斥和交接，说明总体成功率可能掩盖局部协调缺陷。
- A2A 规范定义 Agent Card、Task、Message、Artifact、状态生命周期以及认证/授权交互；CloudEvents 规范定义事件信封及 source+id 唯一性。两者分别解决协议互操作和事件格式，不等于完整生态运行时。

**证据结论：** “环境痕迹能减少显式消息、降低总成本并改善扩展性”是 V1.3 的待验证假设，不作为已证实结论。

# 38. 三种协作范式与混合架构选择

## 38.1 集中式 Orchestration

中央规划器负责目标拆解、任务分配、依赖控制、异常处理和结果验收。

**优势：** 全局计划明确；强顺序任务更易控制；审批与审计集中；实现与调试相对直接。

**局限：** 中央规划器可能形成吞吐瓶颈和故障域；Agent 对全局上下文的获取依赖中央汇总；开放式任务发现与局部机会响应可能受到调度延迟影响。

**适用：** 固定流程、强事务、低动态性、责任链明确的任务。

## 38.2 消息/事件驱动 Choreography

Agent 通过直接消息或发布订阅事件协作。事件触发消费者行动，消息用于澄清、谈判、委托或反馈。

**优势：** 时间解耦；适合异步事件响应；容易与现有消息基础设施集成。

**局限：** 事件路由不自动解决任务归属、资源竞争和依赖冲突；事件链路可能分散在多个服务；重复投递、事件风暴和循环触发必须治理。

**适用：** 事件触发、异步流程、系统间状态通知。

## 38.3 环境痕迹驱动 Stigmergy

Agent 观察共享环境，读取任务、状态和成果痕迹；按局部策略决定行动；再将结果写回环境，刺激其他 Agent 后续行动。

**优势：** 时间解耦；Agent 无需彼此持续在线；成果可复用；支持动态加入、退出和故障接续；协作过程可沉淀为因果链。

**局限：** 环境状态可能陈旧、冲突或污染；任务可能重复认领或无人认领；错误痕迹可能被正反馈放大；需要更严谨的状态机、来源验证、衰减和资源仲裁。

**适用：** 开放式、可分解、异步、可观察、可接续的任务。

## 38.4 范式对比

| 维度 | 集中式编排 | 消息/事件驱动 | 环境痕迹驱动 |
|---|---|---|---|
| 主要协调媒介 | 中央计划器 | 消息/事件链路 | 共享环境状态和痕迹 |
| 全局状态 | 中央维护 | 分散于事件消费者 | 环境提供统一查询投影 |
| 时间耦合 | 相对较高 | 较低 | 较低 |
| 任务发现 | 中央分配 | 订阅/路由 | Agent 观察环境并匹配 |
| 竞争治理 | 中央仲裁 | 需额外实现 | 环境原子认领与策略仲裁 |
| 主要风险 | 中央瓶颈 | 事件链复杂 | 陈旧痕迹、冲突、反馈失控 |
| 典型适用 | 确定流程 | 异步事件 | 开放协作与动态接力 |

![三种协作范式](assets/18_coordination_paradigms_8k.png)

## 38.5 推荐的混合 Agent Ecology

不建议把三种范式视为互斥路线。推荐的分工是：

- **环境驱动：** 任务发现、持久上下文、状态演化、成果共享、依赖表达。
- **事件驱动：** 状态变化通知、订阅分发、唤醒和异步触发。
- **A2A 直接交互：** 必要的澄清、能力握手、协商和跨 Runtime 委托。
- **集中治理：** 身份、策略、跨域授权、资源预算、风险升级和审计。
- **领域自治：** 专业规则、领域数据、局部执行策略和专业验收。

# 39. Agent Environment：五平面数字协作环境

## 39.1 环境不是共享聊天记录

Agent Environment 是受治理的协作运行空间，由五个逻辑平面组成：

| 平面 | 核心内容 | 权威数据 | 一致性要求 |
|---|---|---|---|
| State Plane | 当前任务状态、租约、依赖、预算和资源占用 | 任务/资源权威存储 | 认领、租约和权限变更需要强约束 |
| Trace Plane | 观察、意图、进度、决策、风险、反证和审计痕迹 | 追加式痕迹账本 | 保留历史、可验证来源和因果关系 |
| Artifact Plane | 文件、报告、数据集、模型和中间成果 | 版本化对象存储 | 内容寻址、版本不可混淆 |
| Semantic Plane | Ontology、能力契约、术语映射和领域语义 | 版本化语义注册库 | 版本兼容和显式迁移 |
| Governance Plane | 身份、策略、授权、审批、撤权和审计 | 策略权威与本地 PEP | 默认拒绝、可撤销、可审计 |

五个平面可以逻辑统一、物理分布。共享环境不要求所有数据集中在一个数据库，也不意味着所有 Agent 可以看到全部数据。

![Agent Environment 五平面架构](assets/19_environment_five_planes_8k.png)

## 39.2 权威状态与派生投影必须分离

- 任务权威状态由 State Plane 的状态机管理。
- Trace Plane 记录状态变化的原因、主体、证据和因果关系，不允许 Agent 直接覆盖历史。
- 搜索索引、推荐排序、仪表盘和订阅视图属于派生投影，可以最终一致。
- Artifact 内容以版本和内容哈希定位，不能仅凭文件名判断是否为同一版本。
- 权限决策由 Governance Plane 产生，但必须由资源所在域的 PEP 在访问发生时执行。

如果把“消息成功投递”当作“业务状态已经提交”，就会产生消息与状态不一致。应使用事务性 Outbox、幂等消费者和状态版本校验，避免丢失或重复触发。

## 39.3 一致性分层

建议采用三类一致性：

1. **强约束操作：** 任务唯一认领、租约续期、Fencing Token 递增、权限撤销、资源预留和不可逆动作审批。
2. **最终一致投影：** 搜索索引、Agent 订阅列表、热度排序、推荐和跨域非敏感摘要。
3. **追加式审计：** Trace 和审计事件只追加、不静默覆盖；更正通过新事件、撤销引用或反证完成。

不要为了“所有东西实时一致”而把整个环境设计成昂贵的全局强一致系统。

## 39.4 最小 Trace 数据契约

每条协作痕迹至少包含：

- `trace_id`：全局唯一标识；
- `trace_type`：observation、intent、claim、progress、artifact、risk、verification、counter_evidence 等类型；
- `subject`：产生痕迹的 Agent/用户/系统身份；
- `occurred_at` 与 `recorded_at`：事件发生时间和写入时间；
- `target_ref`：任务、资源、成果或语义实体引用；
- `causation_ref` / `correlation_ref`：因果和关联链；
- `source_refs`：原始证据或数据来源；
- `schema_version`：契约版本；
- `classification` / `visibility`：数据分类和可见范围；
- `valid_until`：有效期；
- `verification_status`：unverified、corroborated、verified、disputed、rejected；
- `content_hash`：内容完整性校验；
- `revokes_or_supersedes`：撤销或替代关系。

Trace 不是“Agent 的自然语言随笔”。自然语言可以作为载荷，但驱动状态转换的字段必须结构化、可校验。

# 40. 数字信息素：强化、衰减、反证与抗操纵

## 40.1 不把信息素等同于点赞数

自然界的痕迹可能通过沉积、挥发和环境变化影响后续行动。数字环境可以借鉴这种机制，但不能把痕迹价值简化为一个持续累加的热度分数。

建议将发现排序拆成多维信号：

`S = {relevance, freshness, evidence_strength, source_independence, contradiction, duplication, risk}`

检索层可将其映射为排序分值，例如：

`P(x,t) = αR + βF + γE + δI − εC − ζD − ηK`

其中各权重必须按领域和实验结果配置。衰减可以采用：

`P_decay(x,t) = P(x,t0) × exp(−λ × Δt)`

但这类分值只用于发现与排序，不能直接用于判断事实真伪、授权或执行高风险动作。

## 40.2 正反馈与负反馈

- **强化：** 独立验证通过、与任务相关、来源可靠的痕迹提高可发现性。
- **衰减：** 时效性降低的内容逐步退出默认排序。
- **抑制：** 重复、冲突、低质量和来源异常的痕迹降低优先级。
- **隔离：** 可疑或被反证的痕迹进入 quarantine，不再触发正常自动化。
- **恢复：** 经复核后重新开放，但保留隔离、反证和恢复历史。

![数字信息素反馈机制](assets/20_stigmergy_feedback_8k.png)

## 40.3 防止群体回音室和虚假多数

如果 Agent 只按引用数、点赞数或其他 Agent 的赞同次数判断信息，早期偏差就可能被放大成群体共识。

建议：
1. 多个 Agent 引用同一原始来源，只计为一个来源簇，而不是多份独立证据。
2. 关键事实要求不同来源或不同验证方法交叉验证。
3. 生产成果的 Agent 不得担任唯一验证者。
4. 为探索性任务保留一定比例的非热门候选预算。
5. 记录被放弃的替代假设，避免系统只保留“胜出路径”。
6. 对来源异常、账号协同、重复模板和异常速率进行 Sybil/串谋检测。
7. 可信度分数不等于授权等级，任何高风险动作必须单独经过策略决策。

## 40.4 数字痕迹的安全属性

痕迹至少要具备：来源可识别、内容可校验、权限可判断、时效可管理、因果可追踪、反证可附加、撤销可传播。对于敏感数据，Trace 只存必要元数据和受控引用，不将密钥、访问令牌或原始隐私内容写入公共痕迹。

# 41. 自组织任务生命周期、竞争仲裁与可靠性

## 41.1 任务状态机

推荐状态：

`DRAFT → READY → DISCOVERABLE → CLAIMED → RUNNING → SUBMITTED → VERIFYING → ACCEPTED`

异常状态包括 `BLOCKED`、`EXPIRED`、`REJECTED`、`CANCELED` 和 `QUARANTINED`。状态转换必须由有权主体、合法前置条件和状态版本控制。

![自组织任务生命周期](assets/21_task_lifecycle_8k.png)

## 41.2 Agent 自主发现流程

1. Agent 订阅自己有权访问的任务类型或环境变化。
2. 读取任务契约、输入、依赖、验收标准和数据分类。
3. 匹配自身能力、版本、资源、预算和风险边界。
4. 查询授权决策；缺少授权时不得先执行再补审批。
5. 计算局部参与效用，决定忽略、认领、请求澄清或升级。
6. 通过环境原子命令认领任务。
7. 获得租约和递增 Fencing Token 后才可写入受保护资源。
8. 执行并发布进度、成果、证据和风险痕迹。
9. 独立验证者检查成果；通过后更新权威任务状态。
10. 任务结果和运行指标进入审计与复盘。

## 41.3 三种认领模式

| 模式 | 机制 | 适用情况 | 关键风险 |
|---|---|---|---|
| 开放认领 | 多 Agent 可并行认领独立子任务 | 低成本、可并行、重复代价低 | 重复劳动 |
| 原子认领 | Compare-and-Swap + Lease + Fencing Token | 需要唯一执行者或独占资源 | 租约失效、旧执行者继续写入 |
| 竞价认领 | 窗口期收集能力、成本、ETA、风险，再按策略选择 | 稀缺资源或高成本任务 | 竞价操纵、低价劣质执行 |

竞价应使用可验证的能力证明、历史验收质量和明确预算，不应仅依赖 Agent 自报“我最擅长”。

## 41.4 租约与 Fencing Token

租约解决“执行权是否仍有效”；Fencing Token 解决“旧执行者在租约过期后仍尝试写入”的问题。

推荐规则：
- 每次成功认领或重新分配时，执行权版本单调递增；
- 写入受保护资源时必须提交当前 Token；
- 资源服务拒绝小于最新 Token 的写入；
- 心跳丢失或租约过期后，旧 Agent 即使恢复网络也不能继续提交；
- 任务重试必须有幂等键，避免重复外部副作用。

只依赖 Redis 锁或超时并不足够；如果下游资源不校验 Fencing Token，旧执行者仍可能造成重复写入。

## 41.5 依赖、死锁与公平性

- 任务依赖表达为 DAG，发布时检测环路。
- 资源按统一顺序申请，避免循环等待。
- 长时间等待的任务采用 aging 提升优先级。
- 对 Agent 和领域设置并发上限与配额。
- 高优先级抢占必须有明确政策、审计和恢复规则。
- 对持续失败任务设置退避、冷却和人工升级。
- 对无人认领任务逐级提升可见性，而不是无限广播。

# 42. A2A、CloudEvents、MCP 与 Agent Environment 的关系

## 42.1 分层互补，不是互相替代

| 机制 | 核心职责 | 在 Agent Ecology 中的定位 |
|---|---|---|
| Agent Environment | 状态、痕迹、成果、语义、治理投影 | 共同上下文与持久协作空间 |
| A2A | Agent 发现、身份交互、消息、任务、成果传递 | 必要的跨 Runtime 直接交互 |
| CloudEvents | 事件信封、source、id、type、time 等 | Trace/Event 的传输封装候选 |
| MCP | Agent 与工具、数据源连接 | Tool Plane 的接入协议 |
| ADS | 跨域治理、能力注册、语义协调、授权和审计 | 生态协调与治理控制面 |

![协议与环境分层](assets/22_protocol_stack_8k.png)

## 42.2 A2A 应承担什么

A2A 的 Agent Card 可声明身份、能力、技能、接口和认证要求；Task、Message、Artifact 及状态生命周期可用于跨 Runtime 交互。规范也包含认证、授权和任务内授权请求机制。

但 A2A 本身并不自动提供：
- 生态级共享状态的权威模型；
- 多 Agent 原子任务认领和资源公平；
- 跨域 Ontology 的共同语义治理；
- 痕迹衰减、反证、来源独立性和可信度模型；
- ADS 的人类审批、跨域撤权和生态进化流程。

因此，A2A 应作为必要的 Agent-to-Agent 交互协议，而环境负责持久上下文与任务协作状态。

## 42.3 CloudEvents 应承担什么

CloudEvents 定义事件信封。规范要求 `source + id` 对每个独立事件唯一，消费者可据此识别重复投递。V1.3 建议：
- V1.2 Trace Envelope 提供 CloudEvents 兼容映射；
- 扩展字段使用受控命名空间；
- 信封保持轻量；
- 敏感业务内容使用受控 Artifact 引用；
- 不把 CloudEvents 当作业务状态机或授权系统。

# 43. ADS：生态协调、共同语义与双闭环治理

## 43.1 ADS 的定位

ADS 不应成为接收所有任务、分配所有 Agent、等待所有结果的超级调度器。它应是生态级共同能力与治理中枢，同时保留 ADS 自身的执行、管理和考核能力。

## 43.2 六项生态职责

1. **跨域能力发现：** 注册和发现能力，记录负责人、版本、输入输出、适用范围、风险和验证证据。
2. **共同语义治理：** 管理核心 Ontology、领域映射、契约版本和语义冲突。
3. **跨域授权协调：** 组织 PDP 决策，由数据所在域的本地 PEP 实际执行。
4. **生态资源协调：** 维护全局配额、跨域预算和公平策略，不替代本地资源管理。
5. **风险与审计：** 统一风险分级、审批升级、独立验证和审计关联。
6. **生态评估与进化：** 在授权范围内提炼通用契约、错误分类、语义映射和协作策略候选。

## 43.3 ADS 不应越权接管

- 领域数据所有权与个人私有记忆；
- 领域专业规则；
- 专业 Agent 的局部执行策略；
- 领域成果的最终专业验收；
- 用户未授权的个人数据；
- 个人助理和领域生态的独立成长闭环。

## 43.4 三层治理边界

| 层级 | 主要职责 | 权限 |
|---|---|---|
| Agent/领域内环 | 任务发现、局部计划、执行、自检、成果提交 | 授权范围内自治 |
| ADS 生态协调层 | 跨域发现、共同语义、资源预算、授权协调、审计 | 跨域协调与治理 |
| 人类外环 | 重大授权、高风险审批、独立验证、否决、接管、问责 | 最终治理权 |

![ADS 生态协调与双闭环治理](assets/23_ads_dual_loop_8k.png)

## 43.5 动态授权的推荐流程

1. Agent 提交具体资源、目的、动作、字段、期限和风险级别。
2. ADS PDP 根据主体、能力、上下文、用户授权和领域策略作出决策。
3. 数据所在域的 PEP 在请求发生时重新校验，不把早先批准视为永久通行证。
4. 跨域访问采用字段级、用途限定、短时有效的投影。
5. 撤权事件传播至订阅、缓存和短期凭证；本地 PEP 对新访问立即拒绝。
6. 对已开始的任务，按风险策略中止、完成安全收尾或请求人工接管。
7. 全流程写入审计痕迹。

**原则：ADS 可以协调授权，但不能替代数据所在域的本地执行控制。**

## 43.6 群体 RSI 的三尺度进化

- **个体尺度：** Agent 改进自身执行策略、工具使用和任务模板。
- **领域尺度：** 领域生态改进专业流程、领域规则和验证方法。
- **生态尺度：** ADS 改进跨域契约、通用语义、风险模板和协作策略。

三个尺度必须具有独立责任主体、版本边界和回滚机制。生态层升级不能自动覆盖领域端。

推荐进化链：

`Candidate → Evidence → Independent Evaluation → Shadow → Approval → Canary → Release → Monitor → Rollback`

候选策略不能自我评估、自我批准和自我发布；权限提升、主动联系、高风险外部副作用和个人数据访问不得由 RSI 自主扩大。

# 44. 最小参考架构：一个环境、三个 Agent、一个 ADS

## 44.1 角色

| 角色 | 职责 | 权限边界 |
|---|---|---|
| Explorer Agent | 发现资料、提出观察和候选证据 | 不能自行宣布高风险结论已验证 |
| Synthesizer Agent | 读取授权证据、形成综合成果 | 不能修改源证据或批准自身成果 |
| Verifier Agent | 独立核查来源、推理和验收标准 | 与生产者分离 |
| ADS | 管理能力、语义、策略、跨域协调和审计 | 不替代领域专业验收 |
| Human Governor | 处理关键风险、授权和发布决策 | 保留否决、接管和问责权 |

## 44.2 端到端示例：技术研究任务

1. 人类提出“研究某技术路线并形成架构建议”。
2. ADS 创建任务契约，设定目的、风险、预算和验收标准。
3. Explorer 观察 READY 痕迹，判断能力匹配后认领。
4. Explorer 将原始来源、摘要、证据引用和未验证假设写入环境。
5. Synthesizer 发现证据痕迹，检查依赖后认领综合任务。
6. Synthesizer 形成架构方案，发布 Artifact 和决策依据。
7. Verifier 观察待验证痕迹，独立复核证据和推理。
8. 如存在冲突，Verifier 发布反证与风险痕迹，触发修订；不覆盖原始证据。
9. 验证通过后，环境更新成果状态。
10. ADS 汇总审计和跨域影响；需要时升级人类审批。
11. 人类确认后，成果进入正式决策库。
12. 运行指标进入 RSI 候选评估，但不自动发布改进。

![最小参考架构全景](assets/24_minimal_reference_architecture_8k.png)

## 44.3 为什么试点仍然保留 ADS

试点的目标不是“完全没有中央控制”，而是验证哪些工作可以由环境驱动自治完成，同时保留身份、授权、预算和审计控制面。若把治理能力也一起去掉，就无法区分“自组织”与“无治理”。

# 45. 对照实验：如何证明环境驱动协作有效

## 45.1 研究问题

- RQ1：环境驱动是否减少显式点对点消息和上下文重复？
- RQ2：Agent 数量增加时，成功率、成本和延迟如何变化？
- RQ3：认领、依赖、互斥和交接的主要失败模式是什么？
- RQ4：痕迹衰减、反证和来源验证能否抑制错误扩散？
- RQ5：ADS 治理能否在不重新集中所有执行的前提下保持安全？
- RQ6：混合模式在跨域和混合风险任务中是否优于纯环境模式？

## 45.2 五组实验条件

| 编号 | 条件 | 说明 |
|---|---|---|
| EXP-01 | 集中式编排 | 中央 Agent 分解和分配任务 |
| EXP-02 | 直接消息 | Agent 通过 A2A/消息协商 |
| EXP-03 | 事件驱动 | 事件总线与订阅规则触发工作 |
| EXP-04 | 纯环境痕迹 | 共享环境发现、认领、成果和风险 |
| EXP-05 | 混合 Agent Ecology | 环境驱动为主，A2A 补充，ADS 治理 |

## 45.3 八类测试场景

1. 并行研究与交叉验证；
2. 共享资源竞争；
3. 顺序依赖与条件触发；
4. Agent 失效与环境接续；
5. 跨域数据最小投影；
6. 错误痕迹与群体误导；
7. 突发任务与优先级冲突；
8. RSI 候选策略灰度进化。

## 45.4 指标体系

| 指标 | 计算/观察方法 | 解释 |
|---|---|---|
| 任务成功率 | 达到验收标准的任务数/总任务数 | 基础效果 |
| 成果质量 | 盲评与独立评分 | 防止只看完成状态 |
| 端到端时延 | 发布至验收的 P50/P95/P99 | 真实协作效率 |
| 通信成本 | 显式消息数、Token 和网络开销 | 消息负担 |
| 重复工作率 | 重复执行的有效工作量/总工作量 | 浪费程度 |
| 交接失败率 | 未正确接续的交接/总交接 | 协作可靠性 |
| 认领冲突率 | 双重有效认领次数/总认领次数 | 竞争治理 |
| Jain 公平指数 | 按 Agent 或 Domain 资源分配计算 | 资源公平 |
| 故障恢复时间 | 故障注入至恢复可用 | 韧性 |
| 安全违规次数 | 未授权动作和敏感字段泄漏 | 安全硬指标 |
| 证据覆盖率 | 有可追溯证据的关键结论/关键结论总数 | 可信度 |
| 痕迹振荡率 | 状态反复变化、重复触发和循环数 | 稳定性 |
| 单成果总成本 | Token、工具、计算和人工复核成本 | 经济性 |

Jain 公平指数可用 `J(x) = (Σxi)² / (n × Σxi²)` 衡量资源分配的均衡程度；它只衡量分配公平，不代表任务优先级一定合理。

## 45.5 试验规模和控制变量

建议 Agent 数量取 3、5、10、20；每个条件/场景先进行 30 次重复，作为试点规模。正式统计结论前必须根据先导方差进行功效分析，预注册主要指标和非劣效界值。

控制模型版本、提示词、工具、权限、输入难度、推理预算、温度、检索快照、运行硬件和网络条件。同一任务实例在不同条件下配对运行，并随机化执行顺序。

报告效应量和置信区间；多重比较采用校正方法；报告失败样本与长尾分布，不能只报告平均值。

## 45.6 安全停止条件

- 任一未经授权的高风险外部副作用；
- 任一敏感字段跨域泄漏；
- 双重有效执行权或旧 Fencing Token 写入成功；
- 事件循环或资源预算突破；
- RSI 候选绕过独立评估或审批；
- 关键审计链丢失或无法验证。

## 45.7 实验成功判定

消息数下降本身不是成功。如果消息数减少，但成果质量下降、重复工作增加、时延恶化或安全违规上升，就不能判定环境驱动有效。

建议采用联合门槛：
- 安全硬门槛全部通过；
- 任务质量达到预注册非劣效要求；
- 无双重有效执行权；
- 关键审计链完整；
- 至少一项总效率指标改善，且没有以明显增加人工复核或隐藏成本为代价。
