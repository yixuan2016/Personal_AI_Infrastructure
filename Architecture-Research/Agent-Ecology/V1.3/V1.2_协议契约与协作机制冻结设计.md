# V1.2 协议契约与协作机制冻结设计卷

**版本定位：** V1.2 将 V1.1 的架构规范进一步转化为候选协议契约、机器可读 Schema、API 草案、核心 Ontology、互操作测试向量和部署边界。所有接口与字段均为参考规范草案，需经过多 Runtime 契约测试后才能正式冻结。

## 27. 协议规范化方法与冻结边界

### 27.1 规范语言

本报告使用以下规范性词语：

- **必须（MUST）：** 不满足即不符合对应互操作配置文件。
- **不得（MUST NOT）：** 明确禁止的行为。
- **应该（SHOULD）：** 除非存在明确、记录在案的理由，否则应当遵循。
- **可以（MAY）：** 实现方可选择支持。
- **配置文件（Profile）：** 对一组必需能力和测试用例的组合定义。

### 27.2 规范层次

| 层次 | 规范对象 | 冻结内容 | 暂不冻结 |
|---|---|---|---|
| 语义层 | Agent Ecology Core Ontology | 核心概念、关系、所有权、状态词汇 | 各行业完整本体 |
| 事件层 | Trace Envelope | 必选字段、类型、时间、来源、分类、因果 | 具体消息中间件 |
| 载荷层 | 七类 Trace Payload | 最小字段、Schema 版本和校验规则 | 所有领域扩展字段 |
| 命令层 | Task Command | 状态迁移、CAS、租约、幂等和 fencing | 数据库产品和锁实现 |
| 治理层 | Policy Decision | 决策效果、目的绑定、撤权和审批语义 | PDP/PEP 厂商和策略语言 |
| 联邦层 | Federation Projection | 身份、投影、版本协商、撤权、对账 | 节点发现网络拓扑 |
| 进化层 | RSI Release | 评估、Shadow、Canary、审批、回滚 | 自动化候选生成算法 |

### 27.3 六类互操作配置文件

| Profile | 名称 | 必需能力 | 适用节点 |
|---|---|---|---|
| EC-BASE | 环境基础 | 身份、空间隔离、分类、审计入口 | 所有节点 |
| EC-TRACE | 痕迹发布与消费 | 信封校验、不可变追加、幂等、因果 | 发布者、消费者 |
| EC-TASK | 任务运行时 | CAS、租约、fencing、状态机、恢复 | 执行 Agent、协调器 |
| EC-GOV | 治理与授权 | PDP/PEP、目的绑定、撤权、审批、fail-closed | ADS、领域节点、个人 OS |
| EC-FED | 跨域联邦 | 双向身份、最小投影、版本协商、撤权传播、对账 | 跨域节点 |
| EC-RSI | 受控进化 | 独立评估、Shadow、Canary、审批、回滚 | RSI 与 ADS |

实现方必须声明自己支持的 Profile 和版本。不得笼统宣称“兼容 Agent Ecology”，却不说明支持的配置文件、测试版本和未支持能力。

## 28. Agent Ecology Core Ontology 核心本体

### 28.1 核心实体

V1.2 建议形成 16 个核心实体：Agent、Domain、Space、Capability、Task、Trace、Artifact、Evidence、Policy、Decision、Lease、Subscription、Delegation、Evaluation、EvolutionCandidate，以及 Resource。

核心本体不等于把所有业务对象放进一张全局知识图谱。它首先是跨 Agent 互操作所需的共同语义契约；实现方可以使用关系数据库、文档存储、图数据库或组合存储。

### 28.2 关键关系

| 主体 | 关系 | 客体 | 约束 |
|---|---|---|---|
| Agent | belongs_to | Domain | 一个 Agent 可有主责任域，也可被授权参与其他域 |
| Agent | exposes | Capability | 能力必须有版本、负责人和验证状态 |
| Domain | owns | Artifact / Task / Policy | 所有权不因共享引用而转移 |
| Space | projects | State / Event / Artifact | 空间保存授权视图，不代表拥有源数据 |
| Agent | produces | Trace | Trace 必须保留实际产生主体 |
| Trace | causes | Trace | 因果关系可多父节点，不承诺全局总排序 |
| Task | depends_on | Task | 硬依赖图必须无环 |
| Task | held_by | Lease | 同一执行权在同一时刻只能有一个有效 fencing token |
| Artifact | supported_by | Evidence | 关键结论必须可追溯到证据 |
| Policy | governs | Action / Resource | 策略适用范围必须明确 |
| Decision | authorizes | Action | 决策受主体、目的、资源和有效期限制 |
| Agent | subscribes_to | Subscription | 订阅不自动授予读取载荷权限 |
| Domain | delegates_to | Domain / Agent | 委托必须限定动作、资源、目的和期限 |
| Evaluation | evaluates | Capability / Artifact / Candidate | 评估者应独立于候选生成者 |
| EvolutionCandidate | derived_from | Evidence | 候选必须保存来源谱系与回滚引用 |

### 28.3 标识符与命名约定

- `agent_id`、`domain_id`、`task_id`、`trace_id`、`decision_id` 等标识符必须全局唯一或在其命名空间内唯一。
- 推荐使用稳定 URI 或带命名空间的 ID；不应将数据库自增主键暴露为跨域永久标识。
- 对象版本与对象 ID 分离；更新对象状态不应改变对象身份。
- URI 是引用，不是授权凭证；解析 URI 时必须重新执行策略检查。
- 软删除、撤销和过期均应保留审计引用，不能通过删除对象使历史因果链断裂。

### 28.4 Ontology 版本映射

本体版本变化分为：
- Patch：标签、注释和不改变语义的修订。
- Minor：增加可选概念、关系或枚举值。
- Major：概念含义、关系约束、基数或状态语义发生不兼容变化。

跨域节点必须明确声明自己使用的 Ontology 版本。语义映射需要记录映射主体、源版本、目标版本、转换规则、信息损失和验证用例。无法无损映射时必须显式标注降级，不得静默转换。

机器可读核心概念表见 `ontology/agent-ecology-core-ontology-v1.2.csv`。

## 29. Trace Envelope 与领域载荷 Schema

### 29.1 信封必选字段

| 字段 | 类型 | 规则 |
|---|---|---|
| specversion | string | 当前信封格式版本 |
| id | string | 唯一事件 ID |
| source | URI/string | 产生事件的运行时或节点 |
| type | string | 稳定的事件类型名称 |
| time | RFC 3339 datetime | 事实发生时间 |
| datacontenttype | string | 本规范载荷采用 application/json |
| trace.trace_type | enum | 七类基础痕迹之一 |
| trace.schema_version | string | 领域载荷版本 |
| trace.actor_id | string | 实际发起者 |
| trace.domain_id | string | 责任域 |
| trace.classification | enum | 数据分类 |
| trace.visibility | enum | 可见范围 |
| trace.purpose | string | 本次处理目的 |
| data | object | 领域载荷 |

### 29.2 七类载荷的最低要求

| Trace 类型 | 最低载荷字段 | 验证重点 |
|---|---|---|
| Observation | observed_subject、observation_method、source_refs、claim_status | 事实、推断和待核实内容分离 |
| Intent | goal、scope、constraints、requested_by | 不得把意图当成已授权任务 |
| Task | objective、inputs、acceptance_criteria、risk_level、owner_domain | 验收、责任、预算和依赖齐备 |
| Artifact | artifact_ref、version、content_hash、producer_id | 哈希、版本和访问策略 |
| Dependency | predecessor_ref、successor_ref、dependency_type、condition | 环路检测和解除条件 |
| Risk | risk_type、impact、likelihood、severity、evidence_refs | 风险来源与独立复核 |
| Decision | decision_maker、scope、outcome、rationale、valid_until | 决策者权限和有效期 |

### 29.3 信封与载荷的分离

信封负责跨域通用属性；载荷负责领域语义。不得把所有业务字段堆进信封。对大文件、模型、数据集和多媒体对象，载荷只保存 Artifact 引用、版本和哈希，不直接嵌入大对象。

### 29.4 Schema 校验策略

- 发布端在写入前进行结构校验、身份校验和策略检查。
- 环境服务在接收时再次校验，不能信任发布端自报结果。
- 消费端按自己声明支持的版本进行校验。
- 未知可选字段可按兼容策略忽略，但未知主版本必须拒绝或隔离。
- Schema 校验通过不代表内容真实，也不代表内容安全；来源、证据和提示注入风险仍需独立处理。

## 30. Environment API 与命令契约

### 30.1 API 资源边界

| 资源 | 主要操作 | 语义 |
|---|---|---|
| Traces | publish / get / query | 追加痕迹、受控读取、按权限过滤查询 |
| Tasks | create / claim / heartbeat / submit / accept / cancel | 命令驱动的状态迁移 |
| Artifacts | register / resolve / version / verify | 注册元数据、解析引用、版本与完整性校验 |
| Subscriptions | create / update / pause / revoke | 注册观察条件，不直接授予数据权限 |
| Capabilities | register / verify / activate / deprecate / revoke | 能力发现和生命周期治理 |
| Policies | evaluate / publish / revoke | 决策与策略生命周期 |
| Decisions | propose / approve / deny / revoke | 人类或授权主体作出治理决定 |
| Federation | handshake / project / reconcile / revoke | 跨节点信任、投影和对账 |

### 30.2 关键请求头

- `Idempotency-Key`：命令类 POST 必须提供；同一键同一请求返回稳定结果。
- `If-Match`：修改聚合对象时携带预期版本；冲突返回 409。
- `Traceparent` 或等价关联标识：贯穿分布式调用链。
- `Authorization`：仅提供身份与委托上下文；不取代每次资源级授权。
- `Content-Type`：与 Schema 声明一致。

### 30.3 命令与查询分离

查询操作读取投影，不产生业务副作用；命令操作请求状态变化，必须校验主体、权限、版本、幂等和合法状态迁移。禁止客户端通过通用 PATCH 任意覆盖 Task 状态字段。

### 30.4 任务认领的原子契约

认领请求必须满足：
1. 当前 Task 状态为 ready；
2. 当前不存在有效 Lease；
3. 认领主体满足 Capability、Policy 和预算要求；
4. 在同一原子操作中写入 Lease、holder、expires_at 和单调递增 fencing_token；
5. 返回新的 Task version；
6. 相同幂等键重试返回原认领结果，不生成第二个租约。

### 30.5 API 错误响应统一结构

错误响应建议统一为：

```json
{
  "error": {
    "code": "FENCING_TOKEN_STALE",
    "message": "提交者持有的 fencing token 已失效",
    "retryable": false,
    "correlation_id": "corr_01JEXAMPLE",
    "details": {
      "task_id": "task_arch_2026_041",
      "expected_version": 8
    }
  }
}
```

`message` 面向人类；调用方必须根据稳定的 `code` 和 `retryable` 决定动作，不应解析自然语言来驱动自动化。

### 30.6 API 草案与状态

OpenAPI 3.1 草案见 `openapi/agent-ecology-environment-api-v1.2-draft.yaml`。其中 `.invalid` 域名仅为文档占位符，不是可访问服务地址。API 仍需通过多语言客户端、Schema 引用解析、错误码一致性和安全测试后才能冻结。

## 31. PDP/PEP 授权契约与撤权传播

### 31.1 授权请求的完整上下文

策略判定输入至少包含：

`subject + delegation_chain + action + resource + purpose + domain + classification + context + risk + requested_fields`

缺少必要上下文时，PDP 不应返回无条件 ALLOW。对于高风险动作，PDP 故障、身份不确定、策略版本不明或审计不可用时必须 fail-closed。

### 31.2 六类决策效果

| 效果 | 语义 | PEP 行为 |
|---|---|---|
| ALLOW | 在限定范围内允许 | 只执行明确列出的动作和字段 |
| DENY | 明确拒绝 | 阻止动作并记录原因 |
| STEP_UP | 需要更强身份或上下文 | 暂停并要求补充认证 |
| REQUIRE_APPROVAL | 需要人工批准 | 生成待审批 Decision，不执行副作用 |
| REDACT | 仅允许脱敏投影 | 按字段白名单生成最小数据视图 |
| DEFER | 暂时无法判定 | 挂起或按策略重试，不默认放行 |

### 31.3 本地 PEP 是最终执行门禁

ADS 的 PDP 可以给出跨域策略建议，但数据所在节点必须由本地 PEP 进行最终执行检查。策略缓存必须有版本、有效期和撤销状态。跨域调用不得仅凭远端节点声称“已经授权”而放行。

### 31.4 撤权协议

撤权顺序建议：
1. 授权主体创建带范围、原因、时间和对象的撤权 Decision。
2. PDP 将相关授权标记为 revoked，并停止签发新令牌。
3. PEP 接收撤权事件，拒绝后续动作。
4. 缓存与订阅失效，停止新的数据投影。
5. 对已投影数据按数据治理规则执行删除、失效、保留或不可逆脱敏。
6. 目标节点返回撤权回执与处理证据。
7. 源节点和 ADS 对撤权覆盖范围进行对账。
8. 无法确认撤权完成的节点进入隔离，不再接收敏感投影。

撤权无法追回已被合法读取并记忆的所有信息，因此系统必须在共享前最小化字段、限定目的和有效期，并对下游留存提出可执行要求。

## 32. Federation Protocol 跨域联邦协作协议

### 32.1 联邦基本原则

- 节点身份必须可验证，域身份不能由调用方任意声明。
- 源领域保留原始数据所有权和本地授权门禁。
- 跨域共享优先采用字段投影、摘要、能力契约和 Artifact 引用。
- 目标领域对收到的投影仍需执行本地策略检查。
- 联邦节点之间必须协商 Schema、Ontology、策略和能力版本。
- 撤权、过期、节点退役和信任根变更必须有传播与对账机制。

### 32.2 联邦握手流程

1. Node A 和 Node B 交换节点身份声明、信任根和支持的 Profile。
2. 双方验证证书链、节点状态和允许的领域关系。
3. 协商协议版本、Schema 版本、Ontology 映射和事件能力。
4. 发起方提交跨域目的、资源范围、字段清单、时限和风险等级。
5. 源节点 PDP 决策，必要时请求人类审批。
6. 源节点 PEP 生成最小投影、签名和哈希。
7. Relay 传输投影与事件序号。
8. 目标节点验证来源、签名、版本、目的和本地策略。
9. 目标节点返回接收回执和投影版本。
10. 双方持续对账事件、租约、撤权和投影状态。

### 32.3 联邦投影契约

投影至少包含：
- `projection_id`、`source_domain`、`target_domain`
- `source_object_ref`、`source_version`、`projection_version`
- `purpose`、`field_allowlist`、`classification`
- `policy_ref`、`decision_ref`、`expires_at`
- `content_hash`、`issuer_signature`
- `revocation_channel`、`retention_rule`

目标节点不能把投影 URI 当作源对象访问令牌；所有访问仍经过目标节点的本地策略。

### 32.4 联邦一致性与对账

跨节点不承诺全局强一致。每个投影流使用源节点序号、版本和幂等 ID；目标节点保存最后确认的 checkpoint。发现序号缺口时请求补齐或快照；发现版本分叉时暂停相关投影并执行对账。不能使用最后写入时间直接覆盖冲突。

![V1.2 跨域联邦投影](assets/15_federation_projection.png)

*图 15 跨域共享的是授权投影，不是源领域底库。*

### 32.5 节点失联与恢复

- 节点失联期间，不得继续使用已经过期的跨域授权。
- 允许本地低风险任务在本地有效策略下继续。
- 跨域高风险动作暂停。
- 恢复后先核对节点身份、策略版本、撤权记录、事件 checkpoint 和租约状态。
- 对未知结果的外部副作用先查询对账，再决定是否补偿；不得盲目重放。

## 33. 可靠性、错误恢复与可观测性契约

### 33.1 重试分类

| 错误类别 | 自动重试 | 处理方式 |
|---|---|---|
| 网络短暂失败 | 可以 | 指数退避、抖动、最大次数 |
| 429 限流 | 可以 | 遵循 Retry-After 和预算 |
| 503 依赖不可用 | 条件允许 | 高风险动作挂起，低风险按策略重试 |
| 403 权限拒绝 | 不可以 | 停止并申请授权 |
| 409 版本冲突 | 条件允许 | 重新读取状态，重新计算命令 |
| 410 租约过期 | 不可直接重试原提交 | 检查副作用，再重新认领 |
| 422 Schema 错误 | 不可以 | 修复载荷或版本 |
| 哈希不一致 | 不可以 | 隔离成果并重新获取可信副本 |
| 外部副作用结果未知 | 不可盲目重试 | 查询目标系统并对账 |

### 33.2 Outbox/Inbox 事务边界

发布领域事件时，业务状态变更和 Outbox 记录必须在同一事务内提交。消费者收到事件后，应先建立 Inbox/去重记录，再执行可重入处理。若消费过程跨越外部系统，必须把“调用结果未知”作为显式状态处理，不能简单认为超时等于失败。

### 33.3 可观测性字段

每条任务链至少贯穿：
- `trace_id`、`correlation_id`、`causation_id`
- `task_id`、`agent_id`、`domain_id`
- `capability_id`、`capability_version`
- `policy_version`、`decision_id`
- `lease_id`、`fencing_token`
- `artifact_ref`、`verification_id`
- `runtime_version`、`ontology_version`
- `attempt`、`budget_remaining`、`latency_ms`

日志中不得直接输出不必要的个人数据、密钥、授权令牌或完整私有上下文。

## 34. 互操作测试与一致性认证建议

### 34.1 测试套件结构

| 测试套件 | 重点 | 通过条件 |
|---|---|---|
| Schema Validation | 必选字段、类型、枚举、版本 | 正确样例通过，错误样例拒绝 |
| Trace Semantics | 事实/推断区分、因果、追加写 | 语义不丢失，历史不可篡改 |
| Task State Machine | 合法迁移、CAS、Lease、Fencing | 无双重有效认领，无旧令牌写入 |
| Policy Enforcement | 动态授权、目的、字段、撤权 | 未授权操作成功次数为零 |
| Federation | 节点身份、投影、版本、撤权 | 无未授权数据扩散，恢复可对账 |
| Failure Recovery | 断连、重复、乱序、重放 | 不产生重复外部副作用 |
| RSI Release | 离线、Shadow、Canary、审批、回滚 | 无越权发布，回滚可验证 |

### 34.2 V1.2 最小一致性测试向量

| 编号 | 输入场景 | 预期结果 |
|---|---|---|
| CV-001 | 同一事件重放 10 次 | 仅一个业务效果 |
| CV-002 | 两个 Agent 同时认领 | 仅一个有效租约 |
| CV-003 | 旧 fencing token 提交 | 拒绝并审计 |
| CV-004 | 撤权后再次读取 | 拒绝或按新策略脱敏 |
| CV-005 | PDP 故障时请求 L3 动作 | DEFER/DENY，不默认放行 |
| CV-006 | 跨域请求含未授权字段 | 字段剔除或整体拒绝 |
| CV-007 | 收到未知主版本 Schema | 隔离并返回版本不兼容 |
| CV-008 | 事件循环达到预算上限 | 停止扩散并进入冷却/死信 |
| CV-009 | RSI 候选绕过审批 | 发布门禁拒绝 |
| CV-010 | 联邦节点断连后恢复 | 对账后恢复，无重复副作用 |

## 35. 本地优先与云端混合部署参考映射

### 35.1 三种节点角色

| 节点 | 主要组件 | 数据责任 | 失联时行为 |
|---|---|---|---|
| Personal Node | 本地 Agent Runtime、私有 Environment、Local PEP、Artifact Store | 个人私有状态和本地成果权威 | 本地低风险能力继续；跨域动作挂起 |
| Domain Node | 领域 Agent、领域状态、领域 PEP、验证服务 | 领域业务数据和专业验收 | 领域内按本地策略继续 |
| Cloud Coordination Node | ADS 控制面、能力目录、跨域 Relay、全局索引投影 | 共同语义、跨域契约和协调元数据 | 缓存策略范围内有限运行；高风险跨域 fail-closed |

### 35.2 逻辑组件与物理部署不绑定

首期可以将 Environment API、Trace Service、Task Runtime、Artifact Registry、Policy Enforcement 和 Audit Service 作为模块化单体部署。随着负载、故障域、团队所有权和安全边界变化，再逐步拆分服务。不得为了“Agent Ecology”概念而提前引入过度复杂的微服务、消息平台或图数据库。

### 35.3 本地数据最小上云

建议云端优先保存：
- 能力目录中可公开或授权共享的描述；
- Ontology 核心版本和映射元数据；
- 经授权的事件摘要与投影；
- 不包含私有载荷的任务协作状态；
- 审计引用和必要的合规证据。

个人原始记忆、私有文件、完整上下文和敏感成果默认留在本地。任何上云投影必须有目的、字段清单、授权期限和撤权机制。

### 36.1 本轮建议冻结

### 36.2 仍需实验验证

1. 在单机、本地局域网和跨区域网络下比较事件投递延迟与恢复能力。
2. 测试多 Agent 高并发认领时 CAS 和租约机制的竞争表现。
3. 评估不同订阅索引和语义检索方式的召回率、误触发率和成本。
4. 验证撤权事件在断网、缓存、重放和节点恢复条件下的收敛时间。
5. 验证字段投影和 Ontology 映射是否存在隐性信息泄漏或语义损失。
6. 评估 Shadow/Canary 的样本量、统计显著性和回滚门槛。

### 36.3 正式冻结门槛

只有同时满足以下条件，才能把候选契约升级为正式冻结版本：
- 至少两个独立 Runtime 通过相同 Schema 与状态机测试；
- 发布者与消费者对相同事件得到一致语义解释；
- 任务并发测试无双重有效认领；
- 过期租约写入被可靠拒绝；
- 撤权在所有已登记 PEP 上有可观测回执；
- 联邦断连恢复可对账且不产生重复外部副作用；
- 高风险策略故障时 fail-closed；
- 全部测试报告、版本、环境、失败记录和回滚证据归档。

### 36.4 版本发布状态

**V1.2 当前状态：候选规范（Draft）。** 本轮已经形成文档、机器可读 Schema、OpenAPI 草案、核心 Ontology 表和测试向量；尚未通过独立 Runtime 互操作测试，因此不能宣称正式冻结或生产可用。
