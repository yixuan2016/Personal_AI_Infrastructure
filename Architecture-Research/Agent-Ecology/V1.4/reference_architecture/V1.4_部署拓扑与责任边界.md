# V1.4 部署拓扑与责任边界

## A. 单节点 / 本地试点
- 一个模块化 Environment Runtime。
- 一个事务型 State Store。
- Outbox/Inbox 与轻量 Event Relay。
- Trace Ledger、Artifact Registry、Ontology/Capability Registry。
- 本地 PEP 与工具适配器。
- 3–5 个 Agent Runtime。
- ADS 可作为逻辑独立控制模块或单独部署控制面。

## B. 单领域多 Agent
- Runtime Gateway、State Coordinator、Event Relay 明确接口。
- 本地数据与私有上下文不离开领域。
- 订阅与发现仅返回授权投影。
- Agent 通过 CAS、Lease、Fencing 取得执行权。
- 生产者与独立验证者分离。

## C. 多领域联邦
- 每个领域拥有自己的 State Store、Artifact Store、Trace 载荷和 PEP。
- ADS 管理跨域能力目录、共同 Ontology、策略模板、全局配额与审计关联。
- Federation Relay 仅同步经策略批准的最小事件投影。
- 网络分区时本地低风险自治有时限；高风险动作 fail closed。
- 跨域业务使用 Saga/补偿和人工升级，不使用全局数据库事务作为默认方案。

## D. 责任边界
- Agent：局部计划和授权范围内执行。
- Environment Runtime：权威状态、认领、事件、痕迹和成果索引。
- ADS：跨域能力、语义、策略协调、审计和生态评估。
- Domain PEP：本地数据/工具访问最终执行控制。
- Human Governor：关键授权、高风险审批、否决、接管和问责。

## E. 技术中立约束
本参考架构不指定 PostgreSQL、Kafka、NATS、Redis、Temporal 或 Kubernetes 为唯一技术选项。选型必须通过数据一致性、持久性、运维成本、资源占用、离线能力和团队能力的对照评估。
