## 摘要

V1.3 确立了环境驱动协作的基本命题：Agent 不必依靠持续点对点汇报来维持协作，而可以观察共同环境中的状态、痕迹和成果，并根据局部能力、依赖、预算与授权条件采取行动。V1.4 进一步回答：这个环境由什么组成、哪些数据具有权威性、事件如何传播、Agent 如何订阅和认领、执行权如何防止双重持有、错误痕迹如何被抑制、跨域授权如何落地、网络分区时如何恢复。

本报告提出 Environment Runtime 的七个逻辑子系统：Runtime Gateway、State Coordinator、Subscription & Discovery Router、Event Relay、Trace & Evidence Ledger、Artifact & Semantic Registry、Policy Enforcement & Audit。七者是逻辑职责，不要求第一阶段拆成七个微服务。首期建议采用模块化单体或少量边界清晰的进程，在本地优先架构下逐步拆分。

最重要的架构原则是：**权威状态与通知分离、事件投递与业务提交分离、痕迹与事实判断分离、能力声明与可信能力分离、ADS 决策与领域本地执行分离。** 环境中的事件只负责唤醒和提示，Agent 必须重新读取有权限的权威状态；事件采用至少一次投递并通过幂等消费处理重复；唯一执行权由原子认领、租约和 Fencing Token 共同约束；跨域数据由本地 PEP 最终执行访问策略。

# 47. V1.4 的研究目标与设计边界

## 47.1 本阶段要回答的七个问题

1. Environment Runtime 的逻辑组件、部署边界和职责是什么？
2. Task State、Domain Event、Trace、Artifact、Ontology 和 Policy 分别由谁拥有？
3. Agent 如何从环境中发现任务，而不把通知误认为执行授权？
4. 多个 Agent 同时认领任务时，如何避免双重执行和旧执行者复活？
5. 数字信息素如何排序候选，而不把热度误当成事实或权限？
6. ADS 如何实施跨域治理，而不把所有数据和执行集中到中央？
7. 网络分区、事件重复、Agent 崩溃、授权撤销和存储故障时，系统如何安全恢复？

## 47.2 设计目标

- **环境优先：** 共同环境成为协作上下文和任务发现的默认入口。
- **局部自治：** Agent 在授权边界内自主发现、判断、执行和复盘。
- **状态可验证：** 任务状态具有权威来源、版本和合法状态转换。
- **事件可恢复：** 事件允许重复投递，消费者可幂等处理并从检查点恢复。
- **痕迹可信：** 来源、因果、有效期、证据和反证可追溯。
- **执行可接续：** 执行者失效后可安全重新认领，旧执行者不能继续写入。
- **本地优先：** 领域数据与执行控制尽可能留在本地域；跨域只投影必要信息。
- **治理可执行：** ADS PDP 做策略协调，数据所在域 PEP 做最终访问控制。
- **渐进演进：** 先冻结逻辑契约，再按负载、隔离和可靠性证据拆分服务。

## 47.3 非目标

V1.4 不追求：
- 所有数据跨站点全局强一致；
- 所有 Agent 共享完整上下文或全部记忆；
- 每一个 Trace 都触发一次 Agent 执行；
- 用信息素分数替代事实核验、授权或人工审批；
- 通过一个中央 Agent 处理所有任务；
- 第一阶段部署完整微服务、Kubernetes、复杂服务网格或全局分布式事务；
- 承诺跨任意外部系统的端到端 exactly-once；
- 让 RSI 自动扩大权限或自行批准生产策略。

# 48. Environment Runtime 总体架构

## 48.1 逻辑架构

Environment Runtime 是一个受治理的协作运行时，由以下逻辑组件构成：

| 组件 | 核心职责 | 关键输入 | 权威输出 |
|---|---|---|---|
| Runtime Gateway | 身份接入、协议适配、请求路由、租户隔离 | Agent 身份、请求、协议声明 | 认证上下文、标准化请求 |
| State Coordinator | 任务状态机、原子认领、租约、资源预留 | 状态命令、版本、执行权令牌 | 权威任务状态、执行权 |
| Subscription & Discovery Router | 订阅管理、候选发现、能力匹配、唤醒 | 事件、能力、订阅条件 | 受权限过滤的候选通知 |
| Event Relay | Outbox 转发、事件路由、重试、死信、消费检查点 | 已提交事件 | 可重放的事件投递 |
| Trace & Evidence Ledger | 痕迹、证据、反证、因果链、审计引用 | Agent/系统产生的 Trace | 追加式可信记录 |
| Artifact & Semantic Registry | 成果版本、内容寻址、Ontology、能力契约 | 文件、语义变更、能力声明 | 版本化引用和语义映射 |
| Policy Enforcement & Audit | PDP/PEP、动态授权、审批、撤权、审计 | 主体、动作、资源、目的、上下文 | Permit/Deny/Challenge/Obligations |

这些是职责边界，不是服务拆分指令。第一阶段可以在一个 Runtime 进程内实现多个模块，只要数据所有权、API 契约、故障边界和权限边界明确。

## 48.2 七层运行时视图

1. **Agent Execution Layer：** Agent Runtime、工具适配器、局部执行状态、Checkpoint。
2. **Environment API Layer：** Runtime Gateway、身份解析、协议适配、请求校验。
3. **Coordination Layer：** 任务状态机、订阅发现、认领、租约、资源配额。
4. **Event Layer：** Outbox、Event Relay、Inbox、订阅投递、重试与死信。
5. **Knowledge Layer：** Trace Ledger、Artifact Registry、Ontology/Capability Registry。
6. **Governance Layer：** ADS PDP、领域 PEP、人类审批、撤权和审计。
7. **Storage & Observability Layer：** 权威状态存储、事件存储、对象存储、指标、日志和链路追踪。

![Environment Runtime 七层架构](assets/26_runtime_layers_8k.png)

## 48.3 运行时的三个平面

| 平面 | 管理对象 | 典型组件 | 失效影响 |
|---|---|---|---|
| Control Plane | 身份、能力、策略、Schema、订阅配置、预算 | ADS、Registry、Policy Catalog | 新配置、跨域协调和策略更新受影响 |
| Data Plane | 任务状态、Trace、Artifact、领域数据 | State Coordinator、Ledger、Object Store、PEP | 任务读写和本地协作受影响 |
| Event Plane | 事件发布、订阅、投递、重试、消费位点 | Outbox、Broker、Relay、Inbox | 通知延迟或堆积，但不应直接改变权威状态 |

**关键边界：** Event Plane 故障不应使已经提交的 Task State 变成未知状态；Control Plane 短暂不可用时，领域本地已授权的低风险操作可以按受限离线策略继续；高风险操作必须 fail closed。

## 48.4 运行时请求主路径

`Agent → Runtime Gateway → 身份认证 → 权限预检 → 读取授权投影 → 本地决策 → State Coordinator → Outbox → Event Relay → 订阅者唤醒`

Agent 被唤醒后仍必须重新读取权威状态和当前策略。事件通知不是任务所有权，也不是执行许可。

# 49. 数据权威边界：谁拥有事实，谁拥有痕迹

## 49.1 六类核心数据及权威源

| 数据对象 | 权威来源 | 更新方式 | 是否允许覆盖历史 |
|---|---|---|---|
| Task State | State Coordinator 所属事务数据库 | 条件更新、状态机命令 | 当前状态可变，历史状态事件不可静默覆盖 |
| Domain Event | 本地域 Outbox/事件日志 | 事务提交后追加 | 不覆盖；重复事件可识别 |
| Trace/Evidence | Trace Ledger | 追加、引用、反证、撤销关系 | 不覆盖；更正通过新记录表达 |
| Artifact | Artifact Registry + 对象存储 | 新版本、内容哈希 | 已发布版本不可原位替换 |
| Ontology/Capability | 版本化 Registry | 提案、评审、发布、废弃 | 不覆盖已发布版本，必须迁移 |
| Policy/Authorization | ADS 策略目录 + 领域本地执行点 | 策略版本、授权决策、撤权 | 决策留痕；权限可撤销 |

## 49.2 不建议第一阶段采用“所有数据全量 Event Sourcing”

应区分三个概念：

- **State Store：** 当前权威状态，支持条件更新和事务。
- **Domain Event Log：** 记录关键业务状态转换，支持投影重建、订阅和审计关联。
- **Trace Ledger：** 记录观察、证据、反证、执行和治理痕迹，支持追加和来源追溯。

三者可以共享底层存储技术，但逻辑职责和保留策略不同。不要把所有模型推理文本、工具输出、业务状态和安全审计混成一个无边界事件流。

建议首期采用“事务状态存储 + Transactional Outbox + 追加式 Trace + 版本化 Artifact”。只有当审计重建、复杂时态查询或状态回放成为明确需求时，再对特定聚合引入更完整的 Event Sourcing。

![权威数据与派生投影边界](assets/27_data_authority_8k.png)

## 49.3 核心数据对象

### Task

- `task_id`：全局任务标识；
- `domain_id` / `workspace_id`：所属领域与工作空间；
- `goal` / `task_contract`：目标、输入、输出和验收标准；
- `required_capabilities`：能力约束；
- `dependencies`：前置任务与依赖条件；
- `classification`：数据分类；
- `risk_tier`：风险等级；
- `budget`：Token、工具、计算、时长和外部成本预算；
- `state` / `state_version`：权威状态和单调版本；
- `claim_epoch`：认领代次；
- `created_by` / `owner_domain`：责任主体；
- `deadline` / `expires_at`：期限与过期时间。

### Claim / Lease

- `claim_id`、`task_id`、`agent_principal`；
- `lease_id`、`lease_expires_at`；
- `fencing_token`：针对受保护资源单调递增；
- `claim_epoch`：任务执行代次；
- `heartbeat_at`、`renewal_count`；
- `quota_reservation_ref`；
- `policy_decision_ref`；
- `claim_status`：active、expired、released、revoked、superseded。

### Trace

- `trace_id`、`trace_type`、`subject`；
- `occurred_at`、`recorded_at`；
- `target_ref`、`causation_ref`、`correlation_ref`；
- `source_refs`、`content_hash`；
- `schema_version`、`classification`、`visibility`；
- `valid_until`、`verification_status`；
- `revokes_or_supersedes`；
- `policy_projection_ref`。

### Artifact

- `artifact_id`、`version`、`content_hash`；
- `media_type`、`size`、`created_by`；
- `task_ref`、`source_refs`；
- `classification`、`retention_policy`；
- `storage_location_ref`、`signature_ref`；
- `supersedes`、`verification_status`。

### Subscription

- `subscription_id`、`principal`、`domain_scope`；
- `event_types`、`ontology_filter`、`task_predicate`；
- `required_capabilities`、`classification_ceiling`；
- `delivery_mode`、`max_concurrency`；
- `rate_limit`、`retry_policy`、`expires_at`；
- `policy_version`、`subscription_status`。

## 49.4 数据版本和删除

追加式审计与隐私删除可能存在张力。建议：
- Trace 尽量保存必要元数据和受控引用，不复制完整敏感内容；
- Artifact 内容与索引元数据分离，按领域保留策略管理；
- 到期或删除请求通过 tombstone/撤销引用表达；
- 对必须删除的载荷，删除密钥或对象并保留最小化审计事实；
- 哈希本身也可能成为可关联数据，不能默认所有哈希都无隐私风险；
- 法律保留、用户删除、审计完整性之间必须由明确策略决定，不能由 Agent 自行裁决。

# 50. 状态机与事件契约

## 50.1 Task State 状态机

推荐状态：

`DRAFT → READY → DISCOVERABLE → CLAIMED → RUNNING → SUBMITTED → VERIFYING → ACCEPTED`

异常或中断状态：

`BLOCKED`、`LEASE_EXPIRED`、`REJECTED`、`CANCELED`、`QUARANTINED`、`FAILED`、`RETRY_WAIT`。

不是所有状态都允许任意跳转。状态转换由 State Coordinator 校验前置条件、当前版本、主体权限和风险要求。

![Task State 状态机](assets/28_task_state_machine_8k.png)

## 50.2 状态转换规则

| 当前状态 | 目标状态 | 触发主体 | 前置条件 |
|---|---|---|---|
| DRAFT | READY | 创建者/授权系统 | 契约完整、输入引用有效 |
| READY | DISCOVERABLE | Runtime | 依赖满足、策略允许发现 |
| DISCOVERABLE | CLAIMED | Agent/仲裁器 | 能力匹配、授权通过、原子认领成功 |
| CLAIMED | RUNNING | 当前持有者 | 租约有效、Fencing Token 当前 |
| RUNNING | SUBMITTED | 当前持有者 | 成果引用、证据和预算账本提交 |
| SUBMITTED | VERIFYING | 验证调度器 | 独立验证者已接受任务 |
| VERIFYING | ACCEPTED | 独立验证者/领域验收者 | 验收条件通过 |
| RUNNING | BLOCKED | 当前持有者/Runtime | 依赖、资源或授权阻塞 |
| CLAIMED/RUNNING | LEASE_EXPIRED | Runtime | 租约失效且无有效续期 |
| 任意非终态 | CANCELED | 有权主体 | 取消策略允许 |
| 任意状态 | QUARANTINED | 安全治理主体 | 检测到污染、越权或完整性风险 |

建议统一使用事件名称与 Schema 版本：
- `task.created.v1`
- `task.ready.v1`
- `task.claimed.v1`
- `task.lease.renewed.v1`
- `task.lease.expired.v1`
- `task.progress.updated.v1`
- `task.blocked.v1`
- `task.submitted.v1`
- `task.verification.started.v1`
- `task.accepted.v1`
- `task.rejected.v1`
- `trace.recorded.v1`
- `trace.disputed.v1`
- `artifact.published.v1`
- `policy.revoked.v1`
- `capability.version.published.v1`
- `runtime.health.changed.v1`

## 50.4 CloudEvents 兼容信封

推荐以 CloudEvents 作为事件信封映射，而不是将其当成业务模型：

```json
{
  "specversion": "1.0",
  "id": "evt-01J...",
  "source": "urn:agent-ecology:domain:research",
  "type": "agent.ecology.task.ready.v1",
  "subject": "task/task-01J...",
  "time": "2026-11-10T01:00:00Z",
  "datacontenttype": "application/json",
  "dataschema": "urn:agent-ecology:schema:task-ready:1",
  "data": {
    "task_ref": "task-01J...",
    "state_version": 8,
    "required_capabilities": ["research.verify"],
    "classification": "internal",
    "projection_ref": "projection-01J...",
    "expires_at": "2026-11-10T03:00:00Z"
  }
}
```

CloudEvents 的 `source + id` 可用于事件去重；重复投递时消费者应识别同一事件。事件中只放最小必要数据和受控引用，不放长期凭证、密钥或无权限的原始内容。

## 50.5 投递语义：至少一次 + 幂等，而不是虚假的端到端 exactly-once

- Outbox 事件随状态事务一并提交；
- Relay 可以重复投递；
- Inbox 保存已处理的 `source + id` 或业务幂等键；
- 消费者先检查幂等记录，再提交本地状态变化；
- 外部副作用使用外部系统支持的幂等键；
- 无幂等能力的外部 API 必须执行结果核对和人工对账策略；
- 事件顺序只在明确的聚合键/分区内承诺，不承诺跨所有任务的全局顺序。

Kafka 官方文档明确区分发布、消费和外部系统写入的语义；即使消息平台支持事务，也不能自动保证跨任意外部系统的端到端 exactly-once。Temporal 的持久事件历史和重放机制则说明长时间工作流可以通过事件记录恢复，但 Agent 的非确定性推理仍需被包装为可审计的活动边界。

# 51. Agent 订阅、发现与资格匹配

## 51.1 订阅不是授权

Agent 可以订阅“我希望知道某类任务”，但订阅不代表它可以读取任务全部内容，更不代表它能执行任务。

订阅流程：
1. Agent 声明所需事件类型、领域范围、能力和数据分类上限。
2. Runtime 校验身份、订阅权限和配额。
3. Router 将订阅注册为可版本化配置。
4. 事件到达后执行过滤和权限投影。
5. Agent 收到最小通知。
6. Agent 使用当前身份重新读取授权任务投影。
7. Agent 判断是否参与，必要时申请澄清或授权。
8. 符合条件后进入认领流程。

## 51.2 两阶段资格筛选

**第一阶段：硬性资格门槛。** 任一条件不满足就不得进入候选集：
- 能力和版本不匹配；
- 不属于允许的领域范围；
- 数据分类超出授权上限；
- PDP/PEP 拒绝；
- 预算或并发配额不足；
- Agent 状态不健康；
- 工具或模型不满足任务约束。

**第二阶段：候选排序。** 仅对通过硬门槛的 Agent 评分：
- 能力匹配程度；
- 历史验收质量；
- 预计完成时间；
- 资源和 Token 成本；
- 任务连续性和上下文准备度；
- 当前负载；
- 公平调度和探索预算。

排序分数不能覆盖硬门槛。即使 Agent 得分最高，若授权不通过，也不能执行。

## 51.3 事件通知是唤醒提示，不是事实

通知可能延迟、重复、乱序或过期。Agent 收到通知后必须：
- 获取当前 `task_id` 和 `state_version`；
- 重新读取权威任务状态；
- 验证依赖和租约；
- 重新请求或检查授权；
- 只对当前有效状态执行动作。

![订阅发现与认领流程](assets/29_discovery_claim_8k.png)

## 51.4 反对无边界广播

不建议每个新任务都广播给所有 Agent。推荐：
- 按能力、领域、数据分类、风险和资源进行过滤；
- 分层订阅，先唤醒小范围候选；
- 未认领任务逐步扩大候选范围；
- 低优先级任务采用退避和 aging；
- 设定每个 Agent 的通知速率、并发数和订阅租约；
- 观察到事件风暴时触发背压、合并通知和降级策略。

# 52. 原子认领、租约与 Fencing

## 52.1 认领流程

1. Agent 收到候选通知；
2. 读取任务最新状态与版本；
3. 检查依赖、能力、预算和风险；
4. 请求 ADS PDP 或本地域策略决策；
5. State Coordinator 执行条件更新；
6. 认领成功时递增 `claim_epoch` 和相关资源 `fencing_token`；
7. 生成短时租约；
8. Agent 进入 RUNNING；
9. 执行期间续租和心跳；
10. 提交成果后释放租约，或由验证流程关闭任务。

## 52.2 CAS、Lease 与 Fencing 各自解决什么

| 机制 | 解决的问题 | 不解决的问题 |
|---|---|---|
| CAS / 版本条件更新 | 防止多个 Agent 同时把同一任务从 READY 改为 CLAIMED | 不阻止已失效 Agent 对外部系统继续写入 |
| Lease | 执行者失联后允许任务重新分配 | 不保证旧执行者停止工作 |
| Fencing Token | 让资源端拒绝旧执行者的过期写入 | 不自动撤销已经完成的外部副作用 |
| Idempotency Key | 防止同一逻辑动作重复产生副作用 | 不替代权限判断与资源所有权 |

**Fencing Token 必须由被保护资源的写入端校验。** 如果只是发给 Agent 但下游数据库、工具服务或业务 API 不检查它，就没有真正形成防护。

## 52.3 租约时间与时钟

- 租约到期判断由权威状态服务或数据库时间负责，不信任 Agent 本地时钟。
- 心跳间隔、租约长度应基于网络 P99、Agent 推理时间和故障检测目标进行先导测试。
- 续租失败后，Agent 应停止发起新的受保护动作。
- 旧执行者恢复网络时必须重新认领，不得凭旧内存状态继续写入。
- 对外部不可逆动作，执行前再次验证租约、Fencing Token 和授权。

## 52.4 外部副作用

对发送邮件、拨打电话、转账、发布代码、修改权限等副作用，采用：
- 预先授权和动作级策略；
- 动作幂等键；
- 操作前状态检查；
- 操作后结果核对；
- 必要时人类审批；
- 无法自动补偿时升级人工处理。

不要把“Agent 已经写出工具调用”视为“工具动作已经成功”或“动作只会发生一次”。

# 53. 数字信息素引擎 V1.4

## 53.1 从单一热度分数升级为多维信号

每条痕迹保留独立维度：

`TraceSignal = {relevance, freshness, evidence_strength, source_independence, contradiction, duplication, provenance_quality, risk}`

发现排序可使用可配置评分：

`P(x,t) = w1·R + w2·F + w3·E + w4·I + w5·Q − w6·C − w7·D − w8·K`

其中：
- R：与任务相关性；
- F：时效性；
- E：证据强度；
- I：来源独立性；
- Q：来源和过程可追溯质量；
- C：反证强度；
- D：重复程度；
- K：风险或污染信号。

时间衰减可采用：

`F(t) = exp(−λ × Δt)`

权重由领域策略和实验数据确定，不设一个适用于所有领域的全局常数。

## 53.2 引擎处理链

![数字信息素引擎](assets/30_pheromone_engine_8k.png)

1. **Ingest：** 接收 Trace，校验 Schema、身份、来源和签名。
2. **Normalize：** 统一时间、实体引用、来源簇和 Ontology 概念。
3. **Deduplicate：** 识别同源重复、近重复和转述链。
4. **Verify：** 检查证据引用、独立来源、反证和验证状态。
5. **Score：** 计算相关性、新鲜度、证据和风险信号。
6. **Decay：** 根据类型和领域策略衰减。
7. **Quarantine：** 对异常来源、污染和争议痕迹隔离。
8. **Project：** 按 Agent 权限生成排序和可见性投影。
9. **Feedback：** 任务验收结果更新策略候选，但不直接改写历史痕迹。

## 53.3 反证与来源簇

多个 Agent 引用同一个网页、同一篇论文或同一个数据集，不等于多个独立证据。系统应构建 `source_cluster_id`，并区分：
- 原始来源；
- 二手转述；
- 独立测量；
- 独立复核；
- 相互矛盾的来源；
- 被撤回或过期的来源。

反证不能删除旧结论。它应追加一条 `trace.disputed` 或 `evidence.countered`，并让旧痕迹进入降权、复核或隔离流程。

## 53.4 防止信息素被操纵

- 每个主体的影响力设置速率和贡献上限；
- 未验证痕迹不得无限自我强化；
- 生产者不能成为唯一验证者；
- 同源重复引用按来源簇去重；
- 保留探索预算，避免热门痕迹挤压少数新线索；
- 异常增长、协同账号和模板化痕迹触发风险检测；
- 隔离区不参与正常自动化触发；
- 恢复痕迹必须保留原始隔离和复核记录。

**核心原则：信息素决定“先看什么”，不决定“什么是真的”，更不决定“谁有权做什么”。**

# 54. ADS 联邦治理与本地优先执行

## 54.1 全局控制面与领域本地数据面

建议采用联邦式拓扑：

- **ADS 全局控制面：** 能力目录、共同 Ontology、跨域策略模板、身份联邦、全局配额、审计关联和生态级风险管理。
- **领域 Runtime 本地数据面：** 领域任务状态、私有数据、Trace 载荷、Artifact、领域规则、本地 PEP 和专业验收。
- **跨域投影：** 只同步任务所需的最小字段、引用、状态和策略元数据。
- **人类外环：** 对重大授权、敏感数据跨域、高风险动作、策略发布和 RSI 升级保留审批权。

ADS 可以知道“某领域有一个符合某能力契约的任务”，但不应因此自动取得任务的完整数据或领域数据库的读取权。

## 54.2 PDP 与 PEP

- **PDP（Policy Decision Point）：** 依据主体、动作、资源、目的、上下文、数据分类和风险给出决策。
- **PEP（Policy Enforcement Point）：** 在本地资源、工具或数据出口处执行允许、拒绝、字段投影、脱敏、限流和审计要求。
- **PAP（Policy Administration Point）：** 管理策略版本、审批、发布和回滚。
- **PIP（Policy Information Point）：** 提供身份、资源属性、风险和上下文数据。

ADS 可以协调 PDP，但最终访问必须由资源所在域的 PEP 执行。

## 54.3 授权决策模型

请求必须绑定：
- 主体 principal；
- 动作 action；
- 资源 resource；
- 目的 purpose；
- 数据字段 field_scope；
- 领域 domain；
- 风险 risk_tier；
- 期限 expires_at；
- 预算 budget；
- 任务 task_ref；
- 策略版本 policy_version。

决策结果：
- `PERMIT`：允许；
- `DENY`：拒绝；
- `CHALLENGE`：需要补充认证或人类审批；
- `PERMIT_WITH_OBLIGATIONS`：允许，但必须满足字段过滤、脱敏、日志、速率限制或期限等义务。

MCP 的 HTTP 授权规范基于 OAuth 体系，要求资源服务器验证面向自身资源的访问令牌，并以 scope 引导最小权限。V1.4 建议将其作为工具访问的一层，而不是让 MCP Token 取代 ADS 的业务授权决策。

## 54.4 撤权传播

- 本地 PEP 对本地新请求立即应用已知撤权；
- 跨域撤权通过版本化策略事件传播；
- 令牌和缓存必须有明确最大有效期；
- 高风险动作必须获取新鲜授权，不依赖长时间缓存；
- 断网时不得继续执行需要实时审批的高风险动作；
- 对已开始的操作按策略执行中止、补偿或人工接管；
- 记录撤权发起、传播、确认和本地生效时间。

![ADS 联邦控制与本地执行](assets/31_federated_governance_8k.png)

## 54.5 离线与网络分区策略

| 风险等级 | 网络分区时的处理 |
|---|---|
| L0 只读公开信息 | 可按本地缓存和来源时效策略继续 |
| L1 低风险可逆动作 | 可使用短时、范围明确的已签发授权 |
| L2 对外联系、跨域数据处理等 | 依据具体授权；无法确认新鲜策略时暂停或请求审批 |
| L3 高风险、不可逆或重大权限变更 | 默认 fail closed，等待在线授权或人类接管 |

本地优先不是“断网也可以做所有事”。必须明确离线授权的范围、期限、可执行动作和撤权延迟上限。

# 55. 分布式事件、冲突与故障恢复

## 55.1 事件可靠性路径

推荐：

`State Transaction → Outbox → Event Relay → Broker → Inbox → Idempotent Consumer → Projection`

每个环节记录：
- event_id；
- aggregate_id；
- aggregate_version；
- schema_version；
- correlation_id；
- causation_id；
- delivery_attempt；
- occurred_at / recorded_at；
- consumer_checkpoint。

## 55.2 顺序与冲突策略

- 单个 Task 聚合内使用 `aggregate_version` 保证状态转换顺序。
- 不承诺跨任务全局总序。
- 多个投影允许短暂最终一致，但关键动作回源权威状态。
- 任务状态冲突采用 CAS 失败后重新读取和决策，不用最后写入覆盖。
- Artifact 采用不可变版本和显式合并，不做静默覆盖。
- Ontology 变更通过提案、兼容性评审和迁移版本处理。
- Trace 只追加，不对历史记录执行原位合并。

## 55.3 故障模式与恢复

| 故障 | 影响 | 自动恢复 | 必须升级的条件 |
|---|---|---|---|
| Agent 崩溃 | 任务中断 | 租约过期、检查点恢复、重新认领 | 外部副作用结果不确定 |
| Event Broker 不可用 | 通知延迟 | Outbox 累积、恢复后补投 | Outbox 达容量阈值 |
| 重复事件 | 重复触发 | Inbox 去重、幂等处理 | 外部系统不支持幂等 |
| 事件乱序 | 投影暂时错误 | 聚合版本检查、回源 | 关键状态无法收敛 |
| State Store 不可用 | 无法确认权威状态 | 本地缓存只读降级 | 所有写入与认领暂停 |
| Artifact Store 不可用 | 无法读取/提交成果 | 缓存已有内容、延迟提交 | 成果完整性无法验证 |
| PDP 不可用 | 新授权无法确认 | 已授权低风险短时离线策略 | 高风险请求全部拒绝 |
| PEP 撤权滞后 | 旧权限可能继续有效 | 策略版本检查、短令牌 TTL | 超过撤权延迟目标 |
| 网络分区 | 跨域同步中断 | 本地队列与联邦重放 | 高风险跨域动作暂停 |
| Trace 污染 | 错误信息传播 | 隔离、降权、反证 | 关键决策受污染影响 |
| Fencing 校验失效 | 旧执行者可能写入 | 资源端拒绝旧 Token | 任何旧 Token 写入成功 |

![故障检测与恢复路径](assets/32_failure_recovery_8k.png)

## 55.4 长任务与 Durable Execution

对于持续数小时或数天的任务，Runtime 应持久化：
- 当前 Task State；
- 已提交的 Artifact；
- 执行检查点；
- 已完成的外部动作引用；
- 依赖和等待条件；
- 当前预算和租约；
- 相关 Trace 与授权决策引用。

可借鉴 Durable Execution 的事件历史和重放思想，但要区分：
- 工作流引擎负责持久等待、计时器、重试和确定性流程；
- Agent 负责非确定性推理、任务判断和内容生成；
- 外部动作由工具适配器和 PEP 控制；
- 恢复时重建执行上下文，不应重复执行已成功的不可逆动作。

# 56. 多 Runtime 联邦互操作

## 56.1 互操作不等于共享数据库

不同 Runtime 可以使用不同模型、工具、存储和执行框架，只需遵守共同的协作契约：
- Identity Contract；
- Capability Contract；
- Task Contract；
- Trace Contract；
- Artifact Reference Contract；
- Event Envelope Contract；
- Policy Decision Contract；
- Ontology Mapping Contract。

A2A 提供 Agent Card、Task、Message、Artifact 和任务状态等 Agent 交互概念；V1.4 将其作为跨 Runtime 交互适配层，而不是要求所有 Runtime 使用同一内部数据模型。

## 56.2 联邦事件投影

跨域事件只发送：
- `origin_domain`；
- `event_id`；
- `event_type`；
- `aggregate_ref`；
- `state_version`；
- `classification`；
- `projection_policy_id`；
- `policy_epoch`；
- `expires_at`；
- `payload_ref`（受控引用）。

不直接复制：
- 原始个人记忆；
- 访问令牌和密钥；
- 未授权的完整文件；
- 私有推理上下文；
- 无必要的工具返回内容。

## 56.3 Runtime Adapter

每个 Runtime Adapter 负责：
- Agent 身份映射；
- A2A/MCP 等协议适配；
- 本地任务状态映射；
- Trace 和 Artifact 引用映射；
- Schema 版本兼容；
- 授权上下文传递；
- 错误码和重试语义映射；
- 断线重连和事件重放。

不得把不同 Runtime 的内部提示词、记忆格式或模型状态强行统一为一个中央结构。

# 58. 安全威胁模型

## 58.1 主要威胁

1. **Prompt Injection / Trace Injection：** 恶意内容伪装成可信痕迹或指令。
2. **Sybil / Agent Impersonation：** 多个伪造主体制造虚假多数。
3. **Replay：** 重放旧事件、旧授权或旧执行命令。
4. **Confused Deputy：** Agent 利用 Runtime 权限访问超出自身授权的数据。
5. **Cross-domain Leakage：** 事件、Artifact 或 Trace 投影泄露其他领域信息。
6. **Stale Authorization：** 撤权后旧令牌、缓存或离线节点仍可访问。
7. **Capability Poisoning：** Agent 虚报能力或注册恶意工具。
8. **Resource Exhaustion：** 事件风暴、订阅泛滥、任务抢占和预算耗尽。
9. **Fencing Bypass：** 下游资源未校验 Token，旧执行者继续写入。
10. **RSI Policy Drift：** 自我改进扩大权限或改变安全策略。

## 58.2 防护原则

- 所有 Trace、Artifact 和 Agent 输出默认视为不可信数据，必须与系统策略和可执行指令隔离。
- Agent Card/Capability 是声明，不等于已验证能力；必须记录测试、责任人和版本。
- 事件必须具备来源、ID、Schema、时间和权限上下文。
- 工具调用在本地 PEP 进行资源级授权。
- 跨域投影遵循字段最小化和目的限定。
- 高风险动作要求新鲜授权和必要的人类审批。
- Fencing Token 在下游资源端强制验证。
- 预算、并发和速率必须有硬上限。
- RSI 不得修改自身审批边界、审计规则和根策略。
- 安全事件隔离后保留证据链，不能自动清除异常历史。

# 59. 可观测性、容量与运行指标

## 59.1 可观测性三支柱

- **Metrics：** 任务成功率、事件积压、租约过期、认领冲突、授权拒绝、资源使用。
- **Logs：** 结构化操作日志、错误类别、策略版本和执行主体。
- **Traces：** 从任务发布、发现、认领、执行、工具调用到验收的因果链。

建议采用 OpenTelemetry 兼容的 Trace/Metric/Log 关联方式，但避免把敏感提示词、访问令牌、私有记忆和完整工具响应直接写入通用日志。

## 59.2 核心指标

| 指标 | 计算/含义 |
|---|---|
| Event Lag | 事件发生至订阅者收到通知的延迟 |
| Outbox Age | 最老未投递事件的等待时间 |
| Inbox Duplicate Rate | 重复事件占消费总量比例 |
| Claim Contention | 多 Agent 竞争同一任务的比例 |
| Lease Expiry Rate | 租约自然过期与异常过期次数 |
| Stale Fencing Rejection | 被正确拒绝的旧 Token 写入次数 |
| Task Recovery Time | Agent 失效至新执行者恢复时间 |
| Projection Staleness | 派生投影落后于权威状态的时间 |
| Revocation Propagation | 撤权至各 PEP 生效的时间 |
| Quarantine Rate | 被隔离痕迹比例及复核结果 |
| Artifact Integrity Failure | 内容哈希/签名验证失败次数 |
| Cost per Accepted Artifact | 每个验收成果的总成本 |

## 59.3 SLO 不预设虚假数字

V1.4 不直接承诺全局统一的延迟和吞吐数字。应先按本地单节点、单领域多 Agent、跨领域联邦三种部署形态建立基线，再根据任务风险和硬件条件设定：
- 状态提交 P95/P99；
- 本地事件唤醒 P95/P99；
- 事件积压恢复时间；
- 任务恢复时间；
- 撤权传播上限；
- Artifact 完整性验证成功率；
- 审计链完整率；
- 高风险未授权动作数（目标为 0）。

所有指标必须同时报告分位数、失败率和样本量。

# 60. 部署拓扑与渐进演进

## 60.1 单节点 / 本地试点

- 一个 Environment Runtime 模块化进程；
- 一个事务型状态数据库；
- Outbox/Inbox；
- 本地对象存储或受控文件存储；
- Trace Ledger；
- 本地 PEP；
- 3–5 个 Agent Runtime；
- ADS 可先作为逻辑独立模块或单独控制面。

此阶段不需要为了“看起来分布式”而引入完整微服务集群。

## 60.2 单领域多 Agent

- Runtime Gateway 与 State Coordinator 明确接口；
- Event Relay 独立处理通知和重试；
- Trace、Artifact、Semantic Registry 采用逻辑独立存储边界；
- Agent 按能力和资源分组；
- 本地域 PEP 负责所有工具与数据访问；
- 对热点任务和订阅分区进行压测。

## 60.3 多领域联邦

- 每个领域部署自己的本地 Runtime、State Store、Artifact Store 和 PEP；
- ADS 维护全局能力目录、共同语义和跨域策略；
- Federation Relay 传递授权投影；
- 每个领域拥有独立故障域和数据所有权；
- 跨域操作采用 Saga/补偿与人工升级，不依赖全局数据库事务。

## 60.4 拆分服务的触发条件

仅在出现以下证据时拆分：
- 不同模块需要不同扩缩容策略；
- 故障隔离要求独立进程；
- 数据所有权或安全边界要求独立部署；
- 团队责任边界已稳定；
- 单体模块间耦合已可控；
- 独立部署带来的可靠性或成本收益超过运维复杂度。

# 61. V1.4 验证方案与验收门槛

## 61.1 必测场景

1. 两个 Agent 同时认领同一任务；
2. Agent 认领后网络断开，租约过期，旧 Agent 恢复；
3. Event Relay 重复投递同一事件；
4. 消费者处理成功但确认失败；
5. Agent 在外部副作用成功后崩溃；
6. Artifact 上传完成但状态提交失败；
7. ADS 撤权时一个领域 Runtime 处于离线状态；
8. 订阅者收到过期或乱序事件；
9. 多 Agent 对同一 Trace 产生相互冲突的判断；
10. 恶意 Agent 通过大量重复痕迹制造虚假热门；
11. 事件 Broker 中断后 Outbox 堆积并恢复；
12. Fencing Token 未通过下游资源校验的负向测试；
13. Ontology 新版本与旧 Runtime 不兼容；
14. RSI 候选试图修改根策略或跳过审批。

## 61.2 验收清单

- [ ] 每类数据均有唯一权威源和责任主体。
- [ ] Task State 只允许合法状态转换。
- [ ] 所有状态写操作均具备版本条件。
- [ ] Outbox 与权威状态在同一事务边界提交。
- [ ] 消费者能够识别重复事件并幂等处理。
- [ ] 事件通知不会被误当成权限或任务所有权。
- [ ] 任务认领具备 CAS、Lease 和 Fencing。
- [ ] 下游资源能够拒绝旧 Fencing Token。
- [ ] 外部副作用具备幂等或结果核对方案。
- [ ] Agent 崩溃后可从持久状态安全接续。
- [ ] Trace 支持来源、因果、反证和隔离。
- [ ] 数字信息素不会将重复来源当作独立证据。
- [ ] ADS PDP 与领域 PEP 责任边界明确。
- [ ] 跨域投影符合字段级最小权限。
- [ ] 离线策略按风险分级，L3 默认 fail closed。
- [ ] 撤权传播和缓存有效期可测量。
- [ ] Artifact 版本与内容完整性可验证。
- [ ] Ontology/Capability 版本兼容规则明确。
- [ ] RSI 不能自我批准、自我扩大权限或修改根策略。
- [ ] 运行指标、故障演练和审计证据完整归档。

## 61.3 试点通过条件

安全是硬门槛，不可用性能改善抵消：
- 未授权高风险动作：0；
- 跨域敏感数据泄漏：0；
- 旧 Fencing Token 写入成功：0；
- 关键状态无权威来源：0；
- 关键审计链无法追溯：0；
- 重复事件导致重复不可逆副作用：0。

其他性能指标以先导测试建立基线，再按部署形态设定验收阈值。

## 62.1 尚待验证的关键假设

- H1：环境订阅和受限唤醒能降低无效消息与 Token 成本。
- H2：事务 Outbox + 幂等消费在目标部署规模下满足可靠性要求。
- H3：CAS + Lease + Fencing 可在多 Runtime 故障场景下保持唯一有效执行权。
- H4：多维信息素排序比单一热度排序更能抑制错误传播。
- H5：本地 PEP + ADS PDP 能在跨域治理中兼顾安全和延迟。
- H6：模块化单体可支持试点规模，避免过早微服务化。

# 63. V1.5 研究路线：群体调度、生态经济与自治边界

下一阶段不应立即扩展更多组件，而应围绕三个更深的问题推进：

1. **群体调度经济学：** 多目标任务如何在质量、成本、时延、公平性和探索性之间动态平衡？
2. **跨领域生态市场：** 能力如何被发现、验证、计价、授权、组合和退出？能力信誉如何防止自我声明与刷分？
3. **自治边界动态调整：** Agent 在何种证据下可以获得更大自主空间？何种风险或失误会触发降权、暂停和人工接管？

V1.5 的核心交付应是生态资源分配模型、能力信誉模型、风险自适应授权模型和群体进化验收框架，而不是继续堆叠服务组件。
