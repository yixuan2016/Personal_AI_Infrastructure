# F0｜跨生态治理章程与成员边界冻结（候选稿）

**文档编号：** AE-V1.8-F0-GOV-001  
**状态：** Candidate / 待各生态 Owner 确认  
**范围：** Agent Ecology 联邦成员、联邦协调平面、能力提供者、任务发起者、数据与资源 Owner  
**日期：** 2026-11-10

## 0. 决策摘要

F0 的目标不是启动跨生态执行，而是先冻结“谁有权决定什么、谁对什么负责、什么权力永远不能委托给 Agent”。在成员身份、根策略、数据权属、授权链、密钥生命周期、退出和事故处置尚未明确之前，不进入真实跨域副作用操作。

**核心原则：联邦没有统一的全局根权力。** 每个生态拥有自己的治理根、身份根、数据权威、业务 Owner 和本地执行门禁。联邦协调平面（FCP）是协作基础设施，不是超级 ADS，不拥有成员生态的生产凭证，也不能替成员生态批准动作。

本文件是 V1.8 候选设计。未获得各生态 Owner 明确签署前，不视为已冻结的组织制度或生产授权。

## 1. 三层治理权力模型

### 1.1 根治理层（Root Governance）

由每个生态自己的授权人/治理机构掌握，非 Agent 可委托权限。包括：
- 根身份信任锚、根密钥、成员域信任建立与撤销；
- 本地安全策略、禁止动作清单、风险阈值与审批门槛；
- 生产凭证签发规则、权限上限、预算上限和数据出域规则；
- 法律/监管义务、审计留存和事故报告责任；
- 哪些自动化可被允许、哪些操作必须人工批准；
- 本地治理 Owner 的任命、替换和问责。

根治理可定义联邦最低互操作要求，但不得把本地最终授权权转交给 FCP 或其他成员生态。

### 1.2 域治理层（Domain Governance）

由数据 Owner、业务 Owner、资源 Owner、安全 Owner 等分别管理：
- 本域 Ontology 扩展和语义映射；
- 数据分类、用途、驻留、留存和删除；
- 业务能力的发布、版本、服务等级和停用；
- 资源配额、租约、成本上限和优先级；
- 本域 Agent 的工具权限、执行范围和监控策略；
- 本域改进候选的 Shadow、Canary、采用与回滚。

域 Owner 只能在根策略允许的范围内委托任务级权限。

### 1.3 任务授权层（Task-scoped Delegation）

本地授权服务根据明确委托契约签发，Agent 仅能在以下边界内执行：
- 主体、受众、目的；
- 动作与资源范围；
- 数据类别和允许用途；
- 有效期、次数/速率/预算上限；
- 适用策略版本、证据摘要和审批收据；
- 撤销条件、审计义务和补偿要求。

**任何委托不得超过签发者自身权限。** 委托链必须可追溯，不能由 Agent 自我签发、自我扩权或通过多跳委托绕过权限上限。

## 2. 不可委托权限与禁止事项

以下权限不授予 Agent、RSI、FCP 或联邦协调器：
1. 修改或替换人类根策略、根身份信任锚和审批规则；
2. 签发、导出、读取或轮换根私钥、生产主密钥和长期生产凭证；
3. 自行增加自身或其他 Agent 的最高权限、预算上限或审批豁免；
4. 将本地 DENY/ABSTAIN 改写为 ALLOW；
5. 代表数据 Owner 批准原始数据、私有记忆、个人信息或受限数据出域；
6. 代表另一生态批准生产写入、资金转移、对外法律承诺或不可逆动作；
7. 删除、篡改或规避审计记录、事故证据、撤销历史；
8. 取消独立评估、绕过 Shadow/Canary、关闭安全监控或回滚保护；
9. 将联邦成员身份、信誉评分或来源生态批准视为其他生态的自动授权；
10. 以模型自评、内部奖励或多数投票取代本地 Owner 的关键审批。

根治理变更只能由相应生态的人类授权主体按其独立变更流程完成；Agent 可提供分析和候选文本，不得执行批准或签发。

## 3. 成员加入条件（Admission）

新成员必须完成双边确认，不采用“目录注册即入盟”：
1. 申请：提交域标识、运营主体、责任联系人、业务目的和拟提供/请求能力。
2. 身份尽调：核验组织/运营者身份、域控制权、工作负载身份方案和联系渠道。
3. 治理声明：提交根策略摘要、不可委托权限、数据分类、风险等级和事故响应流程。
4. 能力审查：提交能力声明、接口 Schema、Ontology 版本、依赖、限制、证据和撤销端点。
5. 契约协商：双方签署成员协议、数据用途条款、责任边界、审计/留存要求和争议处理机制。
6. 受限试点：先只读或低风险、短时、限额、可撤销；不得直接开放生产写权限。
7. 独立验收：双方安全/业务 Owner 分别确认验收证据。
8. 激活：双方治理主体分别签署加入收据；FCP 仅同步成员状态。

任何一方未完成身份、Owner、策略、数据用途或撤销能力核验，状态保持 PENDING 或 HOLD。

## 4. 成员生命周期与退出

正常状态：`PROPOSED → DUE_DILIGENCE → IDENTITY_BOUND → POLICY_CONTRACTED → CAPABILITY_SCOPED → PILOT_LIMITED → ACTIVE`。

异常/终止状态：`HOLD / SUSPENDED / REVOKED / EXITING / EXITED`。

暂停或撤销时：
- 停止新任务、新授权或指定能力；
- 允许按本地策略完成必要安全收尾；
- 撤销短期凭证、能力声明和任务委托；
- 传播撤销事件，接收方在本地执行前重新验证；
- 撤销状态不可达时，高风险动作 HOLD；
- 处理在途任务、租约、补偿、数据留存与审计；
- 发布签名退出收据。

正常退出不得删除依法或按合同必须保留的审计证据，也不得使历史事件来源链失效。

## 5. 身份与密钥生命周期

身份层次：
- Federation Trust Anchor：仅用于联邦协议验证，不构成全局生产授权根；
- Domain Identity：每个生态自己的域身份；
- Workload Identity：Agent、服务和执行实例的短期身份；
- Delegation Credential：绑定目的、动作、资源、范围和期限的任务凭证。

密钥要求：
- 根密钥与生产签名密钥应与普通 Agent 运行环境隔离，优先使用 HSM/受控密钥服务或等效保护；
- 工作负载凭证短时有效并轮换，禁止放入 Prompt、共享环境、日志或普通工件；
- 签名材料声明算法、key_id、有效期、用途和撤销状态；
- 轮换保留有限过渡验证窗口，旧 key 撤销不得被无限延长；
- 疑似泄露时先隔离、撤销和停止新授权，再评估影响；
- FCP 只持有目录/路由服务身份，不持有成员域生产执行凭证。

算法套件、轮换周期、撤销传播 SLA 和 HSM 产品属于待验证/待组织决策事项，不虚构固定数值。

## 6. 跨域授权模型

跨域动作可能需要同时满足：
- 发起域授权（Initiator Grant）；
- 执行域能力/动作授权（Executor Grant）；
- 数据 Owner 授权（DataUseGrant，如涉及数据）；
- 资源 Owner 授权（Resource Grant，如涉及资源）；
- 双方本地 PDP/PEP 实时策略检查；
- 必要的人类审批和独立评估收据。

组合规则：
- 任一必要授权 DENY → 整体 DENY；
- 任一关键授权 ABSTAIN、过期、撤销状态不可达或证据缺失 → HOLD；
- 仅当全部必要条件 ALLOW 且执行前复核仍有效，才可执行。

授权不能仅凭对话、Agent 声明、目录排序或来源生态的成功记录成立。执行域必须在副作用发生前再次验证本地凭证、目的、范围、策略版本、撤销状态和预算。

## 7. R0–R4 风险与审批矩阵

| 等级 | 典型动作 | 默认控制 |
|---|---|---|
| R0 | 公开元数据只读、无敏感数据、无副作用 | 可在已登记能力范围内自动执行并审计 |
| R1 | 低风险、可逆、本地范围内的状态/配置变更 | 限额授权、自动监控、可回滚 |
| R2 | 有界跨域写入、有限资源消耗、可补偿副作用 | 双域本地策略 ALLOW；相关 Owner 授权；按本地门槛人工确认 |
| R3 | 敏感数据、重要业务、外部通信、资金/合同影响、生产变更或较难逆转动作 | 双方指定人类审批；独立评估；分阶段 Canary |
| R4 | 修改根策略/根身份/权限上限、签发根凭证、关闭安全门禁、删除审计等 | Agent 禁止执行；只能走相应生态的人类根治理流程 |

跨域风险不得取平均值。各生态、数据 Owner、资源 Owner 分别评估，整体等级取其中最高等级；有争议或信息不足时 HOLD。R4 不是“提高审批后 Agent 就能做”，而是 Agent 不具备执行权限。

## 8. RACI 与角色责任

角色：
- RG：各生态根治理授权人/治理机构；
- DO：业务域 Owner；
- DATA：数据 Owner；
- RES：资源/预算 Owner；
- SEC：安全、身份和密钥负责人；
- FOP：联邦目录/协调设施运营者；
- LADS：本地 ADS；
- IE：独立评估者；
- HG：关键人工审批/事故指挥角色。

详细 RACI 见 `F0_RACI.csv`。每个成员生态必须指定实际岗位与替补，不得只登记 Agent 名称。

## 9. 事故、暂停与紧急停止

- 每个生态必须有自己的本地停止开关（Local Kill Switch），可停止本域跨域出口、撤销本地授权或阻断本地执行。
- FCP 可以暂停目录发现、路由和新协商，但不能直接关闭成员生态本地业务，也不能代替本地 PEP 撤销生产权限。
- 跨域紧急停止消息是协调请求；接收域按本地安全策略决定并执行隔离动作。
- 事故中先保护人身、数据和生产边界，再保留证据；恢复由各自 Owner 单独批准。
- 一域暂停/退出不应使其他域失去本地自治能力。

## 10. 审计与责任链

每个跨域任务必须可回答：谁发起、谁执行、谁批准、谁提供数据/资源；任务目的、授权范围、策略版本、风险等级和有效期；使用的能力、工件、模型和工具版本；关键状态由哪个生态 Runtime 记录；哪些证据支持完成、拒绝、撤销或回滚；事故中谁负责通知、处置、补偿和复盘。

审计记录需防篡改、来源可验证、最小化收集并按法律/合同留存。联邦目录只保存必要索引和摘要；敏感原始记录留在各自权威域。

## 11. F0 Gate 退出门槛

F0 只有在以下证据全部齐备后才能标记 PASSED：
1. 每个试点生态有经确认的 Domain ID、运营主体和责任联系人；
2. 根治理、域治理和任务授权三层边界有书面确认；
3. 不可委托权限与 R4 禁止动作清单获得双方确认；
4. 业务 Owner、数据 Owner、资源 Owner、安全/身份 Owner 均已指定；
5. 加入、暂停、撤销、退出和在途任务收尾流程获得双方确认；
6. 身份/密钥签发、轮换、泄露、撤销和恢复流程通过桌面演练；
7. 跨域授权契约具备目的、范围、期限、策略版本、撤销和审计字段；
8. 风险分级、审批矩阵和冲突处理规则获得双方确认；
9. 本地 Kill Switch、FCP 停止边界和事故通知流程通过桌面演练；
10. 数据用途、驻留、留存、删除和证据访问条款获得 Data Owner/合规 Owner 确认；
11. 未解决的 Critical/High 风险均有处置或正式接受记录；
12. 双生态试点范围、只读/低风险初始能力、停止条件和回滚负责人明确。
