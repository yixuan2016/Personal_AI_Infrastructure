# 03｜跨生态改进提案与证据契约

## 1. 目标

V1.7 RSI 生成的改进候选可以作为 V1.8 的跨生态交换对象，但必须把“提案可传播”与“改进可采用”彻底分离。来源生态对提案来源负责；接收生态对本地验证和采用负责。

## 2. 提案包结构

每个 FederatedImprovementProposal 至少包含：

- proposal_id、origin_domain、origin_rsi_version；
- target_scope（允许修改对象、禁止修改对象）；
- problem_statement、hypothesis、expected_benefit；
- change_manifest（文件、模型、Prompt、策略或拓扑差异）；
- dependencies、compatibility_range、ontology_version；
- risk_class、reversibility、blast_radius；
- evaluation_plan、baseline、metrics、stop_conditions；
- evidence_bundle_ref、signature、created_at、expires_at；
- license、data_rights、redistribution_constraints。

禁止提案包含明文密钥、生产凭证、未授权数据、个人私密记忆或无法合法再分发的训练材料。

## 3. 证据等级

- E0：自述/未经核实。
- E1：来源可验证，工件和版本可定位。
- E2：可重复的离线评估与基线对照。
- E3：独立评估者复核，包含负面结果和局限。
- E4：在接收生态的 Shadow/Canary 中验证，具备本地审批收据。

证据等级不是安全等级，也不替代风险评估。E4 仅适用于该接收生态、该版本和该场景。

## 4. 本地采用状态机

`RECEIVED → QUARANTINED → STATIC_REVIEW → SANDBOXED → INDEPENDENTLY_EVALUATED → SHADOW → CANARY → ADOPTED`

分支状态：`REJECTED / HOLD / EXPIRED / REVOKED / ROLLED_BACK`

任何阶段都可以退回 HOLD。候选包必须固定内容摘要，评估前后内容变化即视为新候选。

## 5. 独立评估要求

- 评估者与候选生成者分离。
- 至少包含基线对照、消融或反事实比较。
- 报告成功率、成本、延迟、失败模式、安全违规和回滚结果。
- 评估环境、数据版本、随机种子、模型版本和工具版本可追溯。
- 结果需包括“不适用条件”和“未测试范围”。
- 接收生态必须执行本地 Shadow；高风险动作不得跳过人工审批和 Canary。

## 6. 撤销与传播

来源生态撤销候选后，联邦目录必须发布撤销事件；接收生态查询撤销状态并执行本地影响评估。来源方不能单方面强制删除接收方依法保留的审计记录，但可以要求停止继续分发、停止使用受许可约束的材料，并按契约触发回滚/停用评估。
