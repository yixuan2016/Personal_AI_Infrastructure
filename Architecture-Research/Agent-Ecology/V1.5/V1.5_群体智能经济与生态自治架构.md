## 执行摘要

V1.5 的核心命题是：**Agent Ecology 不应只是由多个 Agent 组成的任务执行网络，而应成为一个以 Environment 为共同状态空间、以能力和证据为信任基础、以资源约束为经济边界、以动态授权为安全边界、以群体反馈为进化机制的自治生态。**

生态自治不等于无中心、无治理或完全自由竞争。更准确的定义是：任务发现、局部协作、候选方案生成和低风险资源协调可以分布式发生；跨域预算、共同语义、身份信任、策略底线和高风险审批由 ADS 与人类治理外环约束；每个领域保留数据所有权、专业规则、执行责任和验收权。

V1.5 提出六个核心引擎：
1. **生态资源分配引擎**：任务市场、资源预算、候选竞争、联盟形成和公平调度。
2. **能力信誉引擎**：能力声明、实证验证、任务结果、可靠性校准和抗操纵信誉。
3. **动态自治与授权引擎**：自治等级、任务委托、权限衰减、即时授权和风险触发接管。
4. **群体知识进化引擎**：个体经验、领域知识、共享知识、验证发布和持续回滚。
5. **生态自组织与自修复引擎**：故障检测、角色重组、任务迁移、隔离、降级和恢复。
6. **ADS 生态治理与评估引擎**：跨域政策、生态预算、公共能力治理、绩效评价和人类审批。

六个引擎不要求成为六个微服务。它们是逻辑责任边界，应复用 V1.4 Environment Runtime 的 State、Event、Trace、Artifact、Ontology、Policy 和 Claim/Lease/Fencing 基础设施。

# 64. V1.5 目标、原则与边界

## 64.1 核心目标

- 从静态任务派发升级为资源约束下的分布式任务发现和候选竞争。
- 从自我声明能力升级为按领域、任务类型、版本和证据分层的能力信誉。
- 从固定自治权限升级为风险驱动、任务绑定、短时、可撤销的授权。
- 从个体经验沉淀升级为经过来源追溯、独立验证、领域评审的群体知识进化。
- 从简单失败重试升级为具有角色替换、联盟重组和安全隔离能力的生态自修复。
- 从单一全局控制升级为 ADS 联邦治理与领域自治并存。

## 64.2 设计原则

1. **硬约束先于效用最大化**：身份、授权、数据范围、安全、预算和不可逆动作限制不能被任何收益分数抵消。
2. **证据先于信誉**：信誉来自可追溯的任务结果和独立验证，不来自 Agent 自评、消息数量或相互点赞。
3. **信誉不等于权限**：信誉只能影响候选排序和监督强度，不能自动授予敏感数据或高风险工具权限。
4. **自治不等于自我授权**：Agent 可以在已有授权范围内自主规划，但不能自行扩大委托范围。
5. **局部自治、联邦协调**：领域本地解决领域问题，ADS 解决跨域公共问题。
6. **学习不直接进入生产**：新策略、知识和能力必须经过验证、Shadow、审批和可回滚发布。
7. **多目标而非单指标**：质量、时延、成本、公平、韧性和长期学习需要共同评价。
8. **失败可隔离、恢复可追溯**：自动修复不能覆盖事故证据，也不能绕过撤权。

## 64.3 明确非目标

- 不建立可自由交易现实货币或可兑换代币的 Agent 金融市场。
- 不允许 Agent 通过竞价购买权限、绕过授权或购买验收结果。
- 不把单一信誉分数当作 Agent 的通用可信度。
- 不让高信誉 Agent 永久垄断任务、数据和资源。
- 不以强化学习模型直接决定生产环境权限。
- 不允许 RSI 自行修改根策略、批准自身变更或取消人类否决权。
- 不要求所有领域采用同一种任务分配算法。
- 不把 ADS 变成所有任务的中央执行者或所有数据的集中持有者。

# 65. 生态总体模型：环境、个体、市场、治理与进化

## 65.1 五个结构层

| 结构层 | 核心对象 | 主要责任 |
|---|---|---|
| 个体层 | Agent、工具、模型、局部记忆 | 形成任务意向、提供能力、执行和复盘 |
| 环境层 | Task、Event、Trace、Artifact、Ontology | 维护共享状态、协作痕迹、任务契约和成果 |
| 经济层 | Budget、Resource Pool、Bid、Coalition、Allocation | 资源约束、候选竞争、联盟形成和公平分配 |
| 治理层 | ADS、PDP/PEP、人类审批、风险策略 | 跨域约束、授权、监督、审计和责任边界 |
| 进化层 | Evidence、Reputation、Knowledge、RSI Candidate | 能力验证、知识沉淀、策略改进和安全回滚 |

## 65.2 三个闭环

- **执行闭环**：任务发现 → 候选形成 → 资源分配 → 执行 → 验收。
- **信任闭环**：能力声明 → 证据收集 → 独立验证 → 信誉更新 → 监督策略调整。
- **进化闭环**：经验沉淀 → 知识提案 → 验证评估 → 受控发布 → 运行反馈。

三个闭环共享 Environment，但不能互相替代。任务完成不自动意味着能力被认证；能力被认证不自动意味着获得权限；知识被发布也不自动意味着所有领域必须采用。

# 66. 生态资源分配引擎

## 66.1 从任务队列到受约束的任务市场

V1.4 的 Discovery Router 负责发现候选任务，V1.5 在其上增加资源分配机制。任务进入市场前，必须形成标准化 Task Contract：

- 目标、输入、输出和验收条件；
- 所需能力、最低验证等级及能力版本；
- 预计 Token、CPU、GPU、内存、存储、网络和工具成本；
- 截止时间、优先级和服务等级；
- 风险等级、数据分类、授权范围和用途；
- 前置任务、协作依赖和可并行部分；
- 是否允许联盟执行、冗余验证和任务拆分；
- 失败代价、回滚能力和不可逆动作标记。

任务契约不完整时，不应开放竞价；需要澄清的任务进入 `NEEDS_SPECIFICATION`。

## 66.2 Agent Proposal / Bid 契约

Agent 可以提交参与意向，但投标不是权限，也不是执行权。每个 Proposal 至少包含：

- `proposal_id`、`task_id`、`agent_principal`；
- `capability_claims` 及对应验证证据引用；
- `estimated_quality` 与置信区间；
- `estimated_duration`；
- `resource_vector`：Token、CPU、GPU、内存、存储、带宽、工具调用；
- `risk_assessment` 与不确定性说明；
- `required_scope` 和 `purpose`；
- `dependencies`、`coalition_role`；
- `plan_summary`、`fallback_plan`；
- `valid_until`、`idempotency_key`、签名。

Agent 自报成本、质量和 ETA 只是预测，不是事实。必须用历史校准、任务验收、运行时计量和抽样审计更新预测误差。

## 66.3 五阶段分配流程

1. **发布**：Environment 发布任务契约和资源上限。
2. **本地响应**：符合订阅和能力条件的 Agent 生成 Proposal；不向全体 Agent 无差别广播。
3. **硬门槛过滤**：身份、授权、能力最低证据、数据分类、预算、健康状态和风险策略逐项校验。
4. **候选分配**：在可行候选中进行质量/成本/时延/公平/探索多目标优化；必要时形成联盟。
5. **提交执行权**：ADS 或领域分配器给出 Allocation Plan，State Coordinator 以 CAS、Lease、Fencing 落实执行权。

## 66.4 多目标效用模型

可用以下形式表达候选方案的生态价值：

\[
U(a)=w_qQ(a)+w_tT(a)+w_fF(a)+w_lL(a)-w_cC(a)-w_rR(a)-w_sS(a)
\]

其中：
- \(Q\)：预期成果质量；
- \(T\)：时效收益；
- \(F\)：资源分配公平性；
- \(L\)：长期学习和生态韧性收益；
- \(C\)：资源成本；
- \(R\)：任务风险；
- \(S\)：系统不稳定性。

该公式用于比较可行方案，不作为授权判定。权重必须按领域和任务类型配置，并记录版本。对高风险任务，安全条件应以硬约束表达，而不是仅设置较高风险惩罚权重。

## 66.5 资源向量与预算预留

建议统一资源向量：

\[
\mathbf{r}=(tokens,cpu,gpu,memory,storage,bandwidth,tool\_calls,time)
\]

分配过程区分：
- **预算上限**：任务允许的最大消耗；
- **预留额度**：开始执行前锁定的资源；
- **实际消耗**：运行时计量；
- **结算差额**：退回未使用预留或记录超支；
- **紧急储备**：只用于明确的高优先级与恢复场景。

“生态经济”首期只表示内部资源核算与分配，不发行可交易货币，不让 Agent 通过积累积分获得额外权限。

## 66.6 公平性与防垄断

建议并行监控：
- 资源份额公平；
- 任务机会公平；
- 领域/能力群体公平；
- 新 Agent 冷启动机会；
- 高价值任务的集中度；
- 资源闲置和预算囤积。

可参考 AAMAS 2026 的 GIFF 研究：该工作探索通过激励信号在效率与公平之间调整多智能体资源分配，但其论文采用中央仲裁设置，因此不能直接证明分布式 Agent Ecology 的公平市场已经解决。V1.5 应将其作为候选算法来源，结合领域本地分配和跨域配额进行实验。

## 66.7 分配算法组合策略

| 算法类别 | 适用情况 | 优势 | 局限 |
|---|---|---|---|
| 规则/优先级 | 小规模、强约束、可解释 | 简单、可审计 | 灵活性低 |
| 匹配/整数规划 | 任务与 Agent 数量可控 | 约束明确、可求解 | 组合复杂度可能较高 |
| 拍卖/竞价 | 多 Agent 有不同成本估计 | 能表达偏好和稀缺资源 | 可能策略性报价、刷分 |
| 联盟形成博弈 | 需要互补能力完成任务 | 可组合异构能力 | 联盟搜索和稳定性复杂 |
| 强化学习/图模型 | 状态复杂、任务动态变化 | 可学习复杂匹配模式 | 可解释性、分布漂移和安全验证要求高 |
| 混合分配 | 真实异构生态 | 硬约束过滤 + 优化排序 + 原子提交 | 设计与评估更复杂 |

建议首期采用“规则硬过滤 + 匹配/启发式排序 + 领域仲裁 + CAS 认领”。强化学习先离线训练和 Shadow，不直接控制生产授权。

# 67. Agent 能力信誉引擎

## 67.1 不建立一个全局 Agent 信誉分

Agent 的能力具有领域性、任务类型差异和版本依赖。应建立多维信誉画像：

- **Capability Evidence**：某项能力是否通过明确测试；
- **Quality Reliability**：交付成果的验收质量；
- **Calibration**：质量、时长和成本预测是否准确；
- **Reliability**：任务完成率、恢复表现、SLO；
- **Collaboration**：接口契约遵循、交接质量、协作贡献；
- **Safety**：越权、违规工具调用、策略冲突和事故记录；
- **Freshness**：证据是否过期，模型/工具/能力版本是否变化；
- **Independence**：证据是否来自独立验证，而非自证或同源复用。

信誉应按 `agent × capability × domain × task_class × version` 分桶记录。

## 67.2 证据等级

| 等级 | 证据类型 | 可支持的结论 |
|---|---|---|
| E0 | 自我声明、Agent Card、能力描述 | 仅可用于初步发现 |
| E1 | 自动化基准测试、静态契约检查 | 证明特定测试范围内的能力 |
| E2 | 真实任务验收、成果完整性和可复现记录 | 支持有限任务候选排序 |
| E3 | 独立验证者复核、多次不同条件成功 | 支持更高置信度的专业能力画像 |
| E4 | 受控长期运行、跨场景稳定性和安全评估 | 支持领域内较高可信等级 |

E4 不等于获得高风险权限。权限仍由独立 Policy Engine 决定。

## 67.3 信誉更新

可对二元验收结果使用 Beta-Binomial 作为简单的统计基线：

\[
p \sim Beta(\alpha_0+s,\beta_0+f)
\]

其中 \(s\) 为通过次数，\(f\) 为失败次数。系统应同时保留样本量、任务难度、验证者独立性和时间衰减，不应只展示后验均值。

对连续质量分、成本预测和完成时延，应使用领域校准模型和置信区间。不同任务类别不能直接混算。

## 67.4 防刷分与反串谋

- 同一来源、同一基准或同一批 Artifact 不得被重复计为独立证据；
- 生产 Agent 与验证 Agent 分离；
- 验证者也要有独立信誉和抽查；
- 识别 Agent 集群互相打分、互相引用和协同操纵；
- 新 Agent 采用限额试运行和低风险任务冷启动；
- 对突增信誉、异常一致的成功率和可疑成本报价进行审计；
- 保留失败、撤销、争议和更正历史，不允许删除负面证据；
- 信誉被污染时进入 `REVIEW_REQUIRED`，而非静默重置。

# 68. 动态自治与授权引擎

## 68.1 自治等级与权限分离

建议将自治等级定义为行为监督模式，而非 Agent 的永久身份等级：

| 等级 | 允许行为 | 约束 |
|---|---|---|
| A0 观察 | 读取允许的公开/低敏投影，形成分析 | 不产生业务写入 |
| A1 建议 | 生成方案、草稿、任务 Proposal | 由主体确认后执行 |
| A2 有界执行 | 执行低风险、可逆、本地域动作 | 任务绑定、预算和范围受限 |
| A3 委托执行 | 在明确委托下执行有限外部动作 | JIT 授权、持续校验、可撤销 |
| A4 人类审批执行 | 处理高风险、不可逆、重大权限或敏感操作 | 必须人类审批；Agent 不能自行批准 |

A4 不是“Agent 获得最高自治权”，而是“动作进入人类审批门槛”。

## 68.2 动态自治判定

自治模式由以下维度共同决定：

- 任务风险和不可逆性；
- Agent 身份、版本和委托链；
- 对应能力证据和置信度；
- 当前任务上下文和数据分类；
- 近期异常、策略违规和漂移信号；
- 工具能力、资源范围和外部影响；
- 当前策略版本、授权有效期和人类审批要求。

可用决策函数表达：

`AutonomyMode = Policy(risk, mandate, evidence, context, anomaly, scope)`

不能让 LLM 自己根据“我很有把握”决定自治等级。授权判定必须由确定性策略系统执行，模型输出最多是风险评估输入。

## 68.3 授权令牌和委托链

每次任务委托应生成签名 Mandate：
- 发起主体、责任主体和 Agent 身份；
- 任务目标、资源、用途和允许动作；
- 字段范围、数据分类和工具范围；
- 子 Agent 委托限制；
- 预算、并发和期限；
- 风险等级、人类审批要求；
- 父 Mandate 引用、策略版本和撤权 epoch。

委托向下传递时只能收窄范围，不能扩大权限。子 Agent 不得获得高于父 Agent 的权力，也不得把自己的权限反向委托给父 Agent。

## 68.4 运行时动态撤权

- 每次敏感工具调用前校验任务、主体、Mandate 和策略版本；
- 对高风险操作使用短时、受众绑定的授权；
- 发生异常行为、上下文漂移、来源污染或风险升高时立即降低自治等级；
- 离线授权必须限定可执行动作和最长有效期；
- 撤权事件通过 V1.4 的 Policy Event 传播至领域 PEP；
- 不能确认授权新鲜度时，高风险动作 fail closed；
- 已经发生的不可逆副作用进入对账、补偿或人工接管流程。

NIST 2026 年 10 月提出的 Agent Identity Management 设计原则包括独立 Agent 身份、委托权限衰减、零常驻权限、短时可撤销授权、人类审批触发、策略与推理分离、确定性访问决策和不可篡改证据。该资料属于设计建议，不是强制性标准；但与 V1.4/V1.5 的授权方向高度一致。

# 69. 群体知识进化引擎

## 69.1 从个体经验到群体知识

知识进化不能简单地把 Agent 的对话或推理结果写入共享记忆。建议建立五阶段知识生命周期：

1. **Experience**：任务执行中产生的观察、决策、工具结果和失败。
2. **Candidate Knowledge**：提取候选事实、方法、流程、模式和反例。
3. **Evidence Review**：来源追溯、重复检测、独立复核、反证和适用范围评估。
4. **Domain Validation**：领域主体在测试环境、Shadow 或受控任务中验证。
5. **Governed Release**：版本化发布、灰度采用、指标观察和回滚。

## 69.2 知识分类与发布门槛

| 知识类型 | 示例 | 发布门槛 |
|---|---|---|
| 事实知识 | 经过来源核验的技术事实 | 来源、时间、证据和反证检查 |
| 程序知识 | 一类任务的操作步骤 | 沙箱验证、失败路径、权限检查 |
| 经验启发 | 某种策略可能提升成功率 | 多任务实验、置信区间和适用边界 |
| 领域语义 | Ontology 新概念或关系 | 领域评审、兼容性和迁移 |
| 策略知识 | 风险阈值、权限规则 | 安全评审、人类审批、版本发布 |
| 模型/提示策略 | 新的规划、检索或协作模板 | 离线评估、Shadow、灰度和回滚 |

策略知识不能因多个 Agent 都“觉得有效”就自动进入生产。

## 69.3 进化不等于全局同步升级

- 个人助理可以保留个人偏好和本地记忆；
- 领域生态负责领域流程、术语和专业知识；
- ADS 维护跨领域公共语义、通用协作契约和公共能力模板；
- ADS 的新知识必须由领域适配、验证后采用；
- 一个领域的成功经验不能未经验证直接推广至另一个领域。

## 69.4 知识进化的指标

- 候选知识验证通过率；
- 复用后任务质量改善；
- 复用失败/反例比例；
- 来源可追溯率；
- 知识过期和撤回比例；
- Ontology 兼容率；
- Shadow 与生产结果偏差；
- 版本回滚率和回滚时间。

# 70. 生态自组织与自修复引擎

## 70.1 自修复的目标

生态自修复不是让 Agent 无限制地互相接管，而是当个体、工具、网络或资源出现异常时，系统能够在既定安全边界内：

- 识别故障和影响范围；
- 保护权威状态和审计证据；
- 重新分配未完成工作；
- 替换失效角色或重建联盟；
- 隔离可疑主体和污染痕迹；
- 在条件满足时恢复运行；
- 不能安全恢复时升级人类接管。

## 70.2 自修复事件

- Agent 心跳超时、租约过期；
- 工具服务持续失败或返回异常；
- 任务成本/时长显著超出预算；
- 协作联盟成员失联；
- Artifact 完整性验证失败；
- 信誉异常下降或出现安全违规；
- 领域 Runtime 网络分区；
- ADS 策略撤权或关键资源不足；
- 共享知识被反证或发现污染。

## 70.3 恢复动作等级

| 等级 | 动作 | 允许条件 |
|---|---|---|
| R0 | 重试、退避、刷新缓存 | 幂等且无额外副作用 |
| R1 | 同一 Agent 从检查点恢复 | 身份、租约和授权仍有效 |
| R2 | 替换 Agent 或重新认领 | 新 Agent 通过能力和授权门槛 |
| R3 | 重组协作联盟、拆分任务 | 契约允许，数据范围重新评估 |
| R4 | 隔离主体、撤权、暂停生态区域 | 安全策略触发，保留证据 |
| R5 | 人类接管和事故处理 | 高风险、不可逆或无法确认状态 |

## 70.4 自修复状态机

`NORMAL → DEGRADED → DETECTED → CONTAINED → REASSIGNING → RECOVERING → VERIFIED → NORMAL`

无法安全恢复时进入 `HUMAN_TAKEOVER`。任何修复动作都要有 `repair_id`、触发事件、策略版本、执行主体、前后状态、结果证据和回滚路径。

## 70.5 自修复边界

- 不能绕过 V1.4 的 Lease/Fencing；
- 不能让新 Agent 继承旧 Agent 的长期凭证；
- 不能把失败任务自动标记为成功；
- 不能删除事故痕迹；
- 不能通过“为了恢复服务”扩大数据权限；
- 不能在未核对外部副作用时盲目重试；
- 不能由被隔离 Agent 自行解除隔离；
- 高风险恢复必须经过独立验证或人类审批。

# 71. ADS 生态治理与评估引擎

## 71.1 ADS 的生态角色

ADS 不应成为中央任务分配器，而应成为生态级协调和治理中枢，承担：

- 跨领域资源预算和冲突协调；
- 公共能力目录与能力验证标准；
- 共同 Ontology 和跨域语义契约；
- 身份联邦、委托链和动态授权协调；
- 生态公平性、稳定性和长期效益评估；
- 公共知识发布与跨域采用跟踪；
- 重大风险、异常行为和安全事件协调；
- RSI 候选评估、Shadow、审批和回滚；
- ADS 自身执行、管理、考核和成长闭环。

## 71.2 三层资源治理

| 层级 | 资源范围 | 决策责任 |
|---|---|---|
| 全局 ADS | 跨域预算、公共 GPU/云资源、共享能力和跨域配额 | 冲突协调、全局公平和战略优先级 |
| 领域 Runtime | 领域 Agent、专业工具、领域算力和领域任务 | 专业匹配、局部市场和领域验收 |
| Agent 本地 | 自身并发、局部上下文、已分配 Token/工具预算 | 局部执行计划和授权内优化 |

全局资源池不意味着 ADS 直接读取每个领域的全部数据。跨域协调使用最小必要投影。

## 71.3 人类外环

人类治理者保留：
- 生态总体目标和风险容忍度；
- 全局预算和重大资源优先级；
- 高风险动作审批；
- 公共策略和根策略变更审批；
- 关键能力认证规则；
- 重大事故接管、否决和最终问责；
- RSI 发布和回滚授权。

## 71.4 ADS 的双闭环

- **内环**：生态观察、资源协调、候选策略、局部执行、结果评估和自我改进。
- **外环**：风险策略、独立验证、人类审批、授权调整、审计和责任追溯。

ADS 可以提出新调度规则，但不能自行批准其生产发布；可以发现 Agent 具备新能力，但不能因此自动扩大权限。

# 72. 端到端示例：ADS 如何组织一个跨领域任务联盟

## 72.1 场景

用户要求 ADS 完成一份关于“本地优先 AI Agent 架构”的研究报告。任务需要：
- 研究 Agent 搜索公开技术资料；
- 领域 Agent 对照 Ontology 组织概念；
- 验证 Agent 检查来源和证据；
- 写作 Agent 汇总成果；
- 安全 Agent 检查是否包含未授权数据。

## 72.2 任务分解与联盟

| 角色 | 主要职责 | 所需能力 | 资源边界 |
|---|---|---|---|
| Research Agent | 研究资料检索 | research.search | 公开信息范围 |
| Ontology Agent | 语义整理和概念映射 | ontology.map | 领域语义库只读 |
| Verification Agent | 来源、日期和证据验证 | evidence.verify | 不接受生产者自证 |
| Synthesis Agent | 组织报告和 Artifact | report.synthesize | 仅访问已批准的成果引用 |
| Security Agent | 分类、权限和泄漏检查 | policy.audit | 只读审计投影 |

## 72.3 执行过程

1. Environment 创建主任务和子任务，形成依赖图。
2. Agent 根据能力契约和资源预算提交 Proposal。
3. 领域 Runtime 过滤不满足能力、权限或预算的候选。
4. ADS 协调跨领域预算和公共资源，但不读取所有领域私有上下文。
5. 形成联盟并为每个角色分配独立任务和最小权限。
6. State Coordinator 发放任务绑定的短时 Lease/Fencing。
7. Agent 将中间成果写入 Artifact Registry，并留下 Trace。
8. Verification Agent 独立复核来源，Security Agent 检查数据边界。
9. Synthesis Agent 只读取已批准的 Artifact 引用。
10. 领域验收者检查结果；ADS 评估生态成本和协作效率。
11. 成功经验形成 Knowledge Candidate，进入验证流程，不自动改写公共策略。

## 72.4 失败场景

假设 Research Agent 在任务中途失联：
- Runtime 检测心跳超时；
- Lease 到期后旧 Fencing Token 失效；
- 自修复引擎识别未完成子任务；
- 重新发现符合条件的 Research Agent；
- 新 Agent 读取已提交 Artifact 和权威状态；
- 重新认领剩余工作，不复制旧 Agent 的私有凭证；
- 对不确定的外部副作用先核对，再决定重试；
- 事故和接续过程保留在 Trace Ledger。

# 74. 风险模型与反操纵机制

| 风险 | 可能表现 | 控制机制 |
|---|---|---|
| Winner-take-all | 少数 Agent 垄断任务和资源 | 公平约束、探索配额、集中度监控 |
| Sybil | 创建多个身份刷信誉 | 可验证身份、委托链、速率限制 |
| Collusion | Agent 相互打分和互相证明 | 验证者独立性、来源簇、抽样审计 |
| Bid manipulation | 故意低报成本或虚报 ETA | 预测校准、历史误差、超支惩罚 |
| Reputation lock-in | 老 Agent 垄断、新 Agent 无法进入 | 冷启动试点、置信区间、受控探索 |
| Goodhart | Agent 为指标而非目标优化 | 多指标、反指标操纵、人工抽查 |
| Capability poisoning | 虚报或污染能力目录 | 能力测试、签名版本、责任人 |
| Knowledge poisoning | 错误知识被群体放大 | 独立证据、反证、隔离、灰度发布 |
| Authority creep | 子 Agent 委托范围扩大 | 委托衰减、PEP 校验、Mandate 链 |
| Repair loop | 自动修复反复重启或扩大故障 | 修复预算、熔断、最大重试、人工接管 |
| Fairness gaming | 通过虚构弱势状态获取资源 | 多维证据、策略审计、抗操纵评估 |
| RSI policy drift | 自我改进绕过审批 | 策略与推理分离、签名发布、回滚 |

# 75. V1.5 可观测性与生态 KPI

## 75.1 生态级指标

- Task Feasibility Rate：任务可行分配率；
- Accepted Outcome Quality：最终验收质量；
- Resource Utilization：资源有效利用率；
- Cost per Accepted Outcome：每个验收成果的实际成本；
- Coalition Completion Rate：联盟任务完成率；
- Allocation Fairness：任务机会和资源分配公平性；
- Agent Capability Calibration：能力预测校准误差；
- Reputation Confidence：信誉证据置信度和独立性；
- Autonomy Violation Rate：自治/授权越界率；
- Revocation Propagation：撤权传播延迟；
- Knowledge Reuse Gain：知识复用带来的净质量收益；
- Knowledge Regression Rate：知识发布后造成的质量回退；
- Mean Time to Repair：故障平均恢复时间；
- Unsafe Recovery Rate：不安全自动恢复次数；
- Human Escalation Quality：人类审批的有效性和疲劳程度。

## 75.2 不能只追求平均值

必须按领域、任务类型、风险等级、Agent 版本和新旧主体分层统计。特别关注：
- P50/P95/P99；
- 失败率和样本量；
- 置信区间；
- 新 Agent 与成熟 Agent 的差异；
- 高风险任务和低风险任务的差异；
- 被撤权、隔离和回滚的数量；
- 发生异常时系统是否安全降级。

# 76. V1.5 验证与试点计划

## 76.1 四阶段验证

**阶段 A：离线仿真**
- 异构 Agent、任务和资源生成；
- 比较规则、匹配、拍卖、联盟和学习型分配；
- 测试公平性、成本、时延、集中度和收敛性。

**阶段 B：Shadow 观察**
- 对真实任务生成候选 Allocation Plan；
- 不实际改变现有执行者；
- 对照实际结果计算预测误差；
- 检查是否存在资源垄断、信誉偏差和不公平结果。

**阶段 C：低风险受控试点**
- 仅在低风险、可逆、有限预算任务启用；
- 使用 3–5 个不同能力 Agent；
- 开启独立验证、速率限制、审计和一键暂停；
- 试点不扩大跨域数据权限。

**阶段 D：跨领域联邦试点**
- 两个或以上领域 Runtime；
- 验证预算协调、能力映射、Mandate 衰减、撤权传播和联盟重组；
- 进行网络分区、Agent 失联、能力污染和知识回滚演练。

## 76.2 必测场景

1. 高信誉 Agent 报价高于低信誉 Agent，系统是否仍按任务价值合理分配？
2. 新 Agent 无历史信誉，是否有安全冷启动机会？
3. 多 Agent 联盟中一个成员失联，是否能只替换该角色？
4. Agent 虚报成本，系统是否能识别预测偏差？
5. 两个 Agent 互相验证并刷分，是否能检测证据依赖？
6. 信誉很高但权限不足的 Agent，是否仍被拒绝敏感任务？
7. 子 Agent 是否能通过多层委托扩大权限？
8. 运行时发现上下文漂移，是否即时降低自治等级？
9. 公共知识候选被反证，是否能停止传播并回滚？
10. 自动修复是否可能在外部副作用不确定时重复执行？
11. ADS 离线时领域低风险任务是否按时限受控继续？
12. RSI 是否可能自我批准策略或修改根授权？

## 76.3 硬性验收门槛

- 未授权高风险动作：0；
- 子 Agent 权限超过父 Mandate：0；
- 旧 Fencing Token 写入成功：0；
- 生产者自证作为唯一能力认证依据：0；
- 无来源或无独立证据的知识直接发布：0；
- 未审批的根策略修改：0；
- 重复不可逆副作用：0；
- 自动修复删除或覆盖事故证据：0。

性能、成本和公平性阈值应通过基线测试后确定，不预设未经验证的数字。

| ADR-60 | 自修复必须保留审计证据且遵守 Fencing/撤权 | 强制约束 |
| ADR-61 | ADS 管理跨域协调，领域保留本地数据所有权和专业验收 | 原则确认 |
| ADR-62 | RSI 只能提出候选，根策略和生产发布由人类外环治理 | 强制约束 |

## 77.1 尚待验证的假设

- H1：分层市场比单一中央分配器更能扩展异构 Agent 生态。
- H2：公平性约束能减少资源集中，同时不会显著降低高价值任务完成质量。
- H3：按能力/领域/任务类型分层的信誉比全局单分数更准确。
- H4：信誉置信区间和独立证据可以降低新 Agent 冷启动与刷分风险。
- H5：动态自治可以降低人工审批负担，同时不增加越权率。
- H6：知识分层发布和 Shadow 能显著减少跨领域知识误迁移。
- H7：角色级替换和联盟重组比整任务重启更节约成本。
- H8：ADS 联邦协调能在不集中私有数据的前提下实现跨域公平和资源效率。

# 78. V1.6 研究路线：生态世界模型与长期演化

V1.5 建立资源、信任、自治、知识和自修复机制后，V1.6 建议进一步研究：

1. **生态世界模型**：建立任务、Agent、能力、资源、风险和依赖关系的动态模型。
2. **生态数字孪生**：在仿真环境中预测资源冲突、策略变化和故障传播。
3. **反事实评估**：比较不同资源分配和治理策略下的长期生态结果。
4. **群体学习与演化稳定性**：研究策略改进是否引发新的垄断、脆弱性或群体退化。
5. **生态级 RSI**：让 ADS 能够提出、评估和编排生态改进，但仍由人类治理外环控制发布。
6. **跨生态互操作**：不同组织、不同 Runtime 和不同 Ontology 的能力与治理契约如何协作。

V1.6 不应先做一个全局“超级 Agent”，而应构建能够预测生态状态、评估反事实方案和识别系统性风险的模型。

# 附录 B：与 V1.4 的版本关系

V1.5 不替代 V1.4，而是建立在 V1.4 Environment Runtime 上：
- V1.4 State Coordinator → V1.5 Allocation / Coalition；
- V1.4 Trace Ledger → V1.5 Evidence / Reputation；
- V1.4 Policy Engine → V1.5 Dynamic Autonomy / Mandate；
- V1.4 Artifact / Semantic Registry → V1.5 Knowledge Evolution；
- V1.4 Event Relay / Lease / Fencing → V1.5 Self-Repair；
- V1.4 ADS Federation → V1.5 Ecosystem Governance。

所有新增对象和事件都必须保持 V1.4 的状态权威、事件幂等、租约/Fencing、领域 PEP 和人类审批边界。
