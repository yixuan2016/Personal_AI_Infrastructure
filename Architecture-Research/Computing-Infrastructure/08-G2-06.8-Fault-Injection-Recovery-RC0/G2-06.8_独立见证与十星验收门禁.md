# G2-06.8｜独立见证与十星验收门禁

**状态：** RC0 验收框架候选  
**目标：** 确保双区域十星的故障恢复结论可复核、可重复、可追责  
**原则：** 执行者不独立验收自己；模拟结果不替代现场证据

## 1. 验收对象与责任分离

| 角色 | 职责 | 不得越权 |
|---|---|---|
| 架构 Owner | 确认架构不变量、状态机与阶段门 | 不替代设备/数据 Owner 签署事实 |
| ADS/Governance Owner | 共同语义、信任、策略与撤销治理 | 不签发站点 Lease |
| SCO Owner | 全局交易、Saga、对账与投影 | 不改写站点原始事实 |
| RCP/Region Owner | 区域目录、协调、区域 epoch 与恢复 | 不替站点 Owner Commit |
| Site Owner/LCP Owner | 本地执行、Reservation、Lease、TaskRun 和站点恢复 | 不扩大数据用途或其他 Owner 权限 |
| Compute/GPU/Storage/Network/Facility Owner | 对专业资源状态和恢复作权威确认 | 不代表其他资源域签署 |
| Data Owner / PDP/PEP Owner | 数据用途、地域、留存、披露和访问判定 | 不将目录可见性视为访问许可 |
| 安全与审计 Owner | 安全评审、证据完整性、独立见证 | 不代替业务 Owner 决定业务验收 |
| 演练执行团队 | 按批准方案执行故障注入和记录 | 不自行修改通过标准 |
| 独立见证团队 | 重放、复核、抽查证据和签署见证报告 | 不参与被见证场景的唯一执行控制 |

## 2. 五道阶段门

### Gate 0｜方案与风险批准

- 故障场景、范围、影响、注入方式和停止条件明确。
- 站点、网络、数据、设施、安全 Owner 已批准。
- 测试数据、凭证、网络隔离和回滚方案准备完毕。
- 观察者、注入者、恢复负责人和独立见证人已指定。

未满足则不得开始注入。

### Gate 1｜单星基线与本地自治

- 单星 CPU/GPU/存储/网络/能源基线已测量。
- 本地 Lease、PDP/PEP、设施联锁和任务恢复边界清晰。
- Site LCP 在区域协调不可用时按授权范围自治。
- 站点 Owner 原始事实和证据可回读。

### Gate 2｜区域内五星故障遏制

- 区域目录陈旧、RCP Leader 切换和事件缺口通过。
- 五星资源 Owner Prepare/Commit/Stop/Release 事实可追溯。
- 区域网络、存储和控制面故障不造成跨星权限扩张。
- P0/P1 关键控制流不被 P3 遥测洪峰阻塞。

### Gate 3｜双区域十星联邦恢复

- WAN 分区、运营商切换、跨区域交易 Unknown 和 Saga 恢复通过。
- Owner epoch、region_epoch 和 Lease FencingToken 分离有效。
- 撤销传播、DataUseGrant 复核和数据驻留边界通过。
- 两套独立实现对相同契约和故障场景产生一致的关键业务状态。
- 独立见证能从原始回执、事件和证据重建关键状态。

### Gate 4｜运营放行

- 所有 P0/F0 和 P1/F1 场景通过，或有正式风险接受与限制措施。
- 所有失败项已关闭、明确延期或进入有期限的人工风险接受。
- RTO/RPO、撤销窗口、容量和网络 SLO 有真实测量与 Owner 签署。
- 值班、告警、演练、事故升级、回滚和退出流程可执行。
- 版本、配置、Schema、Ontology、策略和证据清单完整。

Gate 4 通过前，不得宣称“十星生产级可用”或“联邦恢复已验收”。

## 3. 独立实现互操作要求

至少两套独立实现参与关键契约验证。独立性不仅是不同进程或不同容器，还应核验：

- 独立代码/运行时或不同实现团队；
- 独立解析与 Schema 验证路径；
- 独立状态机与幂等处理；
- 独立事件消费、快照恢复和证据验证；
- 对相同输入、故障注入和 Owner 回执产生一致的关键状态；
- 对未知字段、未知枚举、签名失败、撤销缺口和版本冲突采取一致的安全处理。

两套实现不必在性能上完全相同，但不能对资源承诺、授权、撤销、Lease、TaskRun、Stop/Release 和最终交易状态产生语义分歧。

## 4. 证据链要求

每项验收证据都必须回答：

1. 谁产生了这条事实？
2. 该主体是否是该事实的权威 Owner？
3. 事实对应哪个区域、站点、对象和版本？
4. 事件序号、Owner epoch 和 region_epoch 是什么？
5. 证据是否有完整性摘要与签名验证结果？
6. 证据是否能与请求、响应、事件和恢复报告关联？
7. 是否存在撤销、重放、缺口或时钟偏差？
8. 谁复核、谁批准、谁独立见证？

证据包应保留原始回执和日志引用，不以截图或人工汇总表替代权威记录。真实密钥、令牌和客户数据不得进入公开仓库。

## 5. RTO / RPO 验收口径

- RTO 必须明确起止点，例如故障发生、故障被发现、服务恢复、关键交易恢复或全部功能恢复，不能混用。
- RPO 必须明确数据对象与权威事实边界，区分业务数据、Checkpoint、事件、Saga Ledger、目录和遥测。
- 对已确认的 Commit/Lease/Stop/Release 权威事实，恢复后不得丢失、覆盖或重复生成；事件投影可由 Owner 权威记录重建。
- 撤销收敛时间从撤销 Owner 发布时开始计算，分别报告传播、PEP 生效和最终审计确认。
- 所有统计需报告样本数、分位数、最大值、故障条件和测量工具版本。

## 6. 失败项与风险接受

- P0/F0 失败默认阻断阶段放行。
- P1/F1 失败必须修复或由有权风险 Owner 明确接受剩余风险、补偿控制、适用范围和到期时间。
- 任何风险接受不得授权未授权数据访问、绕过设施联锁、接受旧 FencingToken 或伪造 Owner 事实。
- 失败场景必须保留原始记录，并建立问题编号、责任人、根因、修复版本和复测证据。
- “未测试”“环境不具备”和“证据缺失”不能标记为 Passed。

## 7. 最终验收包

建议按以下结构形成十星验收证据包：

- 00_范围与签署：拓扑、资产范围、Owner、测试窗口和批准记录。
- 01_版本基线：软件、固件、驱动、Ontology、Schema、策略和配置摘要。
- 02_网络与设施：物理路径、运营商、供电、制冷和联锁证据。
- 03_单星与区域基线：性能、容量、健康和本地自治。
- 04_故障注入：场景、注入日志、影响和停止记录。
- 05_恢复与对账：Owner 回执、快照、事件重放、Lease 与 Saga 结果。
- 06_安全与数据治理：撤销、Grant、PEP、身份、信任和驻留验证。
- 07_独立见证：第二实现结果、差异分析和签署。
- 08_缺陷与风险：失败项、整改、风险接受和复测。
- 09_最终决议：Gate 0—4 结果、限制条件和有效期。

## 8. 放行声明

当前仅完成验收框架设计。未取得真实双区域十星的 Owner 签署、故障注入记录、独立实现互操作报告和 Gate 4 决议前，项目状态必须保持“架构候选/待验证”，不得宣称生产级验收完成。
