## 0. 本轮结论 {#0-本轮结论}

本轮将 AEE/ASCP 从"接口映射候选"推进到"责任与签署治理候选"。

### 0.1 六项候选决策 {#01-六项候选决策}

1.  六个既有接口域保持不变；AEE/ASCP 是横切 Profile，不增加第七接口域。
2.  ADS、SCO、FWSX、A2A
    是不同层次的协调/协议能力，不能相互替代，也不能接管站点本地权威。
3.  全局任务协调与本地任务认领分离：SCO 负责
    TaskContract/ContractGraph/Plan/Saga/ActivationBarrier 汇总；站点
    Local Task Coordinator 签发本地 TaskClaim。
4.  物理资源 Lease 与 TaskClaim 完全分离：资源所在地 Lease Authority
    独立签发 LocalResourceLease 与 FencingToken。
5.  命名空间与扩展 URI 目前尚无已确认的项目控制域名，因此所有 URI
    仅为模板；未完成域名控制权验证和双边签署前，不得跨站点正式激活。
6.  DM04 IFC0.2 的 `profile_extensions` 是增量提案；IFC0.1
    必需字段保持不变，IFC0.2 未经双方批准不得发送该字段。

### 0.2 状态声明 {#02-状态声明}

DM04 IFC0.1 是冻结候选基线，不等于已正式发布。AEE/ASCP V1.1
是架构候选。RACI、签署矩阵、URI 台账和 IFC0.2
增量均待签署。当前没有真实双站点部署或互操作测试通过的证据。

## 1. 权威模型 {#1-权威模型}

### 1.1 六域权威边界 {#11-六域权威边界}

  接口域       最终权威                                                           ADS/SCO可做                               ADS/SCO不可做
  ------------ ------------------------------------------------------------------ ----------------------------------------- ------------------------------------------
  联邦治理     双方治理 Owner                                                     协调、记录批准结果、维护目录投影          单方批准成员或修改对方信任根
  身份与授权   各站点 IAM/PDP/PEP                                                 携带合法委托、查询决策状态、解释策略      授予远端本地权限
  数据空间     数据 Owner/Connector                                               目录发现、合同协调、用途审计汇总          绕过数据合同或代签 DataUseGrant
  算力星       资源所在地 Owner/Lease Authority                                   发现、比较、请求、协调                    代签资源 Lease 或承诺容量
  联邦任务     SCO 全局协调 + 站点本地 Task Owner                                 ContractGraph、Plan、Saga、Barrier 汇总   覆盖本地 TaskStage、TaskClaim 或执行事实
  证据与验收   Evidence Owner、独立 Acceptance Owner、Metering/Settlement Owner   汇总引用、对账、追踪                      自行验收、改写原始计量或裁决合同争议

### 1.2 四类横切能力的边界 {#12-四类横切能力的边界}

-   **ADS：**
    联邦治理协调、环境/能力/语义目录、Profile注册、跨域治理视图；不替代数据/资源/本地策略权威。
-   **SCO：**
    全局任务计划、ContractGraph关联、Saga协调、ActivationBarrier聚合和交易对账；不签发本地资源Lease，不替代本地TaskClaim。
-   **FWSX：**
    事件投递、游标、重试、重放、跨站点传输和传输审计；不拥有事件事实，不批准数据用途，不扩大字段投影。
-   **A2A：**
    Agent发现、消息、任务交互和Artifact交接；不授予数据/算力权限，不替代SCO/DM04领域状态机。

## 2. TaskClaim 权威冲突的正式裁决 {#2-taskclaim-权威冲突的正式裁决}

### 2.1 冲突来源 {#21-冲突来源}

AEE V1.0 曾将 TaskClaimLease 的写入权威归于 SCO；DM04 将 SCO
定位为全局协调方并保留站点执行方权威。若不拆分"全局任务状态"和"本地阶段认领"，实现中可能出现
SCO 与站点任务协调器双重签发或争夺本地状态的问题。

### 2.2 候选裁决 {#22-候选裁决}

  对象                 权威                               作用域                                  签署者
  -------------------- ---------------------------------- --------------------------------------- --------------------------------
  TaskContract         发起方与各合同签署方               全局任务义务                            合同相关方
  ContractGraph        SCO维护关联；每个节点由Owner签署   全局依赖图                              SCO签图摘要；节点Owner签节点
  Plan/Saga            SCO                                全局协调视图                            SCO
  TaskStage            站点本地Task Owner                 单站点阶段                              本地Task Owner
  TaskClaim            Local Task Coordinator             `(site_id, site_task_ref, stage_ref)`   本地Task Coordinator
  LocalResourceLease   资源所在地Lease Authority          具体资源与任务绑定                      资源Owner授权的Lease Authority
  FencingToken         资源所在地Lease Authority          具体资源Epoch                           同上

### 2.3 必须满足的规则 {#23-必须满足的规则}

-   SCO 可以创建、拆分、分派、暂停和汇总
    TaskStage，但不能伪造或代签站点本地 TaskClaim。
-   Local Task Coordinator
    以原子比较交换（CAS）或等效机制保证同一站点同一阶段只有一个有效认领。
-   `claim_epoch` 仅用于本地 TaskClaim 的旧认领者隔离；`fencing_token`
    仅用于资源 Lease 的旧资源持有者隔离。
-   TaskClaim 过期、撤销或站点状态不明时，不得推定资源 Lease
    已失效；二者分别查询各自权威。
-   ActivationBarrier
    是跨域前置条件汇总，不是最终执行许可；每个站点在副作用前仍需本地
    IAM/PDP/PEP、Grant、Lease、FencingToken、撤销水位和设施联锁检查。

**决策状态：** Proposed。需 SCO Owner、Site A Task Owner、Site B Task
Owner、Compute Resource Owner 共同评审。

## 3. Owner/RACI 治理 {#3-ownerraci-治理}

本包提供 23 项活动的 RACI。角色名不代表已指定真实责任人；Site A/B
的组织名称、负责人、替补人和联系通道均待补齐。

### 3.1 RACI 解释 {#31-raci-解释}

-   A：Accountable，最终负责并承担决策责任；除双边共同批准事项外，每项活动原则上只设一个
    A。
-   R：Responsible，负责执行与交付。
-   C：Consulted，必须在决策前征询意见。
-   I：Informed，接收结果和审计记录。
-   A\*：双边共同批准，双方各自对本方范围负责；任一方未批准，双边事项不得生效。

### 3.2 最低角色集合 {#32-最低角色集合}

Federation Governance Owner、IAM/Security Owner、Data Owner、Compute
Resource Owner、SCO/Task Owner、Site Task Owner、Evidence Producer
Owner、Independent Acceptance Authority、Metering
Owner、Settlement/Dispute Authority、Agent Owner、FWSX Service
Owner、Namespace Owner、Human Governance Board。

每个站点应分别指定本地 Owner；不能以"平台统一负责"替代本地权威。

## 4. 签署与证据责任 {#4-签署与证据责任}

签署矩阵按对象权威签署，不按系统调用路径签署：

-   TrustAgreement：双方治理 Owner 双边签署。
-   DataUseGrant：对应 Data Owner 签署；目标站点 PEP 执行。
-   LocalResourceLease：资源所在地 Lease Authority 签署。
-   TaskClaim：目标站点 Local Task Coordinator 签署。
-   ContractGraph：SCO 签图版本/摘要；每个合同节点 Owner
    分别签署节点义务。
-   ActivationBarrier：SCO 签汇总检查结果；各本地 Owner
    的决策证据仍独立存在。
-   Trace/Event：原始事实 Owner 签事件；FWSX 只签投递回执。
-   Evidence/Artifact：生产方签摘要；Evidence 服务保全。
-   AcceptanceRecord：独立验收方签署。
-   MeteringRecord：资源 Owner 签署；更正追加，不覆盖原始记录。
-   RSI 晋级/回滚：人类治理委员会或明确授权审批人签署，RSI
    不得自我授权。

具体签名算法、密钥生命周期、轮换和撤销策略继续沿用双方已批准的安全/信任基线，本备忘录不擅自指定算法。

## 5. 命名空间与 URI 注册 {#5-命名空间与-uri-注册}

### 5.1 当前状态 {#51-当前状态}

项目尚未提供可确认由项目主体控制的正式域名。因此：

-   所有 `https://{controlled-domain}/...` 仅为 URI 模板。
-   `example.invalid` 仅可用于文档占位，绝不可进入生产配置或跨站点请求。
-   在域名控制权、解析稳定性、TLS、命名空间 Owner
    和双方签署未完成前，URI 状态保持 Candidate / Not Registered。

### 5.2 建议 URI 结构 {#52-建议-uri-结构}

-   Profile：`https://{controlled-domain}/aee-ascp/profiles/1.1`
-   AEE Context
    Schema：`https://{controlled-domain}/aee-ascp/schemas/context/1.1`
-   TaskClaim
    Schema：`https://{controlled-domain}/aee-ascp/schemas/task-claim/1.1`
-   Event
    Type：`https://{controlled-domain}/aee-ascp/events/{event-name}/1`
-   Ontology
    Profile：`https://{controlled-domain}/aee-ascp/ontology/{profile-name}/3.0`
-   A2A
    Extension：`https://{controlled-domain}/aee-ascp/a2a/extensions/1.1`

### 5.3 注册规则 {#53-注册规则}

1.  URI 必须属于项目/组织控制的稳定域名或正式命名空间。
2.  URI 对应的规范文档和 Schema
    必须可稳定解析；不得指向临时存储、个人账号或动态短链。
3.  URI
    一经发布不得重新分配给另一语义；弃用必须保留历史记录、替代URI和迁移窗口。
4.  Major 语义变化使用新 Major URI；Minor/patch 版本通过版本元数据和
    Schema Digest 管理。
5.  每个 URI 登记
    Owner、版本、Schema引用、内容摘要、状态、生效时间、兼容范围、弃用策略、联系人和签署记录。
6.  跨站点激活前，双方必须验证 URI、Schema 摘要和签署记录一致。

## 6. DM04 IFC0.2 `profile_extensions` 增量提案 {#6-dm04-ifc02-profile_extensions-增量提案}

### 6.1 原则 {#61-原则}

-   不改变 IFC0.1 已有必需字段。
-   只新增可选 `profile_extensions`。
-   扩展以 URI 为键，值包含
    `profile_version`、`schema_ref`、`criticality`、`payload_digest` 和
    `data`。
-   `data`
    只允许携带环境、Ontology、痕迹、订阅、TaskClaim、ArtifactBinding 和
    GovernanceContext 的引用；不得携带 Grant 凭证、Bearer
    Token、资源Lease或数据正文。
-   任何引用被解析时仍需目标站点重新授权。

### 6.2 候选处理规则 {#62-候选处理规则}

  条件                                                        接收端处理
  ----------------------------------------------------------- --------------------------------------------
  对端未声明支持 IFC0.2                                       不发送扩展；需要扩展才能安全执行时暂停操作
  未知 URI 且 criticality=required                            副作用前拒绝
  未知 URI 且 criticality=optional                            忽略业务处理并记录审计
  已知 URI 但版本不兼容且 required                            拒绝并返回兼容错误
  Schema 校验或摘要校验失败                                   拒绝；不得将该请求送入副作用阶段
  引用存在但无本地授权                                        由目标站点 PDP/PEP 拒绝
  扩展字段试图覆盖 RequestEnvelope 的 purpose/audience/身份   拒绝并记录安全事件

### 6.3 摘要与幂等 {#63-摘要与幂等}

-   `payload_digest` 对扩展 `data` 的规范化序列化结果计算。
-   高风险写操作的请求摘要必须覆盖
    `profile_extensions`，防止扩展数据在签名后被替换。
-   同一幂等键但扩展内容不同，按既有 `IDEMPOTENCY_CONFLICT` 语义处理。
-   扩展不构成授权凭证，不改变
    `caller_principal`、`workload_identity`、`audience`、`purpose`、`expires_at`、`idempotency_key`
    或 `expected_state_version`。

### 6.4 错误码 {#64-错误码}

建议候选错误语义：`UNSUPPORTED_REQUIRED_EXTENSION`、`PROFILE_EXTENSION_INVALID`、`PROFILE_VERSION_MISMATCH`。这些名称尚未分配到
DM04 现有错误码目录；需 DM04 API Owner 审核后再确定最终编号和HTTP映射。

### 6.5 版本门禁 {#65-版本门禁}

IFC0.2 只有在双方 API Owner、Security Owner、AEE/ASCP Profile Owner
签署后，才可纳入候选互操作测试。签署前所有跨站点请求继续使用 IFC0.1
合法字段与操作；不能依赖对端忽略未知字段。

## 7. G0 放行条件 {#7-g0-放行条件}

G0 只有在以下条件全部满足后才能标记 Completed：

1.  Site A/B 正式主体与边界已确认。
2.  六域 Owner 均指定组织、责任人、替补和联系通道。
3.  SCO 全局任务协调与两站点 Task Owner 的职责分层签署。
4.  TaskClaim 与 ResourceLease 双权威分离签署。
5.  Data Owner、Compute Owner、Acceptance Owner 的独立性检查通过。
6.  项目控制域名和 URI Namespace Owner 已确认。
7.  Profile、Schema、Event、Ontology、A2A Extension URI 已注册并验证。
8.  DM04 IFC0.2 扩展提案完成双方评审。
9.  签名算法、密钥轮换、撤销和信任协议引用已确认。
10. 证据保留期与合同争议窗口对齐。
11. RACI 每项决策均有明确 A；双边事项明确 A\*。
12. 所有 ADR 均签署、拒绝或延期；不得将未签署项标为 Frozen。
