# G2-06.18｜双区域十星业主需求基线与冻结规则

**版本：** RC0  
**日期：** 2026-11-14  
**状态：** 候选基线；待业主与各专业Owner审议  
**决策性质：** 需求和架构基线治理，不是采购批准、施工图或投运许可

## 1. 目的与范围

本文件把此前形成的十星逻辑角色、候选设备、双区域自治、网络分层、供电/液冷和三路线设施责任，转成统一的业主需求。供应商响应必须基于同一负载、服务目标、数据边界、计量口径和验收方法。

本阶段要冻结的是：
1. 需求分类、字段、ID和状态定义；
2. 十星角色与区域边界；
3. 数据、控制权、资源Owner与故障域边界；
4. 容量、能耗、有效算力和TCO计算方法；
5. 需求到验收的追踪关系与变更治理。

本阶段不冻结：
- Site A/B具体国家、城市、园区、地块和POI；
- GPU训练/推理的真实规模、模型、并发、tokens/s和利用率；
- CPU节点数量、准确CPU SKU、内存与本地盘；
- 供电firm MW、设施总负荷、PUE/WUE和水量；
- GPU/Storage/WAN实际带宽、RTT、抖动和丢包；
- 服务可用性、RPO/RTO、数据驻留与保留期；
- CAPEX、OPEX、电价、水价、折现率和投资回报；
- 未经OEM签署的准确MTM/SKU、QVL、固件和端口映射。

## 2. 需求状态与冻结级别

每条需求必须使用唯一ID，并区分以下状态：

| 状态 | 含义 | 可否作为采购/工程输入 |
|---|---|---|
| Confirmed-Structure | 已有上游架构决策或项目定义支持的结构性边界 | 可作为架构约束，不等于数量/性能已冻结 |
| Candidate | 已有参考方案，但仍需Owner/OEM/工程验证 | 仅供方案比较与询价 |
| TBD-Owner | 缺少业主业务输入或批准 | 不得填入假设值冒充要求 |
| TBD-Vendor | 需OEM/园区/Utility/运营商提供证据 | 不得通过营销资料放行 |
| TBD-Engineer | 需具资质专业工程师计算/签署 | 不得用于施工 |
| Approved-Baseline | 有权Owner签署、变更记录和验收方法的批准基线 | 可进入相应采购/工程阶段 |
| Superseded | 被新版本替代，保留历史追溯 | 禁止继续引用为当前要求 |

冻结分两层：
- **L1 架构/需求结构冻结：** 可先冻结逻辑星位、Owner边界、需求ID、字段、验证方式和禁止假设。
- **L2 工程/商业参数冻结：** 必须取得业主签署、专业工程审查、项目级资源证据和适用的OEM/Utility文件后才可冻结。

任何RC0、Proposed、Candidate或TBD不得因为进入GitHub、完成静态检查或生成文件包自动升级为Approved-Baseline。

## 3. 业主必须定义的业务画像

### 3.1 GPU训练
至少输入：模型/参数规模、训练类型（预训练/微调/强化学习/多模态）、精度与并行策略、训练数据规模、单作业GPU数、作业时长、目标完成时间、checkpoint大小/频率、可中断性、作业优先级、GPU利用率目标和可接受失败重跑成本。

验收：用业主批准的数据集、模型和软件版本进行端到端训练基准；报告有效GPU小时、吞吐、作业完成率、通信效率、checkpoint/恢复时间和能耗。不得以厂商峰值规格替代实测。

### 3.2 GPU推理
至少输入：模型列表与版本、量化/精度、上下文长度分布、输入/输出token分布、并发会话、峰值/平均QPS、TTFT、TPOT、p95/p99延迟、批处理、缓存命中、可用性、数据隐私和弹性峰值。

验收：在固定模型、精度、上下文、并发和质量门槛下测吞吐、延迟、错误率、GPU显存、利用率、成本和扩缩容恢复。

### 3.3 CPU/HPC/Agent
至少输入：并发Agent/任务数、vCPU/物理核、内存/NUMA、容器/虚拟机密度、任务时长、沙箱类型、网络和本地临时盘、峰值调度量、执行权限和审计要求。

验收：在租户隔离、资源争用、节点失效和区域断网情况下验证任务吞吐、隔离性、队列时延、恢复与审计完整性。

### 3.4 数据与存储
至少输入：初始数据量、年增长率、冷热分层、读写比例、IOPS/吞吐、块大小、并发读写、DWPD、保留期、不可变备份、加密、数据驻留和删除证明。

验收：按真实访问模式验证可用容量、吞吐、延迟、耐久度、重建时间、故障恢复和数据一致性。QLC容量层不得默认承载高写入事务日志或Saga/Lease等权威事实。

### 3.5 控制面与跨区域协同
至少输入：API请求率、事件速率、状态变更量、目录规模、审计事件量、身份/策略请求量、跨区域同步对象、离线自治时长、撤销传播时限和管理面可用性。

验收：控制面故障、WAN分区、重复/乱序事件、Owner不可达、撤销缺口和部分提交时，保持本地权威、幂等、可审计和安全停止。

## 4. 双区域十星逻辑资源基线

每区域五个逻辑资源域：

| 星位 | 角色 | 参考配置 | 核心边界 |
|---|---|---|---|
| A1/B1 | GPU计算星 | 1套HPE GB300 NVL72候选 | NVLink仅限本地机柜域；GPU Fabric A/B分离 |
| A2/B2 | CPU/HPC计算星 | 1套Lenovo N1380候选，8 trays | 2N2S或4N1S待业主/OEM确认；Agent沙箱与NUMA隔离 |
| A3/B3 | 存储数据星 | 2台Dell R7725xd候选 | QLC容量层与高写入事务/元数据层分离 |
| A4/B4 | 控制服务星 | 3台Dell R9815候选 | HA/仲裁拓扑待一致性模型和独立故障域验证 |
| A5/B5 | 网络边缘与安全星 | 2台Dell R9815候选；2台GPU Fabric交换机候选 | OOB、Facility、WAN和租户数据面隔离 |

星位是逻辑资源域，不等于固定服务器数量。设备实例可随采购与工程设计调整，但任何变化都必须同步更新BOM、供电、热工、网络端口、资产Owner、数据模型和验收矩阵。

## 5. 跨区域架构约束

1. A/B各自具备本地身份/策略缓存、调度自治、设施告警、资源状态和审计缓冲能力；WAN中断不应使站点失去本地安全运行能力。
2. Site LCP与本地Resource Owner保持本地资源调度/执行权威；ADS/SCO/RCP承担跨域协同、语义治理、计划与交易协调，不替代站点本地授权。
3. TaskClaim、ResourceLease、PolicyDecision分离；目录发现不等于资源可用，Accepted不等于业务完成，Unknown不等于Failed。
4. 跨区域GPU作业默认按异步数据/Checkpoint/控制协调设计；只有实测RTT、带宽、抖动、拥塞、故障恢复和业务SLO通过后，才允许评估跨区域同步训练。
5. 跨区域复制策略按数据类别分别确定：强一致权威事实、本地事务日志、模型/数据集、Checkpoint、备份和遥测不得采用同一默认策略。
6. 双区域独立性须核验电网、变电站、流域、冷源、物理光路、灾害、身份/密钥/DNS/时间源、OEM备件与运维组织共同故障域。
7. L0人身/建筑/消防/漏液/电气硬联锁由现场专业系统和依法授权人员执行，不依赖ADS、WAN或AI审批。

## 6. 服务等级与业务分级

建立四类业务服务等级，具体数值由业务Owner填写：
- **S0 安全与设施保护：** 本地硬联锁、消防、漏液、过温、断水和电气保护；由当地法规、OEM和专业工程师确定动作阈值。
- **S1 控制/身份/授权/审计：** 支持区域自治、策略验证、撤销与审计；WAN中断时限制高风险跨域动作。
- **S2 生产业务与数据服务：** 推理、在线数据服务、模型/API入口；由业务Owner定义可用性、延迟、错误率、RPO/RTO。
- **S3 批处理与可重调度算力：** 训练、批量分析、可中断Agent/HPC任务；以checkpoint、重试、队列和资源恢复为主要机制。

每一服务必须明确：SLO、SLI、测量边界、时间窗口、排除项、错误预算、维护窗口、RPO、RTO、恢复验证、Owner和违约/升级路径。不得把园区电力SLA等同业务服务可用性。

## 7. 安全、数据和治理要求

- 数据按业务Owner分类；明确数据控制者/处理者、驻留地、跨境流动、保留期、删除、备份和法律保全。
- KMS/HSM、身份、PKI、DNS、时间同步、审计和撤销机制要定义区域自治与跨区恢复边界。
- BMC/Redfish、PDU、CDU、BMS、Facility和交换机管理面进入隔离的OOB/Facility网络，不对租户和普通Agent开放。
- 远程维护采用身份绑定、最小权限、短时授权、审批、双人控制（按风险等级）、录屏/命令审计和可撤销会话。
- 设施紧急硬联锁不能被远程AI审批延迟；但所有紧急操作必须留下独立审计与复核证据。
- 任何跨区域数据访问由Data Owner授权，目标区域PEP每次访问复核；可发现不等于可读取或可训练。

## 8. 供电、冷却、网络和容量基线

### 8.1 供电
分别记录设备典型输入、峰值输入、瞬态、PF、kVA、Whip/支路、UPS/PDU/变压器和POI容量。HPE 132kW TDP、约155kW EDPp、192kW busway planning不可互换；8×33kW Power Shelf额定输出之和不是实际功耗。N1380 54kW N+1 DC chassis capacity不是AC输入。任何区域MW需逐设备和设施负载计算后由Utility项目级证据验证。

### 8.2 冷却与水务
分别定义设施一次侧、CDU、TCS二次侧、Manifold、冷板、介质、水质、温度、压力、流量、压降、热负载、泵N+1和整机冗余。XDU1350 1.3MW是额定冷量，不是电功率；泵N+1不等于整机1+1。水务需独立记录合法供水、排水、取水限制、季节性、WUE口径和极端气候。

### 8.3 网络
GPU Fabric Plane A/B、CPU North-South、Storage、Customer/WAN、Control/Support、OOB/Facility分离。Spectrum-6 RoCE双平面是当前主参考，Quantum-X800 IB为替代；冻结前完成OEM QVL、端口/光模块/线缆、拥塞控制、基准测试和团队运维能力评估。WAN以业务RPO/RTO和数据复制窗口反推带宽，不能只看标称Gbps。

## 9. 三路线共用的业主需求

G2-06.16三条路线继续保留：
- A 完全自建；
- B 高密度托管入驻；
- C 租赁设施/Powered Shell + 业主自建IT和部分下游机电。

三路线必须使用相同的业务负载、GPU SKU/数量、有效GPU小时、存储容量、数据驻留、安全要求、服务等级、五年期限、币种/税费/折现口径比较。任何路线不得因园区宣称“液冷就绪”或“可用MW”免除G2-06.17项目级证据门禁。

## 10. 需求冻结门禁

- Gate R0：需求字段和逻辑星位完整；每项有ID、Owner、状态、验证方法。
- Gate R1：业主业务画像、地理法域、数据分类/驻留、SLO、RPO/RTO和预算假设签署。
- Gate R2：OEM准确SKU/QVL、负载曲线、端口、液冷、电气接口完成核验。
- Gate R3：站点地块、firm MW、供水/排水、冷源、物理光路和许可达到G2-06.17要求的证据等级。
- Gate R4：同口径容量、TCO、故障域、FAT/SAT和验收计划通过专业Owner审查。
- Gate R5：业主批准后，才可冻结采购技术规范或进入工程设计/采购阶段。

任一P0输入缺失、第三方依赖未闭环、Owner未签署或证据等级不足，保持Hold；不得用加权评分抵消硬门禁。

## 11. 变更控制

任何设备SKU/数量、GPU Fabric路线、存储保护方式、数据驻留、供电/冷却边界、SLO、RPO/RTO、站点位置或设施责任变更，必须：
1. 提交变更ID、原因、影响范围和发起Owner；
2. 更新需求、Ontology/数据模型、BOM、接口契约、容量模型、风险和TCO；
3. 评估双区域共同故障域、权限、安全和数据迁移影响；
4. 定义验证、回滚、停机窗口和独立见证；
5. 由业务Owner、资源Owner、专业工程师和业主按权限签署；
6. 更新CHANGELOG、文件清单与SHA-256。

## 12. 当前结论

G2-06.18形成的是“需求结构候选基线”，不是已批准的工程数值基线。当前最关键的未决输入是：A/B地理法域、业务工作负载规模、服务等级、数据驻留、RPO/RTO、供电/冷却目标、网络性能、预算与业主责任人。未取得这些输入前，不应正式冻结区域MW、GPU利用率、PUE/WUE、带宽、可用性或五年TCO。
