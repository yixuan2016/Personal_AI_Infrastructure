# G2-04.1｜ADS / SCO REST Binding RC1 候选规范

**日期：** 2026-11-10  
**状态：** RC1 候选设计，待 ADS/SCO API Owner、站点 Owner、数据 Owner 与安全治理 Owner 联合评审  
**基线：** ADS API v1 RC0、SCO API v1 RC0、DM04 IFC0.1/IFC0.2 增量治理提案、G2-03 75 个 operation 映射  
**范围：** REST 接口绑定、请求/响应、幂等、条件更新、错误语义、分页、撤销与审计；纯架构契约设计，不含工程实现代码。

## 1. 设计目标与非目标

### 1.1 目标

1. 把 DM04 逻辑 Envelope 与 ADS/SCO REST HTTP Binding 明确分层，避免把协议层字段误当作业务身份或授权事实。
2. 每个副作用操作拥有可验证的强类型 payload；禁止用可选、任意字段的 GenericCommand 代替操作契约。
3. 区分命令受理状态、编排状态与权威业务对象状态。
4. 将幂等、请求关联、条件更新、签名、撤销水位和响应证据纳入机器可读契约。
5. 保留 ADS 协调治理职责、SCO 跨站点任务协调职责，以及各资源/数据/站点 Owner 的最终权威。
6. 兼容 IFC0.1 既有必需字段；IFC0.2 扩展继续采用可选 `profile_extensions`，不得未经双方批准改变既有必需字段。

### 1.2 非目标

- 本提案不批准生产 API、不代表 ADS/SCO 已实现。
- 不由 ADS 代替目标 Resource/Data Owner PDP 签发 Permit。
- 不由 SCO 签发站点本地 ResourceLease 或 FencingToken。
- 不把 A2A、CloudEvents、FWSX、DM04 合并成单一协议。
- 不把目录登记、能力发布、计划选择或 Operation Accepted 解释为资源可用、任务运行或业务验收。

## 2. 分层绑定模型

| 层 | 权威内容 | 不承担的职责 |
|---|---|---|
| 身份认证层 | OAuth2/OIDC subject、client、audience；必要时 mTLS/SPIFFE 工作负载身份 | 不从 JSON body 自报身份 |
| DM04 逻辑 Envelope | request_id、correlation_id、issued_at、api_version、schema_version、payload、expires_at、digest、profile_extensions | 不携带可覆盖认证上下文的 caller 身份 |
| REST Binding | HTTP method/path/header/status/content-type、条件请求、分页 | 不改变领域对象所有权 |
| ADS/SCO 领域契约 | 强类型操作 payload、强类型业务对象响应、Operation | 不以 ResourceReference 代替所有业务对象 |
| 本地执行与治理 | PDP/PEP、Lease Authority、Local Task Coordinator、Data Owner、Artifact Owner | 不因中心协调而转移最终执行权 |

## 3. Request Envelope 与 Header 绑定

### 3.1 字段规则

| 逻辑字段 | HTTP/认证承载 | 规则 |
|---|---|---|
| request_id | Body `request_id` + `X-Request-ID` | 两处同时出现必须完全一致；缺失或不一致返回 400 |
| correlation_id | Body `correlation_id` + `X-Correlation-ID` | 端到端因果链；不得作为身份凭证 |
| idempotency_key | `Idempotency-Key` Header | 对所有非幂等副作用 POST 必需；不得只靠 body 可选字段 |
| if_match | `If-Match` Header | 更新已有对象、状态迁移、合同修订必须提供当前 ETag |
| if_none_match | `If-None-Match: *` | 创建要求客户端指定唯一 ID 或防止重复创建时使用 |
| traceparent | W3C Trace Context Header | 仅用于追踪，不是授权证据 |
| caller_principal | 已验证 OAuth2/OIDC subject | 从认证上下文绑定；body 自报值仅可作为提示且必须一致 |
| workload_identity | 已验证 mTLS/SPIFFE/OIDC workload identity | 由验证器确认签发者、受众、有效期与撤销状态 |
| audience | Access Token `aud` + API resource registration | 目标服务必须核验；不能只凭 URL 推断 |
| purpose | 由显式 purpose 与合同/Grant/Policy 引用解析 | reason 不等于 purpose；无法解析时拒绝敏感操作 |
| protocol_profile | 双方登记/协商的 Profile | 不从 api_version 或 schema_version 推断 |
| payload_digest | Body 摘要及签名覆盖范围 | 高风险写操作必需；规范化序列化规则需统一 |
| expires_at | Body | 跨站点命令必需；过期命令拒绝，不得自动延长 |

### 3.2 Header 规范

- `Authorization: Bearer <access-token>`：认证令牌只通过认证层传递；令牌本身不得进入日志或 EvidenceRecord。
- `Content-Type: application/json`；响应按 `application/json` 或 `application/problem+json`。
- `X-Request-ID` 与 body `request_id` 一致；`X-Correlation-ID` 与 body `correlation_id` 一致。
- `Idempotency-Key` 对所有非幂等副作用 POST 必需，作用域为 `(authenticated principal, audience, operationId, key)`。
- `If-Match` 对已有对象的变更必需；缺失返回 428，版本不匹配返回 412。
- `traceparent` 可选，必须按 W3C Trace Context 解析；不得用作安全授权字段。
- `Prefer: respond-async` 仅用于服务明确支持异步的操作；不得改变操作副作用或绕过审批。

## 4. 幂等与条件更新

### 4.1 Idempotency-Key

1. 同一 principal、audience、operationId、key 和相同 request digest：返回原操作/原结果引用，不重复执行。
2. 同一 key 但 request digest 不同：返回 `409 IDEMPOTENCY_KEY_REUSED`，不执行第二次。
3. 去重记录的保留期必须覆盖合同约定的最大重试窗口；跨站点任务至少覆盖合同有效期内的重试/对账周期。
4. 发生超时而调用方不知道结果时，先查询原 operation_id 或按同 key 重放；禁止换新 key 盲目重试高风险副作用。
5. Idempotency-Key 不替代业务唯一键、TaskRun attempt_id 或 FencingToken。

### 4.2 ETag / If-Match

- 每个可变聚合根输出强 ETag，值绑定对象 ID、版本号和内容摘要。
- 修改操作必须提交 `If-Match`；缺失返回 428 `PRECONDITION_REQUIRED`。
- 当前 ETag 不匹配返回 412 `PRECONDITION_FAILED`，响应包含当前可披露版本引用，不自动覆盖。
- 对不可变版本对象（TaskContractVersion、PolicyVersion、OntologyProfileVersion、DatasetVersion）只允许创建新版本，不允许原位更新。
- 状态迁移同时校验 ETag 与允许的前置状态；状态不允许时返回 409 `INVALID_STATE_TRANSITION`。

## 5. Typed Request / Response

### 5.1 Request

`RequestEnvelope` 是逻辑结构，不要求每个 REST path 原样嵌套一个顶层 envelope。REST operation 应在 OpenAPI 中显式绑定：

- 公共元数据：request_id、correlation_id、issued_at、api_version、schema_version、expires_at、payload_digest。
- 操作载荷：按 operationId 引用独立的 `*Request` schema；副作用操作 payload 必需。
- 扩展：`profile_extensions` 只允许 URI-keyed 扩展；未识别的 required extension 拒绝，optional extension 忽略并审计。
- 禁止 `additionalProperties: true` 作为业务 payload 的默认策略；每个 payload 应明确允许字段。

### 5.2 Response

同步只读/创建操作返回强类型业务视图，例如 `ParticipantView`、`PolicyDecisionView`、`TaskContractView`、`TaskRunView`、`FederatedReservationView`、`AcceptanceView`、`SettlementView`。

异步操作返回 `OperationView`，但必须包含 `ResponseContext`：

- `operation_ref`：SCO/ADS Operation 的权威引用；
- `object_ref`：业务对象引用及类型；
- `command_status`：命令/编排状态；
- `authoritative_state`：authority_ref、state、state_version、as_of、freshness；
- `result_ref`：可选、强类型结果引用；
- `event_cursor`：可恢复的事件水位；
- `evidence_refs`：签名回执/验证证据引用；
- `reconciliation_required`：是否必须向权威 Owner 对账。

`Accepted` 仅表示服务已受理命令，不表示资源已预留、租约已签发、任务已启动或验收已通过。

## 6. HTTP 状态码与错误模型

| HTTP | code | 语义 | 客户端行为 |
|---:|---|---|---|
| 200 | OK | 读取/同步操作成功 | 消费强类型对象 |
| 201 | CREATED | 新业务对象已创建 | 读取 Location / ETag |
| 202 | ACCEPTED | 异步命令已受理 | 轮询 Operation 或订阅事件；不推断业务完成 |
| 204 | NO_CONTENT | 无响应体的幂等删除/释放已确认 | 仍保留审计回执引用（如有） |
| 400 | BAD_REQUEST | Header/body 不一致、Envelope 格式错误 | 修复请求，不重试 |
| 401 | UNAUTHENTICATED | 认证缺失/无效 | 重新认证 |
| 403 | FORBIDDEN | 身份已识别但无权限/用途不匹配 | 不重试；申请合法授权 |
| 404 | NOT_FOUND | 对象不存在或按披露策略隐藏 | 不猜测资源存在性 |
| 409 | CONFLICT | 幂等键冲突、状态迁移冲突、资源冲突 | 查询权威状态后决策 |
| 412 | PRECONDITION_FAILED | ETag / If-Match 版本不匹配 | 读取新版本、人工/业务合并 |
| 422 | UNPROCESSABLE_CONTENT | Schema 正确但领域约束失败 | 修正合同/约束 |
| 428 | PRECONDITION_REQUIRED | 缺少 If-Match 等前置条件 | 补充条件请求 |
| 429 | TOO_MANY_REQUESTS | 限流 | 遵守 Retry-After 与退避策略 |
| 500 | INTERNAL_ERROR | 服务内部错误 | 先按 request/idempotency 查询，不盲重试 |
| 502/503/504 | UPSTREAM/UNAVAILABLE/TIMEOUT | 依赖不可用或超时 | 状态未知时必须对账；禁止推定失败 |

错误响应使用 `application/problem+json`，包含 `type`、`title`、`status`、`detail`、`instance`、稳定 `code`、`correlation_id`、`retryable`、`retry_after`、`authority_ref`、`violations[]`。敏感策略细节、跨租户信息和秘密属性不得写入 detail。

## 7. 列表与分页

统一 `Page<T>`：`items[]`、`next_page_token`、`page_size`、`as_of`、`source_refs[]`、`freshness`。分页 token 必须绑定查询条件、principal、audience、scope 和有效期；不得跨租户复用。联邦列表逐项标注 source Owner、版本、验证等级与数据新鲜度。聚合结果不覆盖源权威事实。

## 8. 安全、撤销与本地执行门禁

- 高风险动作在执行前重新验证 Credential、Attestation、PolicyDecision、DataUseGrant、TrustAgreement、Lease 与 FencingToken。
- 撤销事件按 issuer/authority partition 维护 sequence/checkpoint；发现 gap、回滚或超出最大陈旧窗口时，高风险操作 fail-closed。
- ADS 返回的策略评估结果必须指向目标 Owner PDP 的签名 Decision；`Indeterminate` 绝不能转换为 Permit。
- SCO 的 Start/Resume/Cancel/Lease 操作只是请求/协调；本地 Site LCP、PDP/PEP 和 Lease Authority 作最终判定并签发回执。
- 日志仅记录最小化的主体引用、对象引用、purpose、decision digest、operation/correlation ID 和证据引用；不记录 access token、私钥或原始敏感数据。

## 9. 兼容与版本治理

- API major version、operation payload schema version、Ontology Profile version、Protocol Profile version分别治理。
- 新增可选字段可在同一 minor 兼容窗口内；移除/改义/收紧既有字段属于 breaking change。
- OpenAPI RC1 应为 ADS 与 SCO 使用同一工具链验证；必须运行 lint、schema validation、example validation、diff compatibility。
- 先双读/影子校验，再灰度发布；兼容性报告与迁移计划通过后才允许站点 Adopt。
- IFC0.2 仅作为增量扩展候选；不得宣称已批准或把可选扩展强制为 IFC0.1 必需字段。

## 10. RC1 放行清单

- [ ] ADS 40 / SCO 35 operation 全量绑定 typed request/response。
- [ ] RequestEnvelope 到 REST Binding 映射明确且没有未引用组件。
- [ ] GenericCommand 不再作为无约束业务载荷；保留的公共元数据 schema 需封闭字段。
- [ ] 所有非幂等副作用 POST 声明 Idempotency-Key。
- [ ] 所有已有对象更新声明 If-Match；缺失/冲突状态码一致。
- [ ] Header/body 冲突、重复请求、超时重放、状态未知均有测试。
- [ ] EvaluatePolicy 输出签名 PolicyDecision 或强类型 Operation.result_ref。
- [ ] Operation 与业务对象权威状态分离。
- [ ] Lease、TaskRun、Acceptance、Settlement 的 Owner 权威不被中心服务覆盖。
- [ ] 两套独立实现通过同一契约和故障注入测试。
- [ ] API Owner、Site Owner、Data Owner、安全治理 Owner 签署。

**结论：** RC1 是供评审的机器可读绑定候选，不是生产冻结版本。任何接口实现或发布前必须完成 Owner 签署和双实现验证。
