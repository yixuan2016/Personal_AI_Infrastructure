# G2-04.2｜双站点联邦任务交易状态机与 Activation Barrier

**状态：** 架构候选，待 Site A/B、SCO、ADS、资源与安全 Owner 评审。  
**核心目标：** 在跨站点异构资源协作中，把“全局协调状态”与“本地权威状态”分开；通过 Prepare / Commit / Activation Barrier / Execute / Accept / Settle 形成可审计的交易闭环。

## 1. 核心对象与权威归属

| 对象 | 权威 Owner | SCO / ADS 可做什么 | 禁止越权 |
|---|---|---|---|
| FederatedTaskTransaction | SCO Transaction Coordinator（只对全局编排记录负责） | 汇总各站点状态、推进 Barrier、触发 Saga | 不替代站点事实 |
| TaskContract / ContractVersion | 合同签署方 | 版本管理、校验、流程编排 | 不替合同方签署 |
| TaskPlan | SCO Planning Service；选择由 Task Owner 决定 | 生成候选计划、记录选择 | 计划不是资源承诺 |
| ResourceReservation | 各站点 Reservation Authority | 聚合 Prepare/Commit 回执 | 不在中心数据库制造本地预留事实 |
| ResourceLease / FencingToken | 资源所在地 Lease Authority | 保存引用、转发续租/释放请求、对账 | SCO 不签发/续租/改写 Lease |
| TaskClaim / TaskStage | Site Local Task Coordinator | 汇总状态引用 | 全局 TaskClaim 不替代本地 Claim |
| PolicyDecision | 目标 Resource/Data Owner PDP | 路由、聚合、解释授权结果 | ADS 不自授 Permit |
| DataUseGrant | Data Owner Grant Issuer | 协商与传播引用 | ADS 不代签数据许可 |
| Result / OutputArtifact | Result Producer / Artifact Owner | 关联成果与证据 | 不替代成果正文 Owner |
| AcceptanceRecord | 合同指定 Independent Acceptance Owner | 发起、汇总、读取 | SCO/执行者不能自行验收 |
| SettlementRecord | Settlement Owner；计量由 Metering Owner | 计算草案、路由争议 | 计算草案不是最终结算 |

## 2. 全局交易状态

`Draft → Validating → AwaitingApproval → Prepared → Committing → Committed → BarrierPending → Activated → Executing → ResultPending → AcceptancePending → Accepted → SettlementPending → Settled`

终态/异常态：`Rejected`、`Aborted`、`Compensating`、`RecoveryRequired`、`Disputed`、`Expired`、`Unknown`。

全局状态是 SCO 的编排投影；每个状态必须引用站点权威回执和版本。全局状态不得覆盖站点的 TaskRun、Lease、Policy 或 Acceptance 原始事实。

## 3. 单站点本地状态

### 3.1 Reservation

`Requested → Prepared → Committed → Released`，并支持 `Rejected`、`Expired`、`Unknown`。

- Prepared 表示站点已暂时准备满足指定资源约束，带 `prepared_until` 和 reservation owner 签名。
- Committed 表示本地 Lease Authority 已签发有效 ResourceLease 与单调递增 FencingToken。
- Prepared 不等于已获得长期资源权；超时后需释放或重新 Prepare。

### 3.2 TaskRun

`Queued → Preparing → Ready → Running → Suspended → Succeeded/Failed/Cancelled`。

- Start 必须在本地校验 TaskClaim、有效 Lease、FencingToken、PolicyDecision、DataUseGrant、Attestation、数据本地性和运行环境健康。
- Resume 必须重新校验 Lease、撤销水位、策略和数据授权。
- Cancel 需要 Local Task Coordinator 的 StopReceipt；Lease 释放另有 ReleaseReceipt。

## 4. Activation Barrier

Barrier 是从资源准备到实际执行之间的强制门禁，不是普通通知事件。Barrier 满足以下条件才可从 `BarrierPending` 进入 `Activated`：

1. 合同版本、任务目标、验收标准与所有参与站点绑定的摘要一致。
2. 所有必需站点均返回有效 CommitReceipt；回执签名、对象版本、Lease 有效期与 FencingToken 单调性通过验证。
3. 目标资源 Owner PDP 为每个站点/动作签发当前有效 Permit；任何 `Deny` 或 `Indeterminate` 均阻断。
4. Data Owner 对所需数据版本、用途、地域、接收方、衍生物、保留和删除义务签发有效 DataUseGrant。
5. TrustAgreement、Credential、Attestation、Policy 与 Grant 的撤销水位处于允许的最大陈旧窗口内。
6. 所有站点本地 LCP 返回 ReadyToActivateReceipt；本地 TaskClaim 已绑定正确 transaction、contract digest 和 attempt。
7. 预算、配额、成本上限、数据本地性、资源拓扑和故障域约束满足合同。
8. Activation token 绑定 transaction_id、contract_digest、participant set、lease refs、fencing token refs、barrier epoch、expiry；不得跨交易复用。

### 4.1 Barrier 失败规则

- 任一必需站点拒绝或超时：全局交易不得进入 Activated。
- 部分 Commit 成功：进入 `Compensating`，停止所有站点启动；按站点 Owner 回执释放已提交 Lease/Reservation。
- 无法确认某站点状态：进入 `RecoveryRequired` / `Unknown`，先查询权威 Owner，不得推断成功或失败。
- Barrier 激活后若策略/Grant/Trust 被撤销：触发本地 stop/suspend 规则与 Saga，不允许继续使用过期授权。

## 5. 推荐交易序列

1. Task Owner 创建并签署 TaskContract；SCO 校验合同、本体 Profile 和兼容性。
2. ADS/目标 Owner PDP 评估主体、资源、动作、purpose、数据与环境，返回 Decision 引用。
3. SCO 生成候选 TaskPlan；Task Owner 选择明确版本与 digest。
4. SCO 向 Site A/B 分别发 Prepare 请求；各站点本地 Reservation Authority 返回 PrepareReceipt 或 RejectReceipt。
5. SCO 对所有 PrepareReceipt 做签名、TTL、约束和版本校验；满足后发 Commit 请求。
6. 各 Site Lease Authority 自主决定 Commit，签发 ResourceLease / FencingToken 与 CommitReceipt。
7. SCO 建立 Activation Barrier，核对所有回执、撤销水位、Policy/Grant、TaskClaim 和 ReadyToActivateReceipt。
8. Barrier 通过后，SCO 发 ActivationNotice；Site LCP 再次本地检查并启动 TaskRun。
9. 站点通过事件/回执更新 TaskStage；SCO 只维护投影并保留 event_cursor。
10. Result Producer 提交 Result/OutputArtifact 引用；Independent Acceptance Owner 按冻结 criteria 验收。
11. Metering Owner 提交签名计量；Settlement Owner 计算/确认/结算；争议进入 Disputed。

## 6. 关键不变量

- **I-01**：SCO 只对全局交易编排状态负责；Site Owner 对本地执行/资源事实负责。
- **I-02**：任何必需站点未 Commit，不得激活全局 Barrier。
- **I-03**：TaskClaim 与 ResourceLease 分离；二者都不能替代 PolicyDecision。
- **I-04**：每个 Lease 的 FencingToken 对资源 Owner 单调递增；旧 token 永远不能恢复有效。
- **I-05**：Operation Accepted 不能作为 Reservation/Lease/TaskRun/Acceptance 的事实证据。
- **I-06**：Unknown 不是 Failed；先 Reconcile，后重试/补偿。
- **I-07**：所有跨站点命令均绑定 request_id、correlation_id、idempotency_key、contract digest、transaction epoch 和 expiry。
- **I-08**：数据授权由 Data Owner 签发；访问在目标 Site PEP 再次判定。
- **I-09**：执行成功不等于验收成功；验收成功不等于结算完成。
- **I-10**：跨站点状态同步通过共享环境中的持久状态、事件与签名回执完成；A2A 消息只用于协商/唤醒/异常升级，不作为唯一事实源。

## 7. Stigmergy / 共享环境协作落点

多 Agent/多站点协作以共同环境的状态演化为中心：`Transaction Ledger` 保存权威引用与状态版本，`Event Journal` 保存事实事件，`Work Queue` 保存待处理任务，`Evidence Store` 保存签名回执，`Ontology Registry` 提供共同语义。Agent 读取共享状态、基于条件声明 claim、写入结果/证据，再由其他 Agent 观察状态变化继续工作。

A2A 仍有价值，但定位为点对点协商、能力询问、人工升级和短时唤醒；不得把高频状态同步、重复汇报和关键事实只放在聊天记录中。共享状态写入需通过 Owner 权限和版本控制；Agent 不能因看见某条事件就自动获得授权。

## 8. 放行状态

当前为候选状态机。正式放行需：双方 Owner 确认必需站点集合、Barrier 条件、TTL、租约语义、补偿权限、独立验收与争议规则；并通过双实现和故障注入验收。不得将本文件表述为真实双站点已部署或已通过测试。
