# G2-04｜REST Binding RC1 与双站点交易状态机（架构摘要）

**状态：** 架构候选，待Owner评审与双站点互操作验证  
**范围：** 纯架构研究；不代表接口已实现或生产冻结。

## 1. 交易参与方与权威边界

- SCO：维护全局Task Transaction、协调各站点Prepare/Commit、收集回执、发起Saga补偿；不持有站点资源的最终承诺权。
- Site A / Site B Task Coordinator：验证本地TaskClaim、合同约束、数据授权、运行依赖，维护本地TaskRun/TaskStage。
- Site Lease Authority：独立决定本地资源预留、签发ResourceLease与单调递增FencingToken、续租和释放。
- Site PDP/PEP：在Prepare、Commit、Start、Resume等敏感动作前执行本地策略检查；跨域ADS决策不能绕过本地PEP。
- Data Owner / Artifact Owner / Independent Acceptance Owner：分别负责数据用途授权、成果对象和独立验收结论。

## 2. 双站点交易状态机

`Draft → Validating → Prepared → CommitPending → Committed → ActivationPending → Active → Completing → Completed`

异常状态包括 `Aborting`、`Compensating`、`PartiallyCommitted`、`Unknown`、`Expired`、`Failed`。

### Prepare

1. SCO创建全局transaction_id和稳定的idempotency key。
2. 向Site A/B分别发送Prepare请求，绑定TaskContract版本、Plan digest、资源需求、purpose、Policy/Grant引用和deadline。
3. 每个Site本地PDP/PEP复核，并由本地Reservation Authority决定是否预留。
4. 返回签名PrepareReceipt，至少包含site_id、transaction_id、reservation_id、prepared_until、resource_digest、authority_ref、state_version、issued_at。
5. 任一站点拒绝或超时：进入Abort/Unknown处理；不得把缺失回执当作成功。

### Commit

1. SCO校验全部PrepareReceipt未过期、摘要一致、授权仍有效。
2. Commit前再次执行撤销水位和策略复核。
3. 各站点Lease Authority独立签发ResourceLease和FencingToken。
4. SCO收集签名CommitReceipt；部分成功进入PartiallyCommitted并触发Saga补偿。
5. Commit成功仅表示资源承诺完成，不表示任务已启动。

### ActivationBarrier

- 只有所有必需站点的CommitReceipt齐全、Lease仍有效、Policy/Grant未撤销、Ontology/Profile兼容、TaskClaim有效时，才可跨站点进入ActivationPending。
- Site本地仍需再次通过PEP与健康检查，随后由本地Task Coordinator启动。
- 任一站点不能通过Barrier时，禁止另一站点单边宣布全局Active。

## 3. UNKNOWN 与幂等规则

- 超时后状态为UNKNOWN，不得直接重试非幂等副作用。
- 先使用transaction_id、idempotency key和operation_id向权威Owner查询。
- 相同key、相同规范化请求摘要：返回原结果；相同key、不同摘要：409 Conflict。
- 请求状态未知且无法确认是否已提交时，禁止重新分配资源；进入ReconciliationRequired。
- FencingToken必须单调递增；旧Token请求在资源执行面被拒绝。

## 4. Saga补偿

| 失败阶段 | 补偿动作 | 权威确认 |
|---|---|---|
| Prepare部分成功 | CancelReservation | 各Site Reservation Authority |
| Commit部分成功 | Revoke/Release已签发Lease | 各Site Lease Authority |
| Activation失败 | Stop本地TaskRun并保留证据 | 各Site Task Coordinator |
| 结果提交后验收失败 | 保留Result与Evidence，按合同重做/争议 | Result Owner / Acceptance Owner |
| 撤销传播不完整 | 阻断高风险后续动作并对账 | Issuer / PDP / PEP |

补偿不是回滚历史事实；每一步必须追加不可变事件和回执，记录部分成功、失败原因、重试次数与最终对账结果。

## 5. REST Binding RC1建议

- 写操作：`Idempotency-Key`、`X-Request-ID`、`X-Correlation-ID`。
- 条件更新：`If-Match` / `ETag`；缺失返回428，版本不符返回412。
- Header与Body重复的request_id/correlation_id必须一致。
- caller_principal、workload_identity、audience从已验证认证上下文提取，不信任请求体自报。
- 每个异步响应返回Operation与强类型result_ref；Operation只描述命令处理进度。
- ResponseContext应包含authority_ref、object_version、authoritative_state、as_of、freshness、event_cursor和evidence_refs。
- 列表响应使用Page<T>、next_page_token、source_ref与freshness，不用ResourceReference冒充完整列表。

## 6. 最低互操作验收场景

1. Site A Prepare成功、Site B拒绝：验证取消A预留并形成补偿回执。
2. A Commit成功、B Commit超时：验证UNKNOWN对账，不重复分配。
3. B撤销DataUseGrant发生在Prepare与Commit之间：验证Commit前重新授权并Fail-closed。
4. 旧FencingToken重放：资源执行面必须拒绝。
5. If-Match版本冲突：返回412，不覆盖并发更新。
6. 相同幂等键不同请求摘要：返回409。
7. 网络分区期间Lease到期：本地执行面停止接受过期租约。
8. ActivationBarrier只有一站点满足：不得进入全局Active。
9. 重复、乱序、延迟事件：基于event_id/sequence去重并检测缺口。
10. 补偿执行中再次故障：可恢复Saga并保持证据链完整。

## 7. 放行门槛

- ADS/SCO API、REST Binding与DM04逻辑Envelope映射通过统一Schema验证。
- Owner/Coordinator/Authority责任矩阵由各站点签署。
- 两个独立实现通过相同契约测试。
- 以上故障场景通过注入测试并保留证据。
- SHA-256文件清单与发布归档校验通过。

**结论：** 全局交易由SCO协调，本地资源和执行由Site权威组件控制；跨站点成功必须由可验证回执和ActivationBarrier共同证明，不能由中心编排器单方面宣告。
