# G2-06.6｜跨区域 Saga 与恢复协议

**状态：** RC0 候选，待评审  
**适用：** 双区域、十星联邦中的跨区域任务委派与资源交易。

## 1. 设计原则

跨区域任务不假设存在覆盖所有站点的分布式 ACID 事务。采用持久 Saga 编排、站点 Owner 本地事务和可审计补偿。区域协调器可故障、替换或重建；本地已提交任务不依赖 RCP 持续在线。

核心原则：

1. 每个站点只对自己的 Reservation、Lease、TaskRun 和计量事实负责。
2. 区域层对委派和协调过程负责，不创造站点资源事实。
3. 部分成功不等于全局成功；必需站点未全部满足 Barrier，不得激活。
4. Unknown 必须先查询原 Operation/Owner；禁止换 Idempotency-Key 盲重试。
5. 补偿不是删除历史，而是追加 Stop/Release/Reconcile 等事实回执。
6. 超过风险阈值的补偿、数据销毁或资金结算动作必须进入人类审批。

## 2. 交易阶段

Draft → Validating → Proposed → Preparing → Prepared → Committing → Committed → BarrierPending → Activated → Executing → ResultPending → AcceptancePending → Accepted → SettlementPending → Settled

异常/恢复状态：Rejected、Expired、Aborted、Compensating、RecoveryRequired、Unknown、Disputed、Suspended。

所有全局状态都是 SCO 的编排投影；站点 Owner 的本地事实以各自回执为准。

## 3. 标准 Saga 步骤

| 步骤 | 发起者 | 目标 | 成功证据 | 失败/未知处理 |
|---|---|---|---|---|
| 1. 提案 | SCO | 目标 RCP | ProposalReceipt | 修订提案或终止 |
| 2. 校验 | 目标 RCP | 本地目录/Owner | ValidationReport | 硬约束不满足则拒绝 |
| 3. Prepare | RCP | Site Reservation Authority | Site PrepareReceipt | 超时先 Reconcile |
| 4. 汇总 Prepared | RCP/SCO | 全局 Ledger | RegionPrepareReceipt | 必需站点拒绝则补偿 |
| 5. Commit | RCP | Site Lease Authority | Site CommitReceipt + Lease Ref | 部分成功进入补偿 |
| 6. Barrier | SCO | 所有必需站点 | BarrierDecision + Receipt Set | 缺回执/撤销缺口则阻断 |
| 7. Activate | SCO/RCP | Site LCP | Local ActivationReceipt | 过期或本地复核失败则暂停 |
| 8. Execute | Site LCP | 本地执行器 | TaskRun 状态事件 | 站点自治处理并上报 |
| 9. Stop/Release | SCO/RCP 或本地安全策略 | Site Owner | StopReceipt / ReleaseReceipt | 未确认则 RecoveryRequired |
| 10. Reconcile | SCO/RCP | 原权威 Owner | ReconciliationReport | 未对账不得重试或结算 |

## 4. Prepare / Commit 规则

### 4.1 Prepare

Prepare 仅表示目标站点在明确的资源约束和有效期内暂时准备资源。PrepareReceipt 至少绑定：

- transaction_id、proposal_id、site_id；
- contract_digest、resource_request_digest；
- reservation_ref、owner_epoch、sequence_no；
- prepared_until、issued_at；
- policy_decision_ref、attestation_ref（适用时）；
- issuer_ref、signature_ref。

Prepare 不等于 Lease，不等于可启动执行。

### 4.2 Commit

Commit 必须由目标 Site Lease Authority 决策并签发 ResourceLease 与 FencingToken。RCP 只能汇总原始 CommitReceipt。

同一幂等键、同一 payload_digest 的重放返回同一 Operation/Receipt；同一幂等键、不同 digest 返回冲突。响应丢失时先按原 key 查询原 Operation，不得创建第二份 Lease。

## 5. Activation Barrier

所有必需站点满足以下条件才允许激活：

1. 必需站点集合与 proposal/contract digest 一致。
2. 每个必需站点存在有效 CommitReceipt，且 Lease/FencingToken 由正确 Owner 签发。
3. PolicyDecision 为 Permit，且撤销水位满足风险 Profile。
4. DataUseGrant 覆盖目标数据、purpose、处理方式、地域、保留和结果披露。
5. TrustAgreement、Credential、Attestation、Policy 与 Grant 有效。
6. Site LCP 返回 ReadyToActivateReceipt。
7. 资源拓扑、网络 QoS、存储位置、能源/设施和预算硬约束满足。
8. Activation token 绑定 transaction、contract digest、participant set、barrier_epoch 和 expiry。

任一条件缺失、拒绝或 Indeterminate，Barrier 不得激活。Barrier 激活后若发生高风险撤销，应触发本地 Stop/Suspend 规则，不得依赖全局消息到达后才阻断。

## 6. 补偿矩阵

| 已发生事实 | 补偿动作 | 事实记录 | 禁止做法 |
|---|---|---|---|
| 部分 Prepare 成功 | 对已 Prepare 站点请求 ReleaseReservation | ReleaseReservationReceipt | 删除 Prepare 历史 |
| 部分 Commit 成功 | 对已 Commit 站点请求 Stop/Release/Fence | StopReceipt、ReleaseReceipt | 继续激活部分站点 |
| Activate 响应未知 | 查询 Site LCP activation/task 状态 | ReconciliationReport | 再发新 token |
| 执行中撤销授权 | 本地 PEP 阻断，按风险 Stop/Suspend | PolicyDecision、StopReceipt | 沿用旧 Permit |
| 网络分区 | 站点按本地有效租约和策略自治 | 本地事件与恢复证据 | 无限制续租 |
| RCP 丢失状态 | 从持久 Saga Ledger 和 Owner 回执重建 | RecoveryCheckpoint | 从内存缓存推断成功 |
| 计量不一致 | 冻结争议项并交独立对账 | DisputeCase | 改写原始计量 |

## 7. 恢复流程

1. RCP 恢复后先读取持久 Saga Ledger、region_epoch 和最近连续事件游标。
2. 对所有未决交易标记 Unknown/RecoveryRequired，不假设成功或失败。
3. 向每个 Site Owner 查询 Reservation、Lease、TaskRun、Policy 和撤销水位。
4. 对比 contract_digest、owner_epoch、sequence_no、FencingToken 和有效期。
5. 发现重复 Lease、旧 token、签名冲突或撤销缺口时隔离交易并升级安全治理。
6. 仅在权威状态可证明时推进补偿或恢复；无法证明时保持冻结。
7. 生成 RecoveryReport，记录请求、响应、证据、差异和人工决策。
8. 恢复新的跨区域交易前验证目录新鲜度、RCP 代次和区域网络健康。

## 8. 网络分区行为

- 已提交本地任务：可在有效 Lease、本地策略、数据授权和设施联锁允许的范围内继续。
- 新跨区域交易：不得在远端 Owner 状态未知时完成 Commit 或 Barrier。
- 已存在跨区域任务：按合同的分区策略选择继续、暂停或停止；不得扩大离线权限。
- 续租：仅由本地 Lease Authority 按已批准策略决定，不允许 RCP/ADS 离线延长。
- 重连：先交换撤销水位、Owner epoch、Lease 摘要、事件游标和证据引用，再恢复新交易。

## 9. 人工审批与风险门禁

必须进入外环审批的候选场景：

- 跨区域数据用途或地域边界变更；
- 高风险凭证/信任根轮换失败；
- 无法自动确认的 Stop/Release；
- 可能造成数据丢失或不可逆删除的补偿；
- 结算金额或责任归属争议；
- 多站点状态互相矛盾且无法由 Owner 证据消解。

人工审批不能通过直接改写站点事实解决冲突；应记录审批主体、理由、授权范围、有效期和独立验证结果。

## 10. 放行条件

需通过部分 Prepare/Commit、响应丢失、重复命令、区域主节点切换、网络分区、撤销缺口、过期 Lease、旧 FencingToken、Stop/Release 失败、恢复重放和人工审批测试。所有测试必须由两套独立实现互操作并保留可复核证据。
