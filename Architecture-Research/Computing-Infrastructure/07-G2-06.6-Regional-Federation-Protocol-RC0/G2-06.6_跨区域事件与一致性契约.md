# G2-06.6｜跨区域事件与一致性契约

**状态：** RC0 候选，待评审  
**目标：** 统一跨区域事件信封、Owner 顺序、去重、快照修复、撤销传播与状态投影。

## 1. 事件事实模型

采用“Owner 产生事实、事件携带引用、区域聚合投影、全局按需汇总”的模型。

- 事件只由对该事实拥有权威的主体发布。
- RCP 可以发布区域协调事件，但不能以区域事件覆盖 Site Owner 的 Lease、TaskRun、Policy 或 Metering 事实。
- SCO 的全局状态是跨站点交易投影，必须保留每个站点来源事件和回执引用。
- Agent 之间的消息不是唯一事实来源；事件必须落入可重放的持久事件日志或 Owner 证据存储。

## 2. 事件信封

建议使用 CloudEvents 1.0 作为通用事件信封，领域载荷由 Ontology Profile 和本阶段 Schema 定义。

| 字段 | 语义 |
|---|---|
| specversion | CloudEvents 规范版本 |
| id | 事件唯一标识，用于去重 |
| source | 产生事件的 Owner/系统 URI |
| type | 稳定的领域事件类型 |
| subject | 被影响对象 URI |
| time | Owner 声明的事件发生时间 |
| datacontenttype | 载荷媒体类型 |
| dataschema | 对应领域 Schema URI |
| data | 领域事件载荷 |
| region_id | 所属区域 |
| owner_id | 事实 Owner |
| owner_epoch | Owner 当前代次 |
| sequence_no | Owner 事件流内单调序号 |
| entity_version | 对象版本 |
| correlation_id | 跨区域任务关联 |
| causation_id | 引发当前事件的命令/事件 |
| payload_digest | 载荷摘要 |
| revocation_watermark | 撤销状态水位引用 |

region_id、owner_id 等扩展属性应按 CloudEvents 扩展属性命名规则绑定；具体序列化与签名方式由 Profile 冻结。

## 3. 顺序与一致性边界

### 3.1 不承诺全局总序

跨区域系统不建立所有站点事件的单一全局总序。每个 Owner 对自己的事实流提供单调顺序：

(owner_id, owner_epoch, sequence_no)

同一 Owner、同一 epoch 内 sequence_no 必须单调递增。不同 Owner 的事件仅通过 correlation_id、causation_id、业务状态机和权威回执建立因果关系，不比较无意义的全局序号。

### 3.2 Owner epoch

Owner 更换、恢复或发生权威代次切换时递增 owner_epoch。旧 epoch 的迟到事件可以进入审计，但不得覆盖新 epoch 的当前事实。区域协调器切换使用独立 region_epoch；不能把 region_epoch 当作 Site Lease FencingToken。

### 3.3 重复和乱序

- 相同 event id 重复投递：消费者去重，不重复执行副作用。
- 相同 Owner/epoch/sequence_no、不同 digest：视为完整性冲突，隔离并报警。
- 低 sequence_no 迟到：保留审计，不回退当前状态。
- sequence_no 出现缺口：标记 stream_gap，向原 Owner 请求补传或快照。
- 快照低于已确认撤销水位：拒绝应用。
- 事件时间戳仅用于观察，不用于替代 Owner 顺序。

## 4. 快照与事件恢复

建议采用“快照 + 增量事件”恢复：

1. 消费者记录每个 Owner 的 last_contiguous_cursor。
2. 检测到序列缺口或 epoch 变化时暂停相关状态投影。
3. 向原 Owner 请求签名快照，携带 last_known_epoch、last_known_sequence 和当前撤销水位。
4. 验证 Owner 身份、签名、snapshot_digest、epoch 和 sequence。
5. 从快照游标之后补传事件，按 Owner 顺序重放。
6. 重新核验 Policy、Grant、Trust、Lease 和 Attestation 的撤销水位。
7. 只有状态连续且关键授权新鲜后，才恢复受影响的跨区域交易。
8. 保留 gap report、snapshot receipt、replay range 和审计引用。

禁止采用无条件 last-write-wins；禁止因某个区域缓存较新而推断它拥有站点事实权威。

## 5. 撤销事件优先级

撤销、紧急停止和安全联锁使用独立高优先级通道，避免被普通遥测、资源目录刷新或统计事件挤压。

| 级别 | 事件类别 | 处理要求 |
|---|---|---|
| P0 | 身份/凭证撤销、DataUseGrant 撤销、Policy 禁止、设施联锁、Lease fencing | 立即进入治理处理队列；目标 PEP 按风险策略阻断 |
| P1 | Prepare/Commit/Lease/TaskRun/Stop/Release 事实 | 高优先级持久化与确认 |
| P2 | 任务路由、目录变更、资源健康变化 | 有序消费，支持快照修复 |
| P3 | 非关键遥测、分析指标、容量预测 | 可批量、可采样、可降频 |

事件优先级不能改变 Owner 归属。撤销发布者负责撤销事实，目标执行点负责执行本地阻断。

## 6. 消费者确认与背压

- 消费者只有在事件持久化或完成可恢复处理后才确认 cursor。
- 不允许先确认后处理，导致崩溃后丢失事实。
- 背压时先降低 P3，再限制非必要 P2；不得丢弃 P0/P1。
- 对超过保留窗口的事件缺口，必须请求权威快照并记录证据，不得静默跳过。
- 重试必须带 event id 与原始 digest，防止重新编码造成语义漂移。

## 7. 时间与有效期

time、observed_at、issued_at、expires_at 是不同语义：

- time：Owner 声明的事实发生时间。
- observed_at：消费者观察到事实的时间。
- issued_at：凭证或授权发布的时间。
- expires_at / valid_until：有效性截止时间。

系统时钟偏差必须被监测。任何超出允许时钟偏差或有效期窗口的高风险命令，按安全 Profile 拒绝或转人工处理。允许偏差阈值由现场 NTP/PTP 能力、网络条件和风险分析确定，不在 RC0 中固化通用数值。

## 8. 一致性验收

至少验证：重复投递、乱序投递、事件丢失、sequence gap、Owner epoch 变化、区域协调器重启、快照陈旧、撤销延迟、签名失败、digest 冲突、消费者崩溃、背压与恢复。每项都要记录源 Owner、事件游标、最终状态、恢复时间和审计证据。

## 9. 放行条件

本契约为候选。正式冻结前需确认 CloudEvents 扩展字段、Ontology 事件类型目录、Owner 流分区键、快照 API、撤销最大陈旧窗口、签名 Profile、事件保留策略和独立实现互操作结果。
