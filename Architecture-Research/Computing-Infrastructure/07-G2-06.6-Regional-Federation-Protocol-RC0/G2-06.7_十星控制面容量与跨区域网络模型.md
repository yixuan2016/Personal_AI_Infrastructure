# G2-06.7｜十星控制面容量与跨区域网络模型

**状态：** RC0 研究候选，待现场参数与 Owner 评审  
**规模假设：** 双区域、每区域五个异构算力星，共十星  
**性质：** 架构与测量模型，不是设备选型清单、容量承诺或工程实现

## 1. 研究目标

本阶段建立十星规模下的控制面容量、跨区域网络、数据移动、异构资源和能源约束模型。目标不是给出未经现场测量的固定带宽、GPU 数量或吞吐量，而是确定需要测量的变量、计算关系、故障场景和验收方法。

十星架构必须把以下三个维度分开：

1. **部署维度：** 全球/区域/站点服务部署在哪里，是否共址、跨可用区或多运营商。
2. **数据维度：** 数据留域、区域复制、派生数据、模型制品和结果披露的权属与路径。
3. **服务维度：** 单体、模块化单体或渐进式服务拆分；不能把双区域部署直接等同于微服务。

## 2. 十星拓扑与故障域

建议采用两个区域，每区五个算力星。每颗星可以具有不同的 CPU/GPU、存储、边缘推理、网络和能源画像；不要求十颗星同构。

区域内由 RCP 汇总发现和协调；跨区域由全局 ADS/SCO 协调意图与任务图；每颗星的 LCP、Lease Authority、PDP/PEP 和专业资源 Owner 保留本地最终权威。

网络与故障域至少分成：

- 站点内部 GPU Scale-up Fabric；
- 站点存储网络；
- 站点管理与控制网络；
- 租户接入网络；
- 区域站点互联网络；
- 区域间广域网络；
- 独立带外管理与设施联锁网络。

网络冗余不能只按运营商数量判断。必须验证物理路由、管道/机房、供电、接入点、自治系统、上游承载和故障切换路径是否真正独立。

## 3. 五个流量平面

| 流量平面 | 典型内容 | 时延/吞吐特征 | 设计原则 |
|---|---|---|---|
| 控制面 | 任务意图、目录摘要、Prepare/Commit、策略、撤销、回执 | 消息小、交互多、时延敏感 | 区域优先、幂等、优先级隔离 |
| 数据面 | 数据集、模型制品、Checkpoint、输出 | 大流量、吞吐敏感 | Owner 授权、数据路径独立 |
| GPU Fabric | GPU 间同步、集合通信、内存访问 | 极低时延、高带宽、拓扑敏感 | 默认站点内；跨区域须专项验证 |
| 存储面 | NVMe、分布式存储、对象存储、缓存 | IOPS、吞吐、尾时延并重 | 数据位置与计算位置联合调度 |
| 管理/设施面 | 设备管理、监控、供电、制冷、联锁 | 安全与可用性优先 | 与租户数据面隔离，保留带外通道 |

控制面与数据面不得共用一个未经隔离的拥塞域。P0 撤销、停止和设施联锁不能被大文件传输或普通遥测挤压。

## 4. 控制面容量模型

### 4.1 请求到达率

区域控制面请求负载可分解为：

**λ_RCP = λ_discovery + λ_validation + λ_prepare + λ_commit + λ_status + λ_event + λ_policy + λ_reconcile**

其中每一项都要按峰值、突发、重试和扇出计算，而不能只用平均任务数估算。

若任务到达率为 λ_task，单个任务涉及 N 个站点，单站点交易阶段产生的平均控制操作数为 M_site，则交易相关请求量可用：

**λ_transaction ≈ λ_task × N × M_site**

此处 M_site 必须从协议调用图和实测追踪中获得，不能凭经验固定。并行阶段的墙钟时延由最慢必需站点和协调开销决定，而非简单把所有站点时延相加。

### 4.2 排队与容量

对某一服务队列，初步使用：

**ρ = λ / (c × μ)**

- λ：该队列到达率；
- c：并行处理单元数；
- μ：单个处理单元服务率；
- ρ：利用率。

该公式用于建立容量关系，不代表仅凭 ρ 就能推导真实 P99。需要进一步测量服务时间分布、突发、队列长度、锁竞争、数据库连接、下游 Owner 等待、重试和网络抖动。

容量目标必须保留故障余量：至少验证单实例失效、单可用区失效、单运营商故障、突发任务和撤销洪峰叠加时的排队表现。

### 4.3 交易扇出与事件量

十星控制面压力不只由任务数量决定，还取决于每个任务涉及的站点数、候选数、事件数和状态查询频率。

建议采集：

- 每个任务的候选区域数、候选站点数和最终参与站点数；
- 每阶段 API 请求数、重试数、超时数和幂等命中数；
- 每站点事件数、事件字节数、消费者积压和缺口恢复量；
- Saga 未决交易数、平均等待时间和最长等待时间；
- Owner 查询次数、缓存命中率和目录陈旧拒绝数；
- P0/P1/P2/P3 队列的排队时间、丢弃/限流和恢复时间。

## 5. 网络性能模型

### 5.1 路径时延

控制面端到端时延可拆为：

**T_control = T_ingress + T_discovery + T_validate + T_prepare + T_commit + T_barrier + T_activation**

Prepare/Commit 对多个站点并行时，阶段时延主要受必需站点中的慢路径影响：

**T_prepare_stage ≈ max(T_prepare_site_i) + T_coordination_overhead**

应分别报告 P50、P95、P99、最大值和超时比例，不能只报告平均 RTT。

### 5.2 有效吞吐

跨区域数据传输时间的初步估算：

**T_transfer ≈ D / B_effective + T_setup + T_retransmission + T_crypto**

其中 D 是实际传输字节数；B_effective 受路径最窄链路、拥塞、协议开销、丢包重传、加密和限速影响。端到端有效带宽不能将各链路标称带宽简单相加。

路径 RTT 可拆为传播、排队、转发和端点处理；丢包率、抖动、重传率、乱序、MTU 与拥塞窗口都需要纳入测试。

### 5.3 数据位置决策

对数据量 D 的任务，应比较：

- 数据留在源站，计算移动到数据侧；
- 授权派生数据传输到目标区域；
- 传输模型/代码到数据侧；
- 在许可范围内传输结果或统计摘要。

不能只比较带宽和费用，还要考虑 DataUseGrant、地域限制、结果披露、保留/删除、能源和风险。原始数据默认留在 Owner 控制边界。

### 5.4 GPU 同步边界

站点内部 GPU Scale-up Fabric 与跨区域 WAN 的能力边界必须明确。默认不把跨区域网络当作 GPU 集合通信的硬实时互连。跨区域分布式训练、梯度同步或模型并行，必须先证明其通信模式、同步频率、尾时延、丢包恢复、Checkpoint 和失败恢复满足任务 SLO，再单独签署网络与资源合同。

## 6. 异构资源有效容量

资源能力不是单一算力分数。对每类任务，应构建资源向量：

- CPU：ISA、核心/线程、NUMA、内存带宽和本地存储；
- GPU：型号、显存/HBM、驱动/固件、互连拓扑、可用实例和隔离能力；
- 存储：容量、IOPS、吞吐、尾时延、复制因子和数据位置；
- 网络：路径、RTT、带宽、丢包、抖动、QoS 和隔离；
- 能源：可用功率、峰值限制、供电冗余、储能与碳因子；
- 热管理：冷却余量、进出水温、热密度、设施告警和维护窗口。

对某任务的可用容量是这些硬约束的交集，不是各资源数值相加。可用容量必须扣除已预留、故障、维护、安全余量、策略限制和设施约束。

调度顺序应为：硬约束过滤 → Owner 报价/容量复核 → 资源组合 → 多目标排序（完成时间、成本、能耗、碳强度、可靠性、公平性）→ 本地 Prepare/Commit。低成本或高性能不能抵消数据主权、安全等级、设备兼容和设施安全等硬约束。

## 7. QoS 与流量优先级

| 优先级 | 内容 | 过载行为 |
|---|---|---|
| P0 | 撤销、急停、设施联锁、安全阻断 | 保留独立队列与带外通道 |
| P1 | Prepare、Commit、Lease、Stop、Release、Reconcile | 限制新交易，保护既有交易与恢复 |
| P2 | 任务路由、目录更新、健康状态 | 降频、批处理、限流 |
| P3 | 非关键遥测、统计、预测和离线分析 | 可采样、延迟或暂停 |

网络 QoS 标签必须映射到真实交换机、路由器、队列和运营商合同，并通过端到端测量验证。只在应用 Header 中标注优先级，不代表网络已经提供 QoS。

## 8. SLO 与测量指标

| 领域 | 指标 | 解释 |
|---|---|---|
| 控制面 | API P50/P95/P99、队列时延 | 区分自身处理与下游等待 |
| 调度 | Submit→Plan、Plan→Prepare、Prepare→Commit | 分段识别瓶颈 |
| 目录 | Snapshot Age、Stale Reject Rate | 防止旧容量被误用 |
| 网络 | RTT、抖动、丢包、重传、有效吞吐 | 按路径和运营商分组 |
| 数据 | 数据移动量、缓存命中、存储尾时延 | 评估数据位置策略 |
| GPU | 利用率、显存压力、互连吞吐、通信等待 | 区分算力瓶颈与通信瓶颈 |
| 能源 | 功率峰值、能耗、温度、冷却余量 | 设施约束参与调度 |
| 可靠性 | 失败率、恢复时间、未决 Saga、重复 Lease | 验证自治和恢复 |
| 治理 | 撤销收敛时间、撤销缺口、审批等待 | 保护外环治理能力 |
| 运营 | 资源公平、容量碎片、SLO 违约、争议率 | 验证可持续运营 |

每项指标都要定义采集点、统计窗口、分位数、标签、Owner、数据保留和独立复算方式。

## 9. 十星验证矩阵

按双区域、每区五星分层执行：

1. 单星基线：真实设备、网络、存储、供电、冷却和本地调度器。
2. 区域内验证：五站点目录、路由、网络 QoS、Owner Prepare/Commit 和故障隔离。
3. 双区域验证：跨区域目录、任务委派、数据位置、策略撤销和交易 Saga。
4. 负载验证：稳态、突发、阶梯增长、热点区域和高扇出任务。
5. 故障验证：链路中断、丢包、拥塞、运营商切换、RCP 失效、Owner 超时、撤销洪峰。
6. 恢复验证：事件缺口、快照修复、Owner epoch、region_epoch、Lease fencing 和计量对账。
7. 独立见证：第二套实现重放同一契约与故障场景，比较状态、错误、回执和证据。

仿真可以用于探索边界和生成测试，但不能代替真实十星互操作结论。

## 10. 待验证假设与停止条件

### 待验证假设

- 两区域网络具有可证明的路径多样性，而不只是不同运营商名称。
- RCP 控制面在单可用区或单节点失效后仍可恢复，且 P0/P1 不受 P3 洪峰阻塞。
- 区域目录刷新频率和 TTL 能在候选发现效率与陈旧风险之间取得平衡。
- 数据留域/计算到数据侧策略可以降低跨区域大流量并满足任务要求。
- 真实 GPU、存储、网络和设施约束可通过资源向量表达并由 Owner 复核。

### 停止条件

出现未授权数据出域、P0 撤销被阻塞、重复 Lease、旧 FencingToken 被接受、跨区域 GPU 同步未经验证即承诺、设施安全越界、无法恢复的事件缺口或原始计量证据被改写时，停止扩大规模并进入整改。

## 11. 放行条件

本阶段交付的是容量与网络测量模型。放行前必须获得真实站点参数、链路拓扑、设备兼容矩阵、存储与设施基线、负载画像、SLO 合同和故障演练报告。没有这些证据，不得给出固定十星吞吐、带宽、GPU 规模或生产可用性结论。
