# 579｜时间、版本、快照与事件排序一致性规范

**状态：** Temporal and Version Semantics Candidate

## 1. 设计目标

统一Source、Snapshot、RawAsset、KnowledgeAsset、ExtractionRun、Chunk和Evidence中的时间/版本语义，避免“更新时间”被误解为内容版本，“完成时间”被误解为业务生效时间，或时间戳被用于推断不存在的因果关系。

## 2. 时间类型

- Occurred At：来源业务事件实际发生时间；
- Captured At：本地采集动作发生时间；
- Acquired At：内容实际获取时间；
- Recorded At：进入当前系统记录时间；
- Created At：对象/记录创建时间；
- Updated At：对象元数据最近一次修订时间；
- Started/Completed At：某次处理尝试的开始/结束时间；
- Verified At：某次核验活动发生时间。

同名时间字段必须在Profile中固定一种语义。不得用一个timestamp同时代表上述多个事件。

## 3. 版本类型

| 版本 | 对象 | 变化触发 | 是否可变 |
|---|---|---|---|
| Object Version | 对象元数据/状态 | 元数据或对象状态修订 | 版本记录不可变 |
| Content Version | KnowledgeAsset内容 | 内容生成/更正/合并 | 不可变 |
| Snapshot Sequence | SourceSnapshot | 新一次采集 | 不可变 |
| Processor Version | 处理器/模型 | 处理器发布或服务端版本变化 | 不可变引用 |
| Configuration Digest | 单次Run配置 | 关键配置变化 | 不可变 |
| ChunkSet Version | 分块集合 | 新内容版本/策略重新分块 | 不可变 |
| Contract/Profile Version | 契约/Provider Profile | 规则或条款变化 | 不可变 |

## 4. 因果顺序

时间戳仅用于排序线索，不足以证明因果关系。需要明确的父版本、retry_of_ref、correlation_id、supersedes和派生关系作为因果边。跨系统时钟偏差、延迟回执和乱序事件必须被容忍。

## 5. 并发与冲突

Current Version更新必须有预期父版本或等价并发条件；冲突不得由最后写入者静默覆盖。重复/乱序事件应基于稳定Event/Operation ID进行去重和对账。缺少权威时钟时保留Unknown，不制造伪精确时间。

## 6. 历史可重建

历史Run、Chunk、Evidence和Decision必须固定所引用的内容版本、Processor/Profile版本和Policy版本。Current指针变化不得导致历史引用漂移。

## 7. 当前结论

时间与版本语义规则已形成候选；字段的具体类型、精度、时钟来源和迁移规则仍待Owner/Schema批准。
