# 485｜S1 Owner审议操作规程与批准证据规范

**状态：** Review Governance Candidate；No New Owner Approval Recorded

## 1. 目的与适用范围

本规程适用于S1六个既有OT及SourceSnapshot子记录的字段、关系、状态、逻辑契约、治理约束和跨模块交接审议。它规定如何提出问题、确认有权主体、记录结论、处理异议和判断批准证据是否充分；不替代各模块Owner的正式授权流程。

## 2. 审议单元

审议必须拆分为可独立判断的原子单元：
- 字段：一个Field ID及其语义、类型、基数、缺失、可变性、权威、敏感度和校验；
- 关系：一个关系谓词/引用边及其Domain、Range、基数、方向和删除行为；
- 状态转换：一个起始状态、目标状态、触发条件和守卫；
- 契约：一个Command、Query或Event的责任Owner、载荷和错误语义；
- 跨模块控制：一个明确的读/写/执行/批准边界；
- 变更：一个影响既有基线的原子变更提案。

不得用一个“Profile Approved”覆盖未逐项审议的字段和例外。

## 3. 审议前置材料

每个议题至少提供：议题ID、对象/字段/关系ID、当前候选定义、来源依据、目标Owner、会审方、候选选项、推荐方案、反方风险、影响对象、依赖决策、测试映射和所需批准证据。材料缺项时标记`PreparedWithGap`，不得进入批准结论。

## 4. 标准审议流程

1. **Intake**：登记问题来源、提交者、时间和原始材料。
2. **Authority Check**：核验谁有权决定语义、实例、物理保管、策略或个人主权。
3. **Pre-read**：将议题包和依赖项提前送达相关Owner。
4. **Review**：逐项确认事实、语义、选项、风险和未决假设。
5. **Disposition**：形成Retain/Revise/Split/Merge/Deprecate/Reject/Defer/Need-ACR等处置建议。
6. **Approval**：由有权Owner在其权限范围内作出明确结论。
7. **Evidence Capture**：保存签署、可核验书面确认或正式会议决议及范围。
8. **Impact Propagation**：更新受影响Profile、契约、测试、索引和版本关系。
9. **Independent Audit**：由非原提案人复核证据与传播完整性。

## 5. 结论状态

| 状态 | 语义 | 是否可作为冻结证据 |
|---|---|---|
| NotScheduled | 尚未安排 | 否 |
| Prepared | 材料准备完成 | 否 |
| InReview | 正在审议 | 否 |
| ClarificationRequired | 需要补充事实/证据 | 否 |
| OwnerApproved | 有权Owner明确批准 | 是，须有证据引用 |
| ApprovedWithConditions | 附条件批准，条件可验证且有责任人/期限 | 仅在条件满足后 |
| Rejected | 有权Owner拒绝 | 作为否决证据，不是批准 |
| Deferred | 延后处理 | 否 |
| Blocked | 依赖或权威冲突未解决 | 否 |

处置建议和审议状态必须分开记录。例如`ProposedRetain + InReview`不等于`OwnerApproved`。

## 6. 批准证据最低要求

批准证据应能回答：谁批准、以什么角色批准、批准什么精确范围、依据哪个版本、何时生效、有哪些条件/例外、是否有异议、证据是否可回溯。优先使用签署记录或有身份认证的书面确认；会议纪要必须明确决议文字、参会者角色、授权范围和确认人。

下列内容不能单独作为批准证据：聊天中的模糊赞同、未署名会议笔记、文档作者自行填写Approved、模型总结、无范围的“同意整体方案”、未核验的转述。

## 7. 异议与升级

异议必须记录提出者、角色、涉及范围、理由、证据、风险和建议处置。不同权威角色的意见不能通过简单多数表决替代。无法协调时按494号升级；涉及已批准OD的变更按496号路由。

## 8. 记录与审计

每项结论必须有唯一Decision Record，保留原始提案、历次版本、决定文本、证据引用、传播清单和Supersedes关系。不得覆盖旧结论或删除被否决的选项。

## 9. 本阶段状态
